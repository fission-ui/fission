## What you will build

In this tutorial, you will read or change supported audio settings while respecting system-level limits and user control. Try the interactive screen below in your browser. It changes local component state only; it does not open Android permission prompts, use device hardware or build an Android app. Follow the emulator checks below, then use a phone for hardware behavior.

### The Fission pieces in this example

Keep native work out of a component’s `view`: the component sends a typed request through an effect, and the host returns a success or error action for the reducer. That lets the screen stay responsive and show a useful recovery path. The browser preview below simulates these result states locally; the target checks later are where you verify the real capability.

## Create the project and add the target

Install the Fission command line, create the app, and add its native target.

```sh
cargo install cargo-fission
fission init android-use-android-volume-control-from-fission
cd android-use-android-volume-control-from-fission
fission add-target android --project-dir .
fission add-capability volume-control --project-dir .
```

## Files created by Fission

This is the starter tree after `fission init` and `fission add-target`; the component and state used for this task are additions in the steps below. Keep shared Rust behavior under `src/` and leave target launch and packaging in `platforms/android/`.

```text
android-use-android-volume-control-from-fission/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── android/              # generated Android host
```

Keep `src/app.rs`, shared state, reducers and reusable `fission_component!` components in the common Rust project. Add a state, service or effect module only when this feature needs that boundary, and use a name tied to the feature. The generated Android host owns launch and packaging details; shared components describe the user task without importing Android APIs.

## Connect the Volume Control provider to the user action

This is the real Fission request path for this feature. Keep permission and hardware work outside the component view: the component dispatches one intent, the reducer queues the request, and success or error reducers store the returned result.

Start with task data and status in the app state. Keep a text-field draft, open flag or selected tab in the owning component instead of duplicating that temporary state here:

```rust
#[derive(Debug, Default)]
struct VolumeControlState {
    // Add these fields to your existing app state.
    volume: Option<VolumeLevel>,
    volume_error: Option<String>,
}

impl GlobalState for VolumeControlState {}
```

Handle successful and failed results separately so the screen can explain denied permission, cancellation, unsupported hardware and provider errors:

```rust
#[fission_reducer(VolumeChanged)]
fn on_volume_changed(state: &mut VolumeControlState, level: VolumeLevel) {
    state.volume = Some(level);
    state.volume_error = None;
}

#[fission_reducer(VolumeChangeFailed)]
fn on_volume_change_failed(state: &mut VolumeControlState, error: VolumeError) {
    state.volume_error = Some(error.message);
}
```

Queue the operation after the user presses the named control. The host completes asynchronously and dispatches the matching reducer:

```rust
ctx.effects
    .volume()
    .adjust_level(VolumeAdjustRequest {
        stream: VolumeStream::Media,
        direction: VolumeAdjustDirection::Up,
        step: 5,
    })
    .on_ok(ctx.effects.bind(
        VolumeChanged(VolumeLevel::default()),
        reduce_with!(on_volume_changed),
    ))
    .on_err(ctx.effects.bind(
        VolumeChangeFailed(VolumeError::default()),
        reduce_with!(on_volume_change_failed),
    ));
```

Bind the user action from a reusable Fission component. Keep the visible label in the same control so it works with touch, keyboard and assistive technology:

```rust
fission_component!
{
    pub RaiseVolumeButton<VolumeControlState> {
    }
    view(component, _state, _cx) => rust {
        let (ctx, view) = fission::build::current::<VolumeControlState>();
                let run = with_reducer!(ctx, RaiseVolume, on_raise_volume);

                Button::new("Raise volume")
                    .disabled(false)
                    .on_press(run)
                    .into()
    }
}
```

The [complete Volume Control guide](/docs/capabilities/volume-control/) explains configuration and expected platform behaviour. Test a successful memory-provider response and an unavailable or denied response before relying on the physical-device check below. The browser preview exercises the component state only; it does not invoke this native provider.

Keep platform-only code behind the generated target boundary or a typed provider; the shared component should describe the user task rather than call an operating-system API directly.

## Verify the native request on Android

The browser controls simulate app state; they never send a request to the platform provider. Run the target below on an emulator or device that supports this feature. Follow the user path from the first explanation through the request and returned result, and keep success hidden until the host replies.

Repeat with the feature unavailable, denied or cancelled, as applicable. Confirm the screen preserves the user’s existing data and offers the right recovery step. Use a physical device when the behavior depends on real hardware or an operating-system prompt.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Android tools, `fission run` launches the selected emulator or connected device, and `fission test` checks that the generated host can start. A release build checks packaging, but none of these commands proves a physical permission or hardware flow works.


### Emulator and connected-device commands

Run these emulator checks from the generated project root:

```sh
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
```


For a real capability check, use an Android phone that has the required hardware and permission. Connect it with USB or Wi-Fi debugging, confirm its serial, then run the app on that device:

```sh
adb devices -l
fission run --target android --device <adb-serial> --project-dir .
```

An emulator can exercise the UI and memory-provider outcomes; it is not evidence that physical hardware or an OS permission flow works.
