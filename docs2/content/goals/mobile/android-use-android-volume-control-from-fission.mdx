## Create the project and add the target

Create the project and add the target used by this guide. Fission generates the native host; the app and its behaviour stay in shared Rust code.

```sh
cargo install cargo-fission
fission init android-use-android-volume-control-from-fission
cd android-use-android-volume-control-from-fission
fission add-target android --project-dir .
fission add-capability volume-control --project-dir .
```

## Files created by Fission

This is the starter tree Fission generates. Keep shared app code in `src/`; the generated platform files handle native launch and packaging.

```text
android-use-android-volume-control-from-fission/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── android/              # generated Android host
```

Keep the screen, shared state, reducers and reusable `fission_component!` components in the Rust project. Add a feature-specific state, service or effect module only when it gives the feature a useful boundary. The generated platform files handle native launch and packaging; shared components do not need to import platform APIs.

## Preview an alert-volume adjustment

The receiving team needs audible delivery alerts without quietly changing a user's system setting. This first screen lets the user try a five-point adjustment in component-local preview state. It does not read the Android setting; the next step requests the platform capability after the user chooses it.

use fission::prelude::*;

fission_component! {
    pub VolumeControlScreen<()> {
        state {
            preview_level: Option<u8> = None,
        }
    }
    view(screen, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
        let preview_level = screen.preview_level
            .map(|level| format!("{} {level}%", cx.tr("volume.preview_level")))
            .unwrap_or_else(|| cx.tr("volume.preview_not_set"));
    } =>
    SemanticsRegion(
        identifier: Some("alert-volume-preview".to_string()),
        label: Some(cx.tr("volume.title")),
        child: Container(
            Column(gap: tokens.spacing.m, children: [
                Text(cx.tr("volume.site"))
                    .weight(tokens.typography.font_weight_bold),
                Text(cx.tr("volume.title"))
                    .size(tokens.typography.heading2_size),
                Text(cx.tr("volume.stream"))
                    .color(tokens.colors.text_secondary),
                Container(
                    Column(gap: tokens.spacing.s, children: [
                        Text(cx.tr("volume.context")),
                        Text(preview_level),
                    ])
                )
                .padding_all(tokens.spacing.m)
                .bg(tokens.colors.background)
                .border(tokens.colors.border, 1.0)
                .border_radius(tokens.radii.medium),
                Button(
                    child: Text(cx.tr("volume.preview_action")),
                    key: "preview-volume-adjustment",
                    variant: ButtonVariant::Primary,
                    disabled: screen.preview_level == Some(100),
                    on_press: reduce {
                        screen.preview_level = Some(
                            screen.preview_level.unwrap_or(0).saturating_add(5).min(100),
                        );
                    },
                ),
            ])
        )
        .padding_all(tokens.spacing.l)
        .bg(tokens.colors.surface)
        .border(tokens.colors.border, 1.0)
        .border_radius(tokens.radii.large),
    )
}

## Run the Volume operation through Fission

Keep host work out of component conversion. The button dispatches a typed action, its reducer queues the capability request, and separate completion reducers update the screen. The Web preview installs `MemoryVolumeHost` and sends the same operation through Fission’s typed capability path. Its deterministic response is not a claim about device hardware, OS permission or native platform support.

The Web preview uses `MemoryVolumeHost` to exercise the typed capability with an in-memory volume level. It does not change the computer's or phone's system volume.

use fission::prelude::*;

#[derive(Debug, Default)]
pub struct VolumeControlState {
    pub pending: bool,
    pub level: Option<u8>,
    pub failed: bool,
}

impl GlobalState for VolumeControlState {}

#[fission_reducer(RunCapability)]
pub fn run_capability(state: &mut VolumeControlState, ctx: &mut ReducerContext<VolumeControlState>) {
    state.pending = true;
    state.level = None;
    state.failed = false;

    let ok: ActionEnvelope = CapabilitySucceeded.into();
    let err: ActionEnvelope = CapabilityFailed.into();

    ctx.effects
        .volume().adjust_level(VolumeAdjustRequest {
            stream: VolumeStream::Notification,
            direction: VolumeAdjustDirection::Up,
            step: 5,
        })
        .on_ok(ok)
        .on_err(err);
}

#[fission_reducer(CapabilitySucceeded)]
pub fn capability_succeeded(
    state: &mut VolumeControlState,
    ctx: &mut ReducerContext<VolumeControlState>,
) {
    state.pending = false;
    state.level = ctx
        .input
        .capability_ok(ADJUST_VOLUME_LEVEL)
        .map(|value| value.level);
    state.failed = state.level.is_none();
}

#[fission_reducer(CapabilityFailed)]
pub fn capability_failed(
    state: &mut VolumeControlState,
) {
    state.pending = false;
    state.level = None;
    state.failed = true;
}

pub fn callback_registry() -> ActionRegistry<VolumeControlState> {
    let mut registry = ActionRegistry::new();
    registry.register(reduce_with!(capability_succeeded));
    registry.register(reduce_with!(capability_failed));
    registry
}

fission_component! {
    pub VolumeControlScreen<VolumeControlState> {}
    view(_screen, state, cx) {
        let tokens = &cx.view.env().theme.tokens;
        let action = with_reducer!(cx.build, RunCapability, run_capability);
        let status = if state.pending {
            cx.tr("volume.waiting")
        } else if state.failed {
            cx.tr("volume.error")
        } else if let Some(level) = state.level {
            format!("{} {level}%", cx.tr("volume.level"))
        } else {
            cx.tr("volume.ready")
        };
    } =>
    SemanticsRegion(
        identifier: Some("alert-volume-adjustment".to_string()),
        label: Some(cx.tr("volume.title")),
        child: Container(
            Column(gap: tokens.spacing.m, children: [
                Text(cx.tr("volume.site"))
                    .weight(tokens.typography.font_weight_bold),
                Text(cx.tr("volume.title"))
                    .size(tokens.typography.heading2_size),
                Text(cx.tr("volume.stream"))
                    .color(tokens.colors.text_secondary),
                Text(cx.tr("volume.context")),
                Button(
                    child: Text(cx.tr("volume.action")),
                    key: "run-capability",
                    variant: ButtonVariant::Primary,
                    disabled: state.pending,
                    loading: state.pending,
                    on_press: action,
                ),
                Container(Text(status))
                    .padding_all(tokens.spacing.m)
                    .bg(tokens.colors.background)
                    .border(tokens.colors.border, 1.0)
                    .border_radius(tokens.radii.medium),
            ])
        )
        .padding_all(tokens.spacing.l)
        .bg(tokens.colors.surface)
        .border(tokens.colors.border, 1.0)
        .border_radius(tokens.radii.large),
    )
}

## Verify the native request on Android

The website preview cannot exercise the native provider. Build and launch this target on a supported emulator or device, then use the feature action from the component above. Check the result the host actually returns, including denial, cancellation or unsupported hardware where those outcomes apply.

Repeat with the feature unavailable, denied or cancelled, as applicable. Confirm the screen preserves the user’s existing data and offers the right recovery step. Use a physical device when the behavior depends on real hardware or an operating-system prompt.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Android tools, `fission run` launches the selected emulator or connected device, and `fission test` checks that the generated host can start. A release build checks packaging, but none of these commands proves a physical permission or hardware flow works.


### Emulator and connected-device commands

Run these emulator checks from the generated project root:

```sh
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
```


For a real capability check, use an Android phone that has the required hardware and permission. Connect it with USB or Wi-Fi debugging, confirm its serial, then run the app on that device:

```sh
adb devices -l
fission run --target android --device <adb-serial> --project-dir .
```

An emulator can exercise the UI and memory-provider outcomes; it is not evidence that physical hardware or an OS permission flow works.
