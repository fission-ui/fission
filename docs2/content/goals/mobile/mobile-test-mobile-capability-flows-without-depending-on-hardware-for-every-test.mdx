## Create the project and add the target

```sh
cargo install cargo-fission
fission init mobile-test-mobile-capability-flows-without-depending-on-hardware-for-every-test
cd mobile-test-mobile-capability-flows-without-depending-on-hardware-for-every-test
fission add-target android ios --project-dir .
```

## Files created by Fission

Fission generates Android and iOS hosts alongside the shared Rust project:

```text
mobile-test-mobile-capability-flows-without-depending-on-hardware-for-every-test/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    ├── android/              # generated Android host
    └── ios/                  # generated iOS host
```

Keep provider outcome handling in shared reducers. Tests can inject a memory provider, while the generated hosts connect the app to each target’s real provider.

## Use memory providers for success, denial and unsupported cases

Inject a memory provider at the capability boundary and drive its success, denied, unsupported and provider-error results through the same reducers used in production. Assert both the state transition and the user-visible recovery action. Keep a small real-device checklist for the behaviours a memory provider cannot prove, such as the native permission sheet, NFC scan session, camera focus or biometric prompt. This split keeps most tests fast and deterministic without making a false claim that all hardware paths were tested.

## Run the test layers for this task

Use a different check for each risk: `cargo test` for Rust rules you have written, `fission test` for the generated host smoke path, and LiveTest for the composed screen and user journey. A passing test at one layer does not replace the checks at the next layer.

Run the same critical journey on Android Emulator and iOS Simulator. Add a real-device check only for behavior the simulator cannot prove, such as a permission sheet, radio, camera, sensor or signed installation.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

`cargo test` runs Rust tests you add for reducer or stale-completion rules; the generated scaffold does not create those feature tests. `fission doctor` checks each target’s toolchain, `fission run` launches its emulator or Simulator, and `fission test` checks that the generated host can start. A release build validates packaging, not real hardware behavior.


### Run the shared project on both mobile targets

Run both target checks from the generated project root:

```sh
fission doctor android --project-dir .
fission run --target android --project-dir .
fission doctor ios --project-dir .
fission run --target ios --project-dir .
fission test --target android --project-dir .
fission test --target ios --project-dir .
```
