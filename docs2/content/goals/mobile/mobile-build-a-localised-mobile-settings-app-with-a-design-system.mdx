## What you will build

In this tutorial, you will let users change theme and language, persist preferences and verify long translations and accessible controls. Try the interactive screen below in your browser. It changes local component state only; it does not call the Android or iOS host. Follow each target’s run steps below, then check hardware behavior on a supported physical device.

### How the screen uses Fission

Throughout this guide, the screen is written as a `fission_component!`. That component owns its temporary interaction state and renders widgets from that state; a reducer changes it after a user action. Put durable facts shared across screens in `GlobalState`, and request native or service work through an effect or capability after the view is built.

## Create the project and add the target

Install the Fission command line, create the app, and add its native target.

```sh
cargo install cargo-fission
fission init mobile-build-a-localised-mobile-settings-app-with-a-design-system
cd mobile-build-a-localised-mobile-settings-app-with-a-design-system
fission add-target android ios --project-dir .
```

## Files created by Fission

This is the starter tree after `fission init` and `fission add-target`; the component and state used for this task are additions in the steps below. Keep shared Rust behavior under `src/` and leave target launch and packaging in the generated Android and iOS hosts.

```text
mobile-build-a-localised-mobile-settings-app-with-a-design-system/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    ├── android/              # generated Android host
    └── ios/                  # generated iOS host
```

Keep `src/app.rs`, shared state, reducers and reusable `fission_component!` components in the common Rust project. Add a state, service or effect module only when this feature needs that boundary, and use a name tied to the feature. The generated Android and iOS hosts own launch and packaging details; shared components describe the user task without importing either platform API.

## Try the browser-safe interaction

The preview is a compiled Fission component with two deliberately local simulations. Press **Simulate success** to inspect the normal result, then **Simulate unavailable** to see how the screen can explain that a capability cannot proceed. These actions change only preview state: they do not request permission, access a sensor or run the target app. In the main step, compare that state boundary with the feature-specific instructions.

```rust
use fission::prelude::*;

fission_component! {
    pub MobileSettingsApp<()> {
        props {
            title: String,
            step: String,
            goal: String,
        }
        state {
            simulated_success: bool = false,
            simulated_unavailable: bool = false,
        }
    }
    view(preview, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
    } =>
    SemanticsRegion(
        identifier: Some("tutorial-preview".to_string()),
        label: Some(preview.title.clone()),
        child: Container(
            Column(gap: tokens.spacing.m, children: [
                Text(preview.title.clone())

                    .weight(tokens.typography.font_weight_bold),
                Text(preview.step.clone())
                    .color(tokens.colors.text_secondary),
                Text(preview.goal.clone()),
                Button(
                    child: Text(if preview.simulated_success {
                        "Reset success simulation".to_string()
                    } else {
                        "Simulate success".to_string()
                    }),
                    key: "tutorial-complete",
                    on_press: reduce {
                        preview.simulated_success = !preview.simulated_success;
                        if preview.simulated_success { preview.simulated_unavailable = false; }
                    },
                ),
                Text(if preview.simulated_success {
                    format!("Simulated success for {}. Only browser-local state changed. Use the target steps below to verify the real behaviour.", preview.goal)
                } else {
                    "Ready: no native request has run. Choose a simulation to see how the screen state changes.".to_string()
                }),
                Button(
                    child: Text(if preview.simulated_unavailable {
                        "Clear unavailable simulation".to_string()
                    } else {
                        "Simulate unavailable".to_string()
                    }),
                    key: "tutorial-unavailable",
                    on_press: reduce {
                        preview.simulated_unavailable = !preview.simulated_unavailable;
                        if preview.simulated_unavailable { preview.simulated_success = false; }
                    },
                ),
                if preview.simulated_unavailable {
                    Text(format!("Simulated unavailable result for {}. No native request ran; the target app should explain the real reason and recovery action.", preview.title))
                } else {
                    Text("No unavailable response is being simulated.".to_string())
                },
            ])
        )
        .padding_all(tokens.spacing.l)
        .bg(tokens.colors.surface)
        .border(tokens.colors.border, 1.0)
        .border_radius(tokens.radii.large),
    )
}
```

## Build a localised mobile settings app with a design system

Copy the checked-in Fission DSP and token sources into design/, generate the typed design system from build.rs, and install it when the app starts. Put spacing, type and colour choices in the design tokens; read them from Env in the component. Keep light/dark selection and the selected Locale in app state, then synchronize both presentation inputs. Include English and Spanish bundles and check the longest translated setting labels at a large font scale on Android and iOS. See the [design system](/docs/guides/design-system/) and [theming and i18n](/docs/guides/theming-and-i18n/) guides.

The component below is a browser-safe version of this screen. It uses Fission's retained component state and widgets to make the task visible; it does not call a native provider or operating-system API.

<!-- fission:file path="src/app.rs" -->
```rust
use fission::prelude::*;

fission_component! {
    pub MobileLocalisedSettingsDesignSystem<()> {
        props {
            title: String,
            step: String,
            goal: String,
        }
        state {
            saved: bool = false,
        }
    }
    view(screen, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
    } =>
    SemanticsRegion(
        identifier: Some("design-system-settings".to_string()),
        label: Some(screen.title.clone()),
        child: Container(
            Column(gap: tokens.spacing.m, children: [
                Text(screen.title.clone())

                    .weight(tokens.typography.font_weight_bold),
                Text(screen.goal.clone()),
                Text("The spacing, colour, and type in this card come from the active theme tokens."),
                Button(
                    child: Text(if screen.saved { "Preferences saved" } else { "Save preferences" }),
                    key: "save-preferences",
                    on_press: reduce { screen.saved = !screen.saved; },
                )
                .semantics_identifier("settings.save"),
            ])
        )
        .padding_all(tokens.spacing.l)
        .bg(tokens.colors.surface)
        .border(tokens.colors.border, 1.0)
        .border_radius(tokens.radii.large),
    )
}
```

## Check translated text on Android and iOS

Switch between the configured languages and read every screen in the task. Long translations should wrap without hiding buttons, field errors or status messages; user-visible strings should come from translation keys rather than hard-coded component text.

Check the largest supported text size as well. Keep labels and actions understandable when they wrap to multiple lines, and verify that changing the locale updates the active Fission environment.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

`cargo test` runs Rust tests you add for reducer or stale-completion rules; the generated scaffold does not create those feature tests. `fission doctor` checks each target’s toolchain, `fission run` launches its emulator or Simulator, and `fission test` checks that the generated host can start. A release build validates packaging, not real hardware behavior.


### Run the shared project on both mobile targets

Run both target checks from the generated project root:

```sh
fission doctor android --project-dir .
fission run --target android --project-dir .
fission doctor ios --project-dir .
fission run --target ios --project-dir .
fission test --target android --project-dir .
fission test --target ios --project-dir .
```
