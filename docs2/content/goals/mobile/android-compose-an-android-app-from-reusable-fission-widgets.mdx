## The morning inspection round

We’re building the morning inspection board for a city tree-care crew. It needs to show which trees need attention, where they are, what the inspector found, and whether a crew has been assigned. Dispatch can assign an unowned inspection to the Green Crew, and the card and summary should update together.

Each inspection needs the same information and action, so it belongs in one reusable card. The dashboard arranges the cards and calculates its counts from shared records. The card owns presentation; app state remains the source of truth.

The browser preview starts with three sample records, so you can try the workflow before opening an emulator. They belong to the tutorial, not to production data. A real app would load inspections from a service or local database through an effect.

## Create the Android project

Install the Fission CLI, create the project, and add Android as a target. If this is your first Android build, follow the [Android development setup guide](/blog/set-up-rust-android-gui-development-with-fission/) first; it covers the SDK, NDK, and emulator setup.

```sh
cargo install cargo-fission
fission init urban-tree-rounds
cd urban-tree-rounds
fission add-target android --project-dir .
cargo add serde_yaml
```

Fission generates the Android host and Rust application shell. Keep the records, reducers, and screen in shared Rust code. The host launches and packages that app; it shouldn’t have a second copy of the inspection rules.

## Give each inspection a clear card

Before a crew walks to a tree, it needs the inspection number, species, location, priority, and a short report. `TreeInspectionCard` keeps that information in a consistent shape. Its props describe one inspection, so the parent can reuse it without the card reaching into unrelated app state.

The first version is read-only. Check that the records are easy to scan; we’ll add the assignment action next.

## Compose the dispatch board from reusable components

Now connect each card to app state. The board derives its counts from the records, so assigning a crew can’t leave a separate summary number stale. Each `TreeInspectionCard` receives one record and binds its button to a reducer that updates `TreeRoundsState`. All cards use the same component, and each button carries the ID of its own inspection.

Each card’s `key` is its durable inspection ID. When the list changes, Fission can keep retained widget state with the right inspection instead of reusing it for whatever row moves into the same position.

The tutorial keeps the source together so you can run it without creating a set of files first. In an app you plan to grow, put the model, reducer, card, and screen in focused modules. Those boundaries are already visible here; splitting them out doesn’t change how the components fit together.

fn assign_tree_to_green_crew(state: &mut TreeRoundsState, inspection_id: u32) {
    let Some(inspection) = state
        .inspections
        .iter_mut()
        .find(|inspection| inspection.id == inspection_id)
    else {
        return;
    };

    if inspection.status != InspectionStatus::NeedsCrew {
        return;
    }

    inspection.status = InspectionStatus::Scheduled;
    inspection.assigned_crew = Some("tree.assignment.crew");
    state.notice = Some(TreeAssignmentNotice::Assigned(inspection.id));
}

    assign_tree_to_green_crew(state, inspection_id);
}
