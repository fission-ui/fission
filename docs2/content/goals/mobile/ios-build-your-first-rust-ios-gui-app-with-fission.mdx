This tutorial shows how to create a small interactive counter and run it in an iPhone Simulator. The runnable example uses shared Rust code and Fission’s fission_component! API, then checks the parts that need a real iOS target. It assumes basic Rust syntax and explains app state, reducers and host work before using them.

## What you will build

You will build this workflow: create a small interactive counter and run it in an iPhone Simulator. The browser preview demonstrates the component and its state; it does not claim to run native permissions, sensors or device APIs. The final steps identify which checks need a real iOS target.


### The Fission pieces in this example

A component describes a part of the screen. fission_component! declares that component, its inputs and any retained local interaction state. GlobalState holds product data or routes used beyond one component. A typed action names something that happened; a reducer applies the state change synchronously. When an operation needs a file, database, network or operating-system API, the reducer queues an effect or capability request and a later action reports success or failure. This keeps slow work out of the UI rendering path.


## Create the project and add the target

Install the Fission command line, create the app, and add its native target. The [canonical iOS setup tutorial](/blog/set-up-rust-ios-development-with-fission/) covers SDK installation and device prerequisites.

```sh
cargo install cargo-fission
fission init ios-build-your-first-rust-ios-gui-app-with-fission
cd ios-build-your-first-rust-ios-gui-app-with-fission
fission add-target ios --project-dir .
```

The commands generate the shared Rust entrypoints and the selected native host. Add the focused modules shown below as you implement the feature; keep file, database, network and operating-system work out of component conversion and queue it through reducers and asynchronous effects.

```text
│   ├── components/

│   ├── effects/

├── platforms/

└── tests/

```

`src/app.rs` is the shared Fission application, not a platform-specific copy. Put one reusable view in a named `fission_component!` component, keep app truth in `GlobalState`, and keep a one-screen draft or open flag in that component’s retained state. A reducer records the user’s intent; an effect, job, service or capability performs work after the view is built. Show pending, success, denied or failed outcomes in the screen.

The live preview compiles the complete `src/app.rs` component to WebAssembly. It lets you try retained state and normal or unavailable UI states in the browser. The preview does not call Android or iOS hardware. Use the target commands and device checks below to verify native behaviour.

## Build the first iOS screen

Start with a counter whose value begins at zero. The text label and count are visible without interaction, and the named Increase count and Reset counter buttons work with touch, keyboard and assistive technology. The retained count belongs in this component because it is only this screen’s temporary interaction state.

The complete root component below is the small interactive checkpoint used by the later steps. It reads Fission theme tokens and owns only the temporary state needed for this example.

<!-- fission:file path="src/app.rs" -->
```rust
use fission::prelude::*;

fission_component! {
    pub TutorialPreview<()> {
        props {
            title: String,
            step: String,
            goal: String,
        }
        state {
            count: u32 = 0,
        }
    }
    view(preview, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
    } =>
    SemanticsRegion(
        identifier: Some("counter-screen".to_string()),
        label: Some(preview.title.clone()),
        child: Container(
            Column(gap: tokens.spacing.m, children: [
                Text(preview.title.clone())
                    .size(tokens.typography.heading2_size)
                    .weight(tokens.typography.font_weight_bold),
                Text(preview.step.clone()).color(tokens.colors.text_secondary),
                Text(format!("Count: {}", preview.count)),
                Text(if preview.count == 0 {
                    "No count yet. Choose Increase count to begin.".to_string()
                } else {
                    format!("The counter has increased {} time(s).", preview.count)
                }),
                Button(
                    child: Text("Increase count".to_string()),
                    key: "counter-increment",
                    on_press: reduce { preview.count += 1; },
                ),
                Button(
                    child: Text("Reset counter".to_string()),
                    key: "counter-reset",
                    on_press: reduce { preview.count = 0; },
                ),
                Text(preview.goal.clone()).color(tokens.colors.text_secondary),
            ])
        )
        .padding_all(tokens.spacing.l)
        .bg(tokens.colors.surface)
        .border(tokens.colors.border, 1.0)
        .border_radius(tokens.radii.large),
    )
}
```

```rust
    fn tutorial_goal() -> String;

    console_error_panic_hook::set_once();
    let preview = app::TutorialPreview::new(tutorial_title(), tutorial_step(), tutorial_goal());
    WebApp::<(), _>::new(preview)
        .with_title("Fission tutorial preview")
        .mount("#fission-web-mount")
        .run()
        .map_err(|error| JsValue::from_str(&error.to_string()))
}
```

## Implement the main iOS workflow

The counter belongs to this one screen, so its count is retained locally by `TutorialPreview` in the `fission_component!`. The Increase count reducer changes that local value; Reset counter restores the initial zero state. No app-wide state, database or host effect is needed for this small example.

## Handle errors, accessibility and target verification

Start from zero and confirm the screen explains how to begin. Increase the count several times, reset it, and make sure the displayed count follows each action. The first screen remains useful without interaction, and the visible button labels provide accessible names. Check the layout at a narrow phone width and a larger display so the count and both actions remain visible without horizontal scrolling.

Before publishing the screen, check it at a narrow phone width and a larger tablet or desktop width. Keep the primary action visible without horizontal scrolling, preserve readable focus order, and make status changes available to TalkBack or VoiceOver. For list screens, test an empty collection and give repeated stateful rows stable IDs based on durable record IDs.

### Run, test and build

```sh
cargo test
fission doctor ios --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
fission build --target ios --project-dir . --release
```

Expected result: `cargo test` runs the reducer and provider tests for the app; `fission doctor` reports the selected Xcode, simulator SDK and Rust targets; `fission run` launches an iOS Simulator; `fission test` checks the generated iOS host; and the release build completes for the simulator target. The current `fission run --target ios` path is simulator-only. It does not verify iPhone signing or physical hardware.
