## Create the project and add the target

Install the Fission command line, create the app, and add its native target.

```sh
cargo install cargo-fission
fission init ios-connect-to-bluetooth-devices-on-ios
cd ios-connect-to-bluetooth-devices-on-ios
fission add-target ios --project-dir .
fission add-capability bluetooth --project-dir .
```

## Files created by Fission

This is the starter tree after `fission init` and `fission add-target`; the component and state used for this task are additions in the steps below. Keep shared Rust behavior under `src/` and leave target launch and packaging in `platforms/ios/`.

```text
ios-connect-to-bluetooth-devices-on-ios/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── ios/                  # generated iOS host
```

Keep `src/app.rs`, shared state, reducers and reusable `fission_component!` components in the common Rust project. Add a state, service or effect module only when this feature needs that boundary, and use a name tied to the feature. The generated iOS host owns launch and packaging details; shared components describe the user task without importing iOS APIs.

## Connect the Bluetooth provider to the user action

This is the real Fission request path for this feature. Keep permission and hardware work outside the component view: the component dispatches one intent, the reducer queues the request, and success or error reducers store the returned result.

Start with task data and status in the app state. Keep a text-field draft, open flag or selected tab in the owning component instead of duplicating that temporary state here:

```rust
#[derive(Debug, Default)]
struct BluetoothState {
    // Add these fields to your existing app state.
    devices: Vec<BluetoothDevice>,
    bluetooth_error: Option<String>,
    scanning_bluetooth: bool,
}

impl GlobalState for BluetoothState {}
```

Handle successful and failed results separately so the screen can explain denied permission, cancellation, unsupported hardware and provider errors:

```rust
#[fission_reducer(BluetoothDevicesFound)]
fn on_bluetooth_devices_found(state: &mut BluetoothState, result: BluetoothScanResult) {
    state.scanning_bluetooth = false;
    state.devices = result.devices;
    state.bluetooth_error = None;
}

#[fission_reducer(BluetoothScanFailed)]
fn on_bluetooth_scan_failed(state: &mut BluetoothState, error: BluetoothError) {
    state.scanning_bluetooth = false;
    state.bluetooth_error = Some(error.message);
}
```

Queue the operation after the user presses the named control. The host completes asynchronously and dispatches the matching reducer:

```rust
state.scanning_bluetooth = true;
ctx.effects
    .bluetooth()
    .scan_devices(BluetoothScanRequest {
        service_uuids: vec!["0000180d-0000-1000-8000-00805f9b34fb".into()],
        timeout_ms: Some(10_000),
        include_paired: true,
        allow_duplicates: false,
    })
    .on_ok(ctx.effects.bind(
        BluetoothDevicesFound(BluetoothScanResult::default()),
        reduce_with!(on_bluetooth_devices_found),
    ))
    .on_err(ctx.effects.bind(
        BluetoothScanFailed(BluetoothError::default()),
        reduce_with!(on_bluetooth_scan_failed),
    ));
```

Bind the user action from a reusable Fission component. Keep the visible label in the same control so it works with touch, keyboard and assistive technology:

```rust
fission_component!
{
    pub ScanBluetoothDevicesButton<BluetoothState> {
    }
    view(component, _state, _cx) => rust {
        let (ctx, view) = fission::build::current::<BluetoothState>();
                let run = with_reducer!(ctx, ScanBluetoothDevices, on_scan_bluetooth_devices);

                Button::new("Scan devices")
                    .disabled(view.state().scanning_bluetooth)
                    .on_press(run)
                    .into()
    }
}
```

The [complete Bluetooth guide](/docs/capabilities/bluetooth/) explains configuration and expected platform behaviour. Test a successful memory-provider response and an unavailable or denied response before relying on the physical-device check below. The preview is read-only. The native target uses Fission’s provider to perform the request and report the result.

Keep platform-only code behind the generated target boundary or a typed provider; the shared component should describe the user task rather than call an operating-system API directly.

## Verify the native request on iOS

The website preview cannot exercise the native provider. Build and launch this target on a supported emulator or device, then use the feature action from the component above. Check the result the host actually returns, including denial, cancellation or unsupported hardware where those outcomes apply.

Repeat with the feature unavailable, denied or cancelled, as applicable. Confirm the screen preserves the user’s existing data and offers the right recovery step. Use a physical device when the behavior depends on real hardware or an operating-system prompt.

### Run, test and build

```sh
cargo test
fission doctor ios --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
fission build --target ios --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Xcode, simulator SDK or Rust targets, `fission run` launches an iOS Simulator, and `fission test` checks that the generated host can start. A release build checks the simulator package; it does not verify iPhone signing or physical-device behavior.


### Simulator and device commands

Fission’s run command discovers iOS simulators. Run these checks from the generated project root:

```sh
fission doctor ios --project-dir .
fission devices --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
```


To verify a hardware-dependent path on an iPhone, configure development signing and Developer Mode, create a signed release IPA, then install it through Xcode Devices and Simulators:

```sh
fission package --project-dir . --target ios --format ipa --release
```

`fission run --target ios` remains simulator-only; it does not launch directly on a physical iPhone. A simulator preview cannot prove NFC, camera, biometrics or other physical capability behaviour.
