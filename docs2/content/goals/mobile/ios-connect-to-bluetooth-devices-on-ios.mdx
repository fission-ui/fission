This tutorial shows how to configure privacy descriptions and entitlements where required; handle discovery, connect, disconnect and device limits. The runnable example uses shared Rust code and Fission’s fission_component! API, then checks the parts that need a real iOS target. It assumes basic Rust syntax and explains app state, reducers and host work before using them.

## What you will build

You will build this workflow: configure privacy descriptions and entitlements where required; handle discovery, connect, disconnect and device limits. The browser preview demonstrates the component and its state; it does not claim to run native permissions, sensors or device APIs. The final steps identify which checks need a real iOS target.


### The Fission pieces in this example

A component describes a part of the screen. fission_component! declares that component, its inputs and any retained local interaction state. GlobalState holds product data or routes used beyond one component. A typed action names something that happened; a reducer applies the state change synchronously. When an operation needs a file, database, network or operating-system API, the reducer queues an effect or capability request and a later action reports success or failure. This keeps slow work out of the UI rendering path.


## Create the project and add the target

Install the Fission command line, create the app, and add its native target. The [canonical iOS setup tutorial](/blog/set-up-rust-ios-development-with-fission/) covers SDK installation and device prerequisites.

```sh
cargo install cargo-fission
fission init ios-connect-to-bluetooth-devices-on-ios
cd ios-connect-to-bluetooth-devices-on-ios
fission add-target ios --project-dir .
fission add-capability bluetooth --project-dir .
```

`src/app.rs` is the shared Fission application, not a platform-specific copy. Put one reusable view in a named `fission_component!` component, keep app truth in `GlobalState`, and keep a one-screen draft or open flag in that component’s retained state. A reducer records the user’s intent; an effect, job, service or capability performs work after the view is built. Show pending, success, denied or failed outcomes in the screen.

The live preview compiles the complete `src/app.rs` component to WebAssembly. It lets you try retained state and normal or unavailable UI states in the browser. The preview does not call Android or iOS hardware. Use the target commands and device checks below to verify native behaviour.

## Implement the main iOS workflow

Treat the preview action as a user intent. In the real app, send a typed action to a reducer and let the reducer update `GlobalState` or request an asynchronous effect. Keep the view function limited to reading state and composing widgets. For **Configure privacy descriptions and entitlements where required; handle discovery, connect, disconnect and device limits**, work through these files in order:

1. In `src/state.rs`, define the product data and a status type with at least `Idle`, `Pending`, `Ready` and `Failed` variants. Keep durable records and active routes in `GlobalState`; keep only the current field draft or selected tab in local component state.
2. In `src/components/feature_screen.rs`, create a named `fission_component!` view. Give controls text labels, set a semantic label where an icon needs context, and make the primary action usable with keyboard, touch and an assistive technology action.
3. In `src/effects/feature.rs`, request slow or host-owned work after the reducer receives the action. Dispatch a typed success or error action when the effect completes. Do not block the UI thread, and attach a request id or revision when an older completion could overwrite a newer edit.
4. In `src/app.rs`, compose the screen with the state and reducer bindings. Render a pending message while work is running, the returned value on success, and a retry or alternate action on failure.


### Connect the Bluetooth provider to the user action

This is the real Fission request path for this feature. Keep permission and hardware work outside the component view: the component dispatches one intent, the reducer queues the request, and success or error reducers store the returned result.

Start with task data and status in the app state. Keep a text-field draft, open flag or selected tab in the owning component instead of duplicating that temporary state here:

```rust
#[derive(Default)]
struct BluetoothState {
    // Add these fields to your existing app state.
    devices: Vec<BluetoothDevice>,
    bluetooth_error: Option<String>,
    scanning_bluetooth: bool,
}

impl GlobalState for BluetoothState {}
```

Handle successful and failed results separately so the screen can explain denied permission, cancellation, unsupported hardware and provider errors:

```rust
#[fission_reducer(BluetoothDevicesFound)]
fn on_bluetooth_devices_found(state: &mut BluetoothState, result: BluetoothScanResult) {
    state.scanning_bluetooth = false;
    state.devices = result.devices;
    state.bluetooth_error = None;
}

#[fission_reducer(BluetoothScanFailed)]
fn on_bluetooth_scan_failed(state: &mut BluetoothState, error: BluetoothError) {
    state.scanning_bluetooth = false;
    state.bluetooth_error = Some(error.message);
}
```

Queue the operation after the user presses the named control. The host completes asynchronously and dispatches the matching reducer:

```rust
state.scanning_bluetooth = true;
ctx.effects
    .bluetooth()
    .scan_devices(BluetoothScanRequest {
        service_uuids: vec!["0000180d-0000-1000-8000-00805f9b34fb".into()],
        timeout_ms: Some(10_000),
        include_paired: true,
        allow_duplicates: false,
    })
    .on_ok(ctx.effects.bind(
        BluetoothDevicesFound(BluetoothScanResult::default()),
        reduce_with!(on_bluetooth_devices_found),
    ))
    .on_err(ctx.effects.bind(
        BluetoothScanFailed(BluetoothError::default()),
        reduce_with!(on_bluetooth_scan_failed),
    ));
```

Bind the user action from a reusable Fission component. Keep the visible label in the same control so it works with touch, keyboard and assistive technology:

```rust
fission_component!
{
    pub ScanBluetoothDevicesButton<BluetoothState> {
    }
    view(component, _state, _cx) => rust {
        let (ctx, view) = fission::build::current::<BluetoothState>();
                let run = with_reducer!(ctx, ScanBluetoothDevices, on_scan_bluetooth_devices);

                Button::new("Scan devices")
                    .disabled(view.state().scanning_bluetooth)
                    .on_press(run)
                    .into()
    }
}
```

The [complete Bluetooth guide](/docs/capabilities/bluetooth/) explains configuration and expected platform behaviour. Test a successful memory-provider response and an unavailable or denied response before relying on the physical-device check below. The browser preview exercises the component state only; it does not invoke this native provider.

Keep platform-only code behind the generated target boundary or a typed provider; the shared component should describe the user task rather than call an operating-system API directly.

## Handle errors, accessibility and target verification

Test the denied, unavailable or empty path as deliberately as the success path. In the browser preview, choose **Show an unavailable state** and confirm the message explains why the action cannot continue. In the native app, distinguish permission denial, cancellation, unsupported hardware and provider failure; offer a retry only when retrying can help.

Before publishing the screen, check it at a narrow phone width and a larger tablet or desktop width. Keep the primary action visible without horizontal scrolling, preserve readable focus order, and make status changes available to TalkBack or VoiceOver. For list screens, test an empty collection and give repeated stateful rows stable IDs based on durable record IDs.

### Run, test and build

```sh
cargo test
fission doctor ios --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
fission build --target ios --project-dir . --release
```

Expected result: `cargo test` runs the reducer and provider tests for the app; `fission doctor` reports the selected Xcode, simulator SDK and Rust targets; `fission run` launches an iOS Simulator; `fission test` checks the generated iOS host; and the release build completes for the simulator target. The current `fission run --target ios` path is simulator-only. It does not verify iPhone signing or physical hardware.


### Simulator and device commands

The [Xcode and iOS setup guide](/blog/set-up-rust-ios-development-with-fission/) is the single setup source. Fission’s run path discovers iOS simulators only:

```sh
fission doctor ios --project-dir .
fission devices --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
```


To verify a hardware-dependent path on an iPhone, configure development signing and Developer Mode, create a signed release IPA, then install it through Xcode Devices and Simulators:

```sh
fission package --project-dir . --target ios --format ipa --release
```

`fission run --target ios` remains simulator-only; it does not launch directly on a physical iPhone. A simulator preview cannot prove NFC, camera, biometrics or other physical capability behaviour.
