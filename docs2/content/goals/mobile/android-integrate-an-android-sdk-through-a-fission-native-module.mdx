An Android SDK has two different integration boundaries. Gradle must resolve and package its dependency, then application code needs a way to call it and receive a result. A successful build establishes the first boundary; it does not create the second one automatically.

Here, we add AndroidX ExifInterface and compile a small Java helper that reads an image's orientation metadata. This is a concrete build-input example, not a new Fission image API. Calling the helper from Rust, acquiring an allowed image stream and returning its result through an asynchronous effect remain separate runtime work.

The interactive screen records the build checks you performed. It does not display a fabricated photo, work order or SDK response.

## Create the Android project

Complete [Android SDK/NDK setup](/blog/set-up-rust-android-gui-development-with-fission/) and prepare [an emulator](/blog/create-and-launch-a-fission-android-emulator/) or [a phone](/blog/run-a-fission-app-on-a-physical-android-phone/) for the eventual installed app.

```sh
cargo install cargo-fission
fission init android-integrate-an-android-sdk-through-a-fission-native-module
cd android-integrate-an-android-sdk-through-a-fission-native-module
cargo add serde_yaml
fission add-target android --project-dir .
```

Keep the generated `src/main.rs`. The replacement shared library selects the review screen for native and Web targets rather than leaving the starter counter on Android.

## Declare a real dependency and a small Java boundary

This example adds one Android-only library to the tutorial app: `androidx.exifinterface:exifinterface:1.4.2`. The coordinate and Google Maven repository are documented in the [official AndroidX ExifInterface release instructions](https://developer.android.com/jetpack/androidx/releases/exifinterface). Pinning it here makes the example reviewable; it is not an instruction to use a dynamic “latest” version.

Append this module to the existing `fission.toml`. Do not replace the app's identity, targets or other configuration with this fragment.

```toml
[[native.modules]]
name = "photo-metadata"

[native.modules.android]
repositories = ["google()"]
gradle_dependencies = ["androidx.exifinterface:exifinterface:1.4.2"]
source_dirs = ["native/android/photo/src/main/java"]
```

Fission places the dependency in the generated Gradle build and adds the declared directory as Java source. Keep handwritten source outside `platforms/android/`, which is generated. The native-module declaration does not enable a Kotlin plugin, create a JNI bridge or grant access to a user's photos.

```java
package org.example.photo;

import androidx.exifinterface.media.ExifInterface;
import java.io.IOException;
import java.io.InputStream;

public final class PhotoOrientationReader {
    private PhotoOrientationReader() {}

    // The caller owns the stream and closes it. Call this off the UI thread.
    public static int readOrientation(InputStream image) throws IOException {
        ExifInterface metadata = new ExifInterface(image);
        return metadata.getAttributeInt(
                ExifInterface.TAG_ORIENTATION,
                ExifInterface.ORIENTATION_UNDEFINED);
    }
}
```
</TabItem>
</Tabs>

The helper accepts an already-open stream rather than inventing a path it may not be allowed to read. The caller owns its lifetime. The [ExifInterface API reference](https://developer.android.com/reference/androidx/exifinterface/media/ExifInterface) defines the constructor and orientation lookup; a missing orientation returns the explicit undefined value. Do not silently turn missing metadata into a claim that an image is correctly oriented.

Image parsing can perform I/O and fail. A later bridge must call it off the UI thread, propagate the error and return only the typed result needed by the app. Never pass a live component, `GlobalState` reference or reducer context into a background Java task.

## Check generated inputs and distinguish the remaining bridge

Build the real target, then inspect what Fission generated:

```sh
fission doctor android --project-dir .
fission build --target android --project-dir .
sed -n '1,160p' platforms/android/native-modules.gradle
sed -n '1,160p' platforms/android/settings.gradle.kts
fission run --target android --project-dir .
fission test --target android --project-dir .
```

The generated dependency block should name the pinned coordinate, and the Java source set should reference the declared project-relative source directory. A successful Android build compiles the helper against that SDK. Record the command and a non-sensitive summary in the review screen; do not paste private Maven credentials or customer image metadata.

To use the helper in the app, an Android-specific bridge still needs to accept an authorised image stream, invoke the SDK asynchronously, and map its success or failure into a typed Fission result. That bridge is not generated by `native.modules` and is not implemented in this build-wiring lesson. Keep shared UI and product state independent of the Java SDK.

The [native module guide](/docs/build-and-package/native-modules/) explains this boundary, and the [Android package guide](/docs/build-and-package/android-packages/) lists the target configuration. Do not interpret a packaged dependency as a completed end-to-end feature.
