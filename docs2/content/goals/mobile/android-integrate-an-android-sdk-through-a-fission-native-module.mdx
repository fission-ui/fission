## What you will build

In this tutorial, you will add a narrowly scoped Gradle or native dependency, expose a typed boundary and keep Android-only code out of shared UI logic. Try the interactive screen below in your browser. It changes local component state only; it does not open Android permission prompts, use device hardware or build an Android app. Follow the emulator checks below, then use a phone for hardware behavior.

### How the screen uses Fission

Throughout this guide, the screen is written as a `fission_component!`. That component owns its temporary interaction state and renders widgets from that state; a reducer changes it after a user action. Put durable facts shared across screens in `GlobalState`, and request native or service work through an effect or capability after the view is built.

## Create the project and add the target

Install the Fission command line, create the app, and add its native target. The [canonical Android setup tutorial](/blog/set-up-rust-android-gui-development-with-fission/) covers SDK installation and device prerequisites.

```sh
cargo install cargo-fission
fission init android-integrate-an-android-sdk-through-a-fission-native-module
cd android-integrate-an-android-sdk-through-a-fission-native-module
fission add-target android --project-dir .
```

## Files created by Fission

This is the starter tree after `fission init` and `fission add-target`; the component and state used for this task are additions in the steps below. Keep shared Rust behavior under `src/` and leave target launch and packaging in `platforms/android/`.

```text
android-integrate-an-android-sdk-through-a-fission-native-module/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── android/              # generated Android host
```

Keep `src/app.rs`, shared state, reducers and reusable `fission_component!` components in the common Rust project. Add a state, service or effect module only when this feature needs that boundary, and use a name tied to the feature. The generated Android host owns launch and packaging details; shared components describe the user task without importing Android APIs.

## Try the browser-safe interaction

The preview is a compiled Fission component with two deliberately local simulations. Press **Simulate success** to inspect the normal result, then **Simulate unavailable** to see how the screen can explain that a capability cannot proceed. These actions change only preview state: they do not request permission, access a sensor or run the target app. In the main step, compare that state boundary with the feature-specific instructions.

<!-- fission:file path="src/app.rs" -->
```rust
use fission::prelude::*;

fission_component! {
    pub TutorialPreview<()> {
        props {
            title: String,
            step: String,
            goal: String,
        }
        state {
            simulated_success: bool = false,
            simulated_unavailable: bool = false,
        }
    }
    view(preview, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
    } =>
    SemanticsRegion(
        identifier: Some("tutorial-preview".to_string()),
        label: Some(preview.title.clone()),
        child: Container(
            Column(gap: tokens.spacing.m, children: [
                Text(preview.title.clone())
                    .size(tokens.typography.heading2_size)
                    .weight(tokens.typography.font_weight_bold),
                Text(preview.step.clone())
                    .color(tokens.colors.text_secondary),
                Text(preview.goal.clone()),
                Button(
                    child: Text(if preview.simulated_success {
                        "Reset success simulation".to_string()
                    } else {
                        "Simulate success".to_string()
                    }),
                    key: "tutorial-complete",
                    on_press: reduce {
                        preview.simulated_success = !preview.simulated_success;
                        if preview.simulated_success { preview.simulated_unavailable = false; }
                    },
                ),
                Text(if preview.simulated_success {
                    format!("Simulated success for {}. Only browser-local state changed. Use the target steps below to verify the real behaviour.", preview.goal)
                } else {
                    "Ready: no native request has run. Choose a simulation to see how the screen state changes.".to_string()
                }),
                Button(
                    child: Text(if preview.simulated_unavailable {
                        "Clear unavailable simulation".to_string()
                    } else {
                        "Simulate unavailable".to_string()
                    }),
                    key: "tutorial-unavailable",
                    on_press: reduce {
                        preview.simulated_unavailable = !preview.simulated_unavailable;
                        if preview.simulated_unavailable { preview.simulated_success = false; }
                    },
                ),
                if preview.simulated_unavailable {
                    Text(format!("Simulated unavailable result for {}. No native request ran; the target app should explain the real reason and recovery action.", preview.title))
                } else {
                    Text("No unavailable response is being simulated.".to_string())
                },
            ])
        )
        .padding_all(tokens.spacing.l)
        .bg(tokens.colors.surface)
        .border(tokens.colors.border, 1.0)
        .border_radius(tokens.radii.large),
    )
}
```

mod app;

use fission::prelude::*;
use wasm_bindgen::prelude::*;

#[wasm_bindgen(inline_js = "export function tutorial_title() { const parts = document.title.split(' — '); return parts.slice(1).join(' — ') || 'Fission tutorial'; } export function tutorial_step() { return document.title.split(' — ')[0] || 'Tutorial step'; } export function tutorial_goal() { return document.querySelector('meta[name=\"tutorial-goal\"]')?.content || 'Complete the task and verify it on the target.'; }")]
extern "C" {
    fn tutorial_title() -> String;
    fn tutorial_step() -> String;
    fn tutorial_goal() -> String;
}

#[wasm_bindgen(start)]
pub fn run() -> Result<(), JsValue> {
    console_error_panic_hook::set_once();
    let preview = app::TutorialPreview::new(tutorial_title(), tutorial_step(), tutorial_goal());
    WebApp::<(), _>::new(preview)
        .with_title("Fission tutorial preview")
        .mount("#fission-web-mount")
        .run()
        .map_err(|error| JsValue::from_str(&error.to_string()))
}

## Integrate an Android SDK through a Fission native module

Use a native module when an Android SDK needs a Gradle dependency, repository, manifest entry or Java/Kotlin source directory. Fission includes those inputs in the generated Android build, but it does not make SDK methods callable from Rust automatically. First check the vendor's Android install guide and the generated `platforms/android/README.md`; then add the SDK to `fission.toml`:

```toml
[[native.modules]]
name = "scanner-sdk"
path = "platforms/android/scanner"

[native.modules.android]
repositories = ["https://maven.vendor.example/releases"]
gradle_dependencies = ["com.vendor:scanner-sdk:1.2.3"]
source_dirs = ["platforms/android/scanner/src/main/java"]
```

The repository, package coordinate and paths above are examples. Replace them with the values published by the SDK vendor; `source_dirs` is relative to the project root. Keep the UI and product rules in shared Rust. If the SDK must return data to the Rust app, expose it through a typed host capability and request it from a reducer, so Web and desktop targets can still render the same state and error handling. The [native module guide](/docs/build-and-package/native-modules/) explains the build boundary, and the [Android package guide](/docs/build-and-package/android-packages/) lists Android-specific configuration.

## Confirm the native module is included in the Android build

A successful Rust build does not prove the platform SDK was linked. Run the target build below and inspect its first native build output for the module name and dependency. Then launch the generated app on the target and exercise both a successful SDK result and the SDK’s documented error or cancellation path.

If Rust needs the SDK result, verify that the host returns it through the typed capability and that the reducer updates the visible state. A package declaration alone does not create that bridge.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Android tools, `fission run` launches the selected emulator or connected device, and `fission test` checks that the generated host can start. A release build checks packaging, but none of these commands proves a physical permission or hardware flow works.
