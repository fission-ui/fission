**Status: blocked — this is not a completed iOS passkey sign-in flow.** The current iOS shell uses `UnsupportedPasskeyHost`, not an AuthenticationServices provider. The application also needs a real server challenge and assertion-verification endpoint before it can authenticate anyone.

A passkey assertion is not a session. The host gathers credential data; the relying-party server verifies it and decides whether access is allowed. The diagnostic below checks actual host support without generating a challenge locally, fabricating an assertion or displaying a successful sign-in.

## Create a diagnostic project, not a simulated feature

Complete [iOS setup](/blog/set-up-rust-ios-development-with-fission/) first. These commands declare the capability and generate platform inputs; they do not remove the native provider gap.

```sh
cargo install cargo-fission
fission init ios-add-passkey-sign-in-to-an-ios-app
cd ios-add-passkey-sign-in-to-an-ios-app
fission add-target ios --project-dir .
fission add-capability passkeys --project-dir .
cargo add serde_yaml
```

use fission::prelude::*;

#[derive(Clone, Debug, PartialEq, Eq)]
pub struct PasskeyDiagnosticState {
    pub locale: Locale,
    pub pending: bool,
    pub message_key: String,
    pub diagnostic: Option<String>,
}
impl Default for PasskeyDiagnosticState {
    fn default() -> Self {
        Self {
            locale: Locale::from("en-US"),
            pending: false,
            message_key: "check.ready".into(),
            diagnostic: None,
        }
    }
}
impl GlobalState for PasskeyDiagnosticState {}

pub fn check_host(
    state: &mut PasskeyDiagnosticState,
    cx: &mut ReducerContext<PasskeyDiagnosticState>,
) {
    if state.pending {
        return;
    }
    state.pending = true;
    state.message_key = "check.pending".into();
    state.diagnostic = None;
    let ok = cx.effects.bind(HostChecked, reduce_with!(host_checked));
    let err = cx
        .effects
        .bind(HostCheckFailed, reduce_with!(host_check_failed));
    cx.effects.passkeys().availability().on_ok(ok).on_err(err);
}

#[fission_reducer(HostChecked)]
fn host_checked(
    state: &mut PasskeyDiagnosticState,
    cx: &mut ReducerContext<PasskeyDiagnosticState>,
) {
    state.pending = false;
    match cx.input.capability_ok(GET_PASSKEY_AVAILABILITY) {
        Some(value) => {
            state.message_key = if value.supported && value.secure_context {
                "check.available"
            } else {
                "check.unavailable"
            }
            .into();
            state.diagnostic = Some(format!("{value:?}"));
        }
        None => state.message_key = "check.invalid".into(),
    }
}

#[fission_reducer(HostCheckFailed)]
fn host_check_failed(
    state: &mut PasskeyDiagnosticState,
    cx: &mut ReducerContext<PasskeyDiagnosticState>,
) {
    state.pending = false;
    match cx.input.capability_error(GET_PASSKEY_AVAILABILITY) {
        Some(error) => {
            state.message_key = if error.code == "unsupported" {
                "check.unavailable"
            } else {
                "check.failed"
            }
            .into();
            state.diagnostic = Some(format!("{}: {}", error.code, error.message));
        }
        None => state.message_key = "check.invalid".into(),
    }
}

use fission::i18n::{Locale, TranslationBundle};
use fission::prelude::*;
use std::collections::HashMap;

pub fn create_env() -> Env {
    let mut env = Env::default();
    env.locale = Locale::from("en-US");
    for (locale, source) in [
        ("en-US", include_str!("../i18n/en-US.yaml")),
        ("es-ES", include_str!("../i18n/es-ES.yaml")),
    ] {
        let messages: HashMap<String, String> =
            serde_yaml::from_str(source).expect("valid task translations");
        env.i18n.add_bundle(TranslationBundle {
            locale: Locale::from(locale),
            messages,
        });
    }
    env
}

pub fn sync_env(state: &crate::app::PasskeyDiagnosticState, env: &mut Env) {
    env.locale = state.locale.clone();
}

## Keep the missing integration visible

The availability query can succeed and still report `supported: false`. That is the normal iOS provider's current result. A secure browser may report support, but this does not implement the missing native adapter or your server's authentication policy.

For a real deployment, choose a relying-party domain which the service owns. Configure the signed app's Associated Domains with `webcredentials:<your-domain>` and serve the corresponding `apple-app-site-association` document from that domain. Do not copy a demonstration domain into a production identity configuration. These platform associations and a genuine AuthenticationServices adapter are separate prerequisites.

The server must issue a fresh, expiring challenge and verify the returned assertion against the expected challenge, relying-party identity, origin/application association, credential and account policy before creating a session. Reuse a maintained WebAuthn implementation for that work. Cancellation leaves the user signed out; an availability result or credential response alone never unlocks protected content.

This page deliberately stops before those missing contracts. The native sign-in goal remains blocked rather than being renamed to a simulated success.

A completed version must demonstrate the real server challenge/verification round trip and native credential prompt on a signed iPhone build. Test cancellation, no matching credential, expired or replayed challenge, verification failure and returning to the intended protected route only after a verified session exists. Do not publish a test provider as an authentication fallback.
