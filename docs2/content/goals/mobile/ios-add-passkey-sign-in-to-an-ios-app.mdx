## Create the project and add the target

Create a shared Rust app and add the iOS target. Fission generates the native host; keep the app behaviour in Rust.

```sh
cargo install cargo-fission
fission init ios-add-passkey-sign-in-to-an-ios-app
cd ios-add-passkey-sign-in-to-an-ios-app
fission add-target ios --project-dir .
fission add-capability passkeys --project-dir .
```

## Files created by Fission

Fission creates this starter tree. Shared Rust code stays in `src/`; the generated host under `platforms/ios/` handles iOS launch and packaging.

```text
ios-add-passkey-sign-in-to-an-ios-app/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── ios/                  # generated iOS host
```

Keep app behaviour in shared Rust. Add a feature module only when it creates a useful boundary, and keep iOS APIs behind the generated host.

One limitation matters before we write the screen: `fission add-capability passkeys` records the capability, but Fission’s generated iOS shell currently uses an unsupported passkey host. The Web preview below exercises the Rust reducer flow with synthetic data; it does not display an iOS credential prompt. A native `PasskeyHost` adapter is still product-owned work. The domain setup here is required for a real iOS provider, but it does not create that adapter.

## Associate the app with its relying-party domain

Choose a domain you control and use the same relying-party ID in the app, the signed app entitlement, and the website association file. The examples use placeholders: replace the domain, App ID prefix, and bundle ID with the values from your Apple Developer account.

Add this entry to the signed app’s Associated Domains entitlement:

```text
webcredentials:members.example.com
```

The domain must serve an `apple-app-site-association` JSON file at `/.well-known/apple-app-site-association`. For a passkey-only relationship, its `webcredentials.apps` value must contain the app’s application identifier (`<App ID prefix>.<bundle ID>`):

```json
{
  "webcredentials": {
    "apps": [
      "REPLACE_WITH_APP_ID_PREFIX.com.example.cedarridge"
    ]
  }
}
```

For a Fission IPA, point `[package.ios].entitlements` in `fission.toml` at the plist containing the Associated Domains entitlement. The `passkeys` capability does not generate this product-specific domain or entitlement. Apple’s [passkey guide](https://developer.apple.com/documentation/authenticationservices/supporting-passkeys) and [associated-domain setup](https://developer.apple.com/documentation/xcode/supporting-associated-domains) describe the platform requirements. The `example.com` values in this tutorial are placeholders, not a domain you can use to test your app.

## Run the Passkey operation through Fission

Keep host work out of component conversion. The button dispatches a typed action, its reducer queues the capability request, and separate completion reducers update the screen. The Web preview installs `MemoryPasskeyHost` and sends the same operation through Fission’s typed capability path. Its deterministic response is not a claim about device hardware, OS permission or native platform support.

The preview's MemoryPasskeyHost returns synthetic assertion data. The app refuses to open the passkey prompt until it has a challenge; the preview injects deterministic bytes only to exercise the UI. A real sign-in attempt fetches a fresh challenge from the relying-party server, consumes it for one passkey request, and sends the returned assertion back for verification. Keep the assertion in memory only; do not persist or log it, and do not treat it as a signed-in session. A retry needs a new challenge from the server.

```rust
use fission::prelude::*;

#[derive(Debug)]
pub enum SignInError {
    ChallengeMissing,
    MissingAssertion,
    Host(String),
    HostWithoutDetails,
}

#[derive(Debug, Default)]
pub struct PasskeySignInState {
    pub pending: bool,
    /// Fresh challenge supplied by the relying-party server for this attempt.
    pub challenge: Option<Vec<u8>>,
    /// Keep the response only long enough to send it to the server for verification.
    pub assertion: Option<PasskeyAuthenticationResult>,
    pub error: Option<SignInError>,
}

impl GlobalState for PasskeySignInState {}

#[fission_reducer(RunCapability)]
pub fn run_capability(state: &mut PasskeySignInState, ctx: &mut ReducerContext<PasskeySignInState>) {
    if state.pending || state.assertion.is_some() {
        return;
    }

    state.error = None;
    let Some(challenge) = state.challenge.take() else {
        state.error = Some(SignInError::ChallengeMissing);
        return;
    };
    state.pending = true;
    state.assertion = None;

    let ok: ActionEnvelope = CapabilitySucceeded.into();
    let err: ActionEnvelope = CapabilityFailed.into();

    ctx.effects
        .passkeys().authenticate(PasskeyAuthenticationRequest {
            // Replace this with the same domain configured in the entitlement.
            relying_party_id: "members.example.com".into(),
            challenge,
            allow_credentials: Vec::new(),
            user_verification: PasskeyUserVerification::Preferred,
            mediation: PasskeyMediation::Required,
            timeout_ms: Some(60_000),
        })
        .on_ok(ok)
        .on_err(err);
}

#[fission_reducer(CapabilitySucceeded)]
pub fn capability_succeeded(
    state: &mut PasskeySignInState,
    ctx: &mut ReducerContext<PasskeySignInState>,
) {
    state.pending = false;
    if let Some(assertion) = ctx.input.capability_ok(AUTHENTICATE_PASSKEY) {
        state.assertion = Some(assertion);
        state.error = None;
    } else {
        state.assertion = None;
        state.error = Some(SignInError::MissingAssertion);
    }
}

#[fission_reducer(CapabilityFailed)]
pub fn capability_failed(
    state: &mut PasskeySignInState,
    ctx: &mut ReducerContext<PasskeySignInState>,
) {
    state.pending = false;
    state.assertion = None;
    let code = ctx
        .input
        .capability_error(AUTHENTICATE_PASSKEY)
        .map(|error| error.code);
    state.error = Some(code.map(SignInError::Host).unwrap_or(SignInError::HostWithoutDetails));
}

pub fn callback_registry() -> ActionRegistry<PasskeySignInState> {
    let mut registry = ActionRegistry::new();
    registry.register(reduce_with!(capability_succeeded));
    registry.register(reduce_with!(capability_failed));
    registry
}

fission_component! {
    pub PasskeySignInScreen<PasskeySignInState> {}
    view(_screen, state, cx) {
        let tokens = &cx.view.env().theme.tokens;
        let action = with_reducer!(cx.build, RunCapability, run_capability);
        let status = if state.pending {
            cx.tr("auth.waiting")
        } else if let Some(error) = &state.error {
            match error {
                SignInError::ChallengeMissing => cx.tr("auth.challenge_missing"),
                SignInError::MissingAssertion => cx.tr("auth.missing"),
                SignInError::Host(code) => cx.tr(match code.as_str() {
                    "cancelled" | "canceled" | "user_cancel" | "not_allowed" => "auth.error.cancelled",
                    "unsupported" | "unavailable" => "auth.error.unavailable",
                    "security_error" => "auth.error.domain",
                    _ => "auth.error.generic",
                }),
                SignInError::HostWithoutDetails => cx.tr("auth.error_unknown"),
            }
        } else if state.assertion.is_some() {
            cx.tr("auth.assertion")
        } else if state.challenge.is_none() {
            cx.tr("auth.challenge_missing")
        } else {
            cx.tr("auth.ready")
        };
    } =>
    SemanticsRegion(
        identifier: Some("account-passkey-sign-in".to_string()),
        label: Some(cx.tr("auth.title")),
        child: Container(
            Column(gap: tokens.spacing.m, children: [
                Text(cx.tr("auth.account"))
                    .weight(tokens.typography.font_weight_bold),
                Text(cx.tr("auth.title"))
                    .size(tokens.typography.heading2_size),
                Text(cx.tr("auth.identity"))
                    .color(tokens.colors.text_secondary),
                Text(cx.tr("auth.context")),
                Button(
                    child: Text(cx.tr("auth.action")),
                    key: "run-capability",
                    variant: ButtonVariant::Primary,
                    disabled: state.pending || state.challenge.is_none() || state.assertion.is_some(),
                    loading: state.pending,
                    on_press: action,
                ),
                Container(Text(status))
                    .padding_all(tokens.spacing.m)
                    .bg(tokens.colors.background)
                    .border(tokens.colors.border, 1.0)
                    .border_radius(tokens.radii.medium),
            ])
        )
        .padding_all(tokens.spacing.l)
        .bg(tokens.colors.surface)
        .border(tokens.colors.border, 1.0)
        .border_radius(tokens.radii.large),
    )
}
```

## Check the iOS build and provider boundary

The website preview cannot exercise an iOS provider, and the generated Fission iOS shell currently reports passkeys as unsupported. Build the target to verify the shared Rust app and generated iOS bundle, but do not expect the passkey button to open a native prompt until your app supplies a `PasskeyHost` adapter and signs the app with the matching Associated Domains entitlement.

After that adapter and signing configuration are in place, test with no matching credential and with the user cancelling the prompt. Confirm the screen remains signed out and offers another sign-in path. Use a physical device when the behavior depends on native passkey support or an operating-system prompt.

### Run, test and build

```sh
cargo test
fission doctor ios --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
fission build --target ios --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Xcode, simulator SDK or Rust targets, `fission run` launches an iOS Simulator, and `fission test` checks that the generated host can start. A release build checks the simulator package; it does not verify iPhone signing or physical-device behavior.


### Simulator and device commands

Fission’s run command discovers iOS simulators. Run these checks from the generated project root:

```sh
fission doctor ios --project-dir .
fission devices --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
```


To verify a hardware-dependent path on an iPhone, configure development signing and Developer Mode, create a signed release IPA, then install it through Xcode Devices and Simulators:

```sh
fission package --project-dir . --target ios --format ipa --release
```

`fission run --target ios` remains simulator-only; it does not launch directly on a physical iPhone. A simulator preview cannot prove NFC, camera, biometrics or other physical capability behaviour.
