## What you will build

In this tutorial, you will filter, insert and reorder records without transferring retained widget state to another row. Try the interactive screen below in your browser. It changes local component state only; it does not open iOS permission prompts, use device hardware or build an iPhone app. Follow the Simulator checks below, then use a signed iPhone build for hardware behavior.

### How the screen uses Fission

Throughout this guide, the screen is written as a `fission_component!`. That component owns its temporary interaction state and renders widgets from that state; a reducer changes it after a user action. Put durable facts shared across screens in `GlobalState`, and request native or service work through an effect or capability after the view is built.

## Create the project and add the target

Install the Fission command line, create the app, and add its native target. The [canonical iOS setup tutorial](/blog/set-up-rust-ios-development-with-fission/) covers SDK installation and device prerequisites.

```sh
cargo install cargo-fission
fission init ios-give-repeated-ios-list-rows-stable-identity
cd ios-give-repeated-ios-list-rows-stable-identity
fission add-target ios --project-dir .
```

## Files created by Fission

This is the starter tree after `fission init` and `fission add-target`; the component and state used for this task are additions in the steps below. Keep shared Rust behavior under `src/` and leave target launch and packaging in `platforms/ios/`.

```text
ios-give-repeated-ios-list-rows-stable-identity/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── ios/                  # generated iOS host
```

Keep `src/app.rs`, shared state, reducers and reusable `fission_component!` components in the common Rust project. Add a state, service or effect module only when this feature needs that boundary, and use a name tied to the feature. The generated iOS host owns launch and packaging details; shared components describe the user task without importing iOS APIs.

use fission::prelude::*;

fission_component! {
    pub IosListIdentity<()> {
        props {
            title: String,
            step: String,
            goal: String,
        }
        state {
            simulated_success: bool = false,
            simulated_unavailable: bool = false,
        }
    }
    view(preview, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
    } =>
    SemanticsRegion(
        identifier: Some("tutorial-preview".to_string()),
        label: Some(preview.title.clone()),
        child: Container(
            Column(gap: tokens.spacing.m, children: [
                Text(preview.title.clone())

                    .weight(tokens.typography.font_weight_bold),
                Text(preview.step.clone())
                    .color(tokens.colors.text_secondary),
                Text(preview.goal.clone()),
                Button(
                    child: Text(if preview.simulated_success {
                        "Reset success simulation".to_string()
                    } else {
                        "Simulate success".to_string()
                    }),
                    key: "tutorial-complete",
                    on_press: reduce {
                        preview.simulated_success = !preview.simulated_success;
                        if preview.simulated_success { preview.simulated_unavailable = false; }
                    },
                ),
                Text(if preview.simulated_success {
                    format!("Simulated success for {}. Only browser-local state changed. Use the target steps below to verify the real behaviour.", preview.goal)
                } else {
                    "Ready: no native request has run. Choose a simulation to see how the screen state changes.".to_string()
                }),
                Button(
                    child: Text(if preview.simulated_unavailable {
                        "Clear unavailable simulation".to_string()
                    } else {
                        "Simulate unavailable".to_string()
                    }),
                    key: "tutorial-unavailable",
                    on_press: reduce {
                        preview.simulated_unavailable = !preview.simulated_unavailable;
                        if preview.simulated_unavailable { preview.simulated_success = false; }
                    },
                ),
                if preview.simulated_unavailable {
                    Text(format!("Simulated unavailable result for {}. No native request ran; the target app should explain the real reason and recovery action.", preview.title))
                } else {
                    Text("No unavailable response is being simulated.".to_string())
                },
            ])
        )
        .padding_all(tokens.spacing.l)
        .bg(tokens.colors.surface)
        .border(tokens.colors.border, 1.0)
        .border_radius(tokens.radii.large),
    )
}

## Give repeated iOS list rows stable identity

Give each retained row an ID derived from the record, for example .id(WidgetId::explicit(format!("record.{}", record.id))). Never derive identity from the row index: filtering or sorting changes indices and can move a retained disclosure, selection or draft into another record. Keep the row's short-lived control state in its component and the actual record in GlobalState. Test by changing one row, filtering it out, inserting a record, sorting, then restoring the original list; the same record should keep its state throughout.

The component below is a browser-safe version of this screen. It uses Fission's retained component state and widgets to make the task visible; it does not call a native provider or operating-system API.

<!-- fission:file path="src/app.rs" -->
```rust
use fission::prelude::*;

fission_component! {
    #[derive(Default)]
    pub TaskRow<()> {
        props {
            task_id: String,
            label: String,
        }
        state {
            complete: bool = false,
        }
    }
    view(row, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
    } =>
    Row(gap: tokens.spacing.m, children: [
        Text(row.label.clone()),
        Button(
            child: Text(if row.complete { "Reopen" } else { "Complete" }),
            key: format!("task-{}", row.task_id),
            handler: "toggle",
            on_press: reduce { row.complete = !row.complete; },
        ),
    ])
}

fission_component! {
    pub IosRepeatedListRowsStable<()> {
        props {
            title: String,
            step: String,
            goal: String,
        }
    }
    view(preview, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
    } =>
    SemanticsRegion(
        identifier: Some("stable-list-example".to_string()),
        label: Some(preview.title.clone()),
        child: Container(
            Column(gap: tokens.spacing.m, children: [
                Text(preview.title.clone())

                    .weight(tokens.typography.font_weight_bold),
                Text(preview.goal.clone()),
                for (task_id, label) in [("draft-17", "Write release notes"), ("task-42", "Review the pull request")] {
                    TaskRow(key: task_id, task_id: task_id.to_string(), label: label.to_string())
                },
                Text("Complete either row. If the parent later filters or reorders the records, each retained completion flag still belongs to its explicit task id."),
            ])
        )
        .padding_all(tokens.spacing.l)
        .bg(tokens.colors.surface)
        .border(tokens.colors.border, 1.0)
        .border_radius(tokens.radii.large),
    )
}
```

## Verify the user task on iOS

On an iOS simulator, repeat the feature path described above and check the expected result. If this task has an unavailable, denied or failure path, run that path too and confirm the screen offers a way to continue. The browser preview demonstrates component state only; the commands below verify the native host.

Use LiveTest with the semantic identifiers shown in the component to confirm focus and action behavior. If this screen adapts to window size, repeat the flow at a narrow phone width and a wider display.

### Run, test and build

```sh
cargo test
fission doctor ios --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
fission build --target ios --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Xcode, simulator SDK or Rust targets, `fission run` launches an iOS Simulator, and `fission test` checks that the generated host can start. A release build checks the simulator package; it does not verify iPhone signing or physical-device behavior.


### Simulator and device commands

The [Xcode and iOS setup guide](/blog/set-up-rust-ios-development-with-fission/) is the single setup source. Fission’s run path discovers iOS simulators only:
