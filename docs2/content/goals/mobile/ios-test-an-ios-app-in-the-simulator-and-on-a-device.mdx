## Create the project and add the target

Create the project and add the target used by this guide. Fission generates the native host; the app and its behaviour stay in shared Rust code.

```sh
cargo install cargo-fission
fission init ios-test-an-ios-app-in-the-simulator-and-on-a-device
cd ios-test-an-ios-app-in-the-simulator-and-on-a-device
fission add-target ios --project-dir .
```

## Files created by Fission

This is the starter tree Fission generates. Keep shared app code in `src/`; the generated platform files handle native launch and packaging.

```text
ios-test-an-ios-app-in-the-simulator-and-on-a-device/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── ios/                  # generated iOS host
```

Keep app state, reducers and components in shared Rust. Put direct iOS API calls in the generated host or a typed provider, and split a feature into modules when that boundary helps.

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum TestLayer {
    Reducers,
    Host,
    Journey,
    Device,

fission_component! {
    pub IosTestPlan<()> {
        state {
            selected_layer: TestLayer = TestLayer::Reducers,
        }
    }
    view(plan, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
        let (selected_title, selected_detail) = match plan.selected_layer {
            TestLayer::Reducers => (
                cx.tr("tests.layer.reducers"),
                cx.tr("tests.detail.reducers"),

            TestLayer::Host => (
                cx.tr("tests.layer.host"),
                cx.tr("tests.detail.host"),
            ),

                cx.tr("tests.layer.journey"),
                cx.tr("tests.detail.journey"),
            ),
            TestLayer::Device => (
                cx.tr("tests.layer.device"),
                cx.tr("tests.detail.device"),
            ),
        };
    } =>

fn load_bundle(locale: &str, source: &str) -> TranslationBundle {
    TranslationBundle {
        locale: Locale::from(locale),
        messages: serde_yaml::from_str(source).expect("valid tutorial translations"),
    }

fn preview_env() -> Env {
    let mut env = Env::default();
    env.locale = Locale::from("en-US");

    env.i18n
        .add_bundle(load_bundle("es-ES", include_str!("i18n/es-ES.yaml")));
    env
}

#[wasm_bindgen(start)]
pub fn run() -> Result<(), JsValue> {
    console_error_panic_hook::set_once();
    WebApp::<(), _>::new(app::IosTestPlan)
        .with_env(preview_env())
        .with_title("Northstar Field Notes")
        .mount("#fission-web-mount")
        .run()
        .map_err(|error| JsValue::from_str(&error.to_string()))
}

## Test an iOS app in the simulator and on a device

Use three different checks for three different risks: cargo test for Rust reducers and state rules, fission test --target ios for the generated host smoke path, and a focused LiveTest against the running shell for a user journey. Then use a physical device only for behaviour that depends on the real sensor, permission prompt, radio or signed install. Keep the tested scenario and target version in the result; a passing smoke test must not be reported as proof that hardware behaviour works.

## Run the test layers for this task

Use a different check for each risk: `cargo test` for Rust rules you have written, `fission test` for the generated host smoke path, and LiveTest for the composed screen and user journey. A passing test at one layer does not replace the checks at the next layer.

Run the same critical journey on Android Emulator and iOS Simulator. Add a real-device check only for behavior the simulator cannot prove, such as a permission sheet, radio, camera, sensor or signed installation.

### Run, test and build

```sh
cargo test
fission doctor ios --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
fission build --target ios --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Xcode, simulator SDK or Rust targets, `fission run` launches an iOS Simulator, and `fission test` checks that the generated host can start. A release build checks the simulator package; it does not verify iPhone signing or physical-device behavior.


### Simulator and device commands

Fission’s run command discovers iOS simulators. Run these checks from the generated project root:

```sh
fission doctor ios --project-dir .
fission devices --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
```


To verify a hardware-dependent path on an iPhone, configure development signing and Developer Mode, create a signed release IPA, then install it through Xcode Devices and Simulators:

```sh
fission package --project-dir . --target ios --format ipa --release
```

`fission run --target ios` remains simulator-only; it does not launch directly on a physical iPhone. A simulator preview cannot prove NFC, camera, biometrics or other physical capability behaviour.
