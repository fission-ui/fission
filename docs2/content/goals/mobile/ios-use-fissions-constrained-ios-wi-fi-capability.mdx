## Create the project and add the target

Create the project and add the target used by this guide. Fission generates the native host; the app and its behaviour stay in shared Rust code.

```sh
cargo install cargo-fission
fission init ios-use-fissions-constrained-ios-wi-fi-capability
cd ios-use-fissions-constrained-ios-wi-fi-capability
fission add-target ios --project-dir .
fission add-capability wifi --project-dir .
```

## Files created by Fission

This is the starter tree Fission generates. Keep shared app code in `src/`; the generated platform files handle native launch and packaging.

```text
ios-use-fissions-constrained-ios-wi-fi-capability/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── ios/                  # generated iOS host
```

Keep app state, reducers and components in shared Rust. Put direct iOS API calls in the generated host or a typed provider, and split a feature into modules when that boundary helps.

## See where the browser stops

The browser preview does not call a Wi-Fi provider. Fission’s built-in iOS host reports Wi-Fi as disabled with no connected network; permission, scan and connection requests return typed unsupported errors. This guide shows how to handle that result and direct users to configure Wi-Fi in iOS Settings.

## Connect the Wifi provider to the user action

Keep Wi-Fi requests out of component conversion. Dispatch an action from the screen; a reducer queues the provider request, and completion reducers update state from its actual result.

Keep scan results and status in app state. Keep temporary UI choices, such as open flags or selected tabs, local to their component:

```rust
#[derive(Debug, Default)]
struct WifiState {
    // Add these fields to your existing app state.
    networks: Vec<WifiNetwork>,
    wifi_error: Option<String>,
    scanning_wifi: bool,
}

impl GlobalState for WifiState {}
```

Use separate success and error paths so an unsupported request is not mistaken for a successful empty scan. The success path applies only when the app uses a provider that supports scanning; the built-in iOS host takes the error path:

```rust
#[fission_reducer(WifiNetworksFound)]
fn on_wifi_networks_found(state: &mut WifiState, result: WifiScanResult) {
    state.scanning_wifi = false;
    state.networks = result.networks;
    state.wifi_error = None;
}

#[fission_reducer(WifiScanFailed)]
fn on_wifi_scan_failed(state: &mut WifiState, error: WifiError) {
    state.scanning_wifi = false;
    state.wifi_error = Some(error.message);
}
```

The reducer requests a scan through Fission’s Wi-Fi provider. On iOS, the built-in host returns a typed unsupported error, which dispatches `WifiScanFailed`:

```rust
state.scanning_wifi = true;
ctx.effects
    .wifi()
    .scan_networks(WifiScanRequest {
        ssid_prefix: Some("Device-".into()),
        include_hidden: false,
        timeout_ms: Some(8_000),
    })
    .on_ok(ctx.effects.bind(
        WifiNetworksFound(WifiScanResult::default()),
        reduce_with!(on_wifi_networks_found),
    ))
    .on_err(ctx.effects.bind(
        WifiScanFailed(WifiError::default()),
        reduce_with!(on_wifi_scan_failed),
    ));
```

Keep the action, visible label and disabled state together in the button so touch, keyboard and assistive-technology users get the same control:

```rust
fission_component!
{
    pub ScanWifiNetworksButton<WifiState> {
    }
    view(component, _state, _cx) => rust {
        let (ctx, view) = fission::build::current::<WifiState>();
                let run = with_reducer!(ctx, ScanWifiNetworks, on_scan_wifi_networks);

                Button::new("Scan networks")
                    .disabled(view.state().scanning_wifi)
                    .on_press(run)
                    .into()
    }
}
```

The [Wi-Fi guide](/docs/capabilities/wifi/) covers configuration and target behaviour. `MemoryWifiHost` can exercise the generic success path in tests; it does not make Wi-Fi scanning available on iOS. In the app, handle `on_err` with a clear manual setup message, such as asking the user to connect in iOS Settings. The web preview does not query Wi-Fi.

Keep direct iOS Wi-Fi calls in the host or typed provider. The shared component sends a request through Fission and renders the result it receives.

## Verify the unsupported path on iOS

The website preview cannot exercise the native provider. Build and launch the app in an iOS Simulator or on a device, then use the scan action. With the built-in host, confirm that the app receives the typed unsupported error and offers a manual setup path. Test the success reducer separately with `MemoryWifiHost`; that verifies the generic result handling, not iOS support.

Repeat with the feature unavailable, denied or cancelled, as applicable. Confirm the screen preserves the user’s existing data and offers the right recovery step. Use a physical device when the behavior depends on real hardware or an operating-system prompt.

### Run, test and build

```sh
cargo test
fission doctor ios --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
fission build --target ios --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Xcode, simulator SDK or Rust targets, `fission run` launches an iOS Simulator, and `fission test` checks that the generated host can start. A release build checks the simulator package; it does not verify iPhone signing or physical-device behavior.


### Simulator and device commands

Fission’s run command discovers iOS simulators. Run these checks from the generated project root:

```sh
fission doctor ios --project-dir .
fission devices --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
```


To verify a hardware-dependent path on an iPhone, configure development signing and Developer Mode, create a signed release IPA, then install it through Xcode Devices and Simulators:

```sh
fission package --project-dir . --target ios --format ipa --release
```

`fission run --target ios` remains simulator-only; it does not launch directly on a physical iPhone. A simulator preview cannot prove NFC, camera, biometrics or other physical capability behaviour.


Fission’s built-in iOS host does not implement Wi-Fi permission, scan, connect or disconnect operations. Its availability result reports Wi-Fi disabled, permission denied and no connected network; the other operations return typed unsupported errors. Treat unsupported as a capability boundary—not as permission denial or a successful empty scan—and give users a manual network setup path.
