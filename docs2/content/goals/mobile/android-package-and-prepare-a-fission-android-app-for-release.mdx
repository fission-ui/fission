A release is an artifact you can identify and verify, not merely a successful build command. An APK installed on a phone and an AAB uploaded to Play are different outputs. Testing one does not automatically qualify the other, especially if another command rebuilt the app in between.

Here, we configure Android packaging, keep signing inputs outside source control and collect evidence for exact files. The small review app records checks you performed; it does not pretend that ticking a box verifies a signature or that Fission readiness guarantees Play acceptance.

## Prepare the Android project

Complete [Android SDK/NDK setup](/blog/set-up-rust-android-gui-development-with-fission/), then prepare [an emulator](/blog/create-and-launch-a-fission-android-emulator/) and [a phone](/blog/run-a-fission-app-on-a-physical-android-phone/) for the appropriate checks.

```sh
cargo install cargo-fission
fission init android-package-and-prepare-a-fission-android-app-for-release
cd android-package-and-prepare-a-fission-android-app-for-release
cargo add serde_yaml
fission add-target android --project-dir .
```

For an existing product, work in that product's checkout instead of generating another app. Keep the generated `src/main.rs`; the library below makes the review screen the app on native and Web targets.

## Record evidence without inventing verification

The worksheet accepts an artifact digest and explicit self-reported checks. Its unit test validates only the digest's shape, not the file or signature. Notes are retained in this screen only; keep the actual package, manifest and verification results together outside the app.

pub fn valid_artifact_digest(value: &str) -> bool {
    value.len() == 64 && value.bytes().all(|byte| byte.is_ascii_hexdigit())
}

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn digest_entry_requires_a_complete_hex_digest() {
        assert!(valid_artifact_digest(&"a".repeat(64)));
        assert!(!valid_artifact_digest("not a digest"));
        assert!(!valid_artifact_digest(&"z".repeat(64)));
        assert!(!valid_artifact_digest(&"a".repeat(63)));
    }
}

use fission::prelude::*;
use crate::validation::valid_artifact_digest;

fission_component! {
    pub ReleaseReview<()> {
        state {
            digest: String = String::new(),
            signature_checked: bool = false,
            phone_checked: bool = false,
            notes: String = String::new(),
        }
    }
    view(review, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
        let valid_digest = valid_artifact_digest(review.digest.trim());
    } =>
    SafeArea(child: Scroll(child: Container(
        child: Column(gap: tokens.spacing.m, children: [
            Text(cx.tr("release.title")).size(tokens.typography.heading2_size),
            Text(cx.tr("release.context")),
            TextInput(
                label: Some(cx.tr("release.digest").into()),
                helper_text: Some(cx.tr("release.digest_help").into()),
                bind: review.digest,
                semantics_identifier: "release.digest".to_string(),
            ),
            Checkbox(
                label: Some(cx.tr("release.signature")),
                checked: review.signature_checked,
                bind(on_toggle): to(review.signature_checked),
            ),
            Checkbox(
                label: Some(cx.tr("release.phone")),
                checked: review.phone_checked,
                bind(on_toggle): to(review.phone_checked),
            ),
            TextInput(
                label: Some(cx.tr("release.notes").into()),
                helper_text: Some(cx.tr("release.notes_help").into()),
                multiline: true,
                bind: review.notes,
            ),
            Text(cx.tr(if valid_digest && review.signature_checked && review.phone_checked {
                "release.reported"
            } else { "release.incomplete" })),
            Text(cx.tr("release.not_verified")),
        ]),
    ).padding_all(tokens.spacing.l)))
}

use std::collections::HashMap;
use fission::prelude::*;

pub fn create_env() -> Env {
    let mut env = Env::default();
    env.locale = Locale::from("en-US");
    for (locale, source) in [
        ("en-US", include_str!("../i18n/en-US.yaml")),
        ("es-ES", include_str!("../i18n/es-ES.yaml")),
    ] {
        let messages: HashMap<String, String> =
            serde_yaml::from_str(source).expect("valid checked-in translations");
        env.i18n.add_bundle(TranslationBundle { locale: Locale::from(locale), messages });
    }
    env
}

## Configure identity, version and signing sources

Update the existing tables in `fission.toml`; do not append a second `[app]` table. Replace the example package namespace with one you own. Keep a released package's identity stable so the next package can be an update rather than a different app.

```toml
[app]
name = "Delivery Notes"
app_id = "com.yourcompany.deliverynotes"

[package.android]
package_name = "com.yourcompany.deliverynotes"
version_code = 1
version_name = "1.0.0"
keystore_alias = "upload"
keystore_env = "ANDROID_KEYSTORE"
keystore_password_env = "ANDROID_KEYSTORE_PASSWORD"
key_password_env = "ANDROID_KEY_PASSWORD"
```

This example makes the Android-specific version fields authoritative for Android. Do not accidentally retain a conflicting stale override whilst changing an app-wide version elsewhere. Increase the Android version code for successive releases; a user-facing version name alone does not establish update ordering. See [Android's versioning rules](https://developer.android.com/studio/publish/versioning).

Keep the keystore outside the repository, restrict access to its owner or signing service and back it up according to the product's key-management policy. Supply its path and passwords from a secure local or CI secret source. Do not put passwords in TOML, shell history, screenshots, logs or this worksheet. The generated release build fails when required signing inputs are missing.

For Google Play, an upload key and the key used for delivered APKs can be different under Play App Signing. Follow [Android's app-signing guidance](https://developer.android.com/studio/publish/app-signing) when generating or registering keys; do not replace an existing product's signing identity just to make a local installation succeed.

Run readiness separately for each format, then package that format:

```sh
fission readiness package --project-dir . --target android --format apk
fission package --project-dir . --target android --format apk --release
fission readiness package --project-dir . --target android --format aab
fission package --project-dir . --target android --format aab --release
```

## Verify the exact APK, then test the Play-delivered build

Use the artifact manifest emitted by `fission package` to locate the candidate. Do not guess an output path from a different Fission version, and do not call a later rebuild the same file merely because it has the same version name.

Inspect the actual APK with Android build-tools and install that file:

```sh
apksigner verify --verbose --print-certs /absolute/path/to/candidate.apk
adb devices -l
adb -s <adb-serial> install -r /absolute/path/to/candidate.apk
```

Compare the reported certificate fingerprint with the expected certificate from your signing policy, and compare the file's SHA-256 with the manifest. On Linux use `sha256sum`; on macOS use `shasum -a 256`. Record the digest of the checked file, not one copied from another build.

Launch the installed app and run the critical user journey, including a restart and any required permission path. A signature conflict is not a reason to uninstall a data-bearing app automatically; use a dedicated test device or resolve the signing mismatch deliberately.

`fission run --release` is useful for building and launching a release, but it can rebuild. It does not establish that the exact previously packaged APK was installed.

For the AAB, create an internal testing release in Play Console, upload the candidate, complete the required setup and signing steps, select authorised testers and share the opt-in link. Install through that test track on a phone and repeat the critical flow. The [official internal-testing guide](https://support.google.com/googleplay/android-developer/answer/9845334) describes the current process; do not confuse internal testing with a public production rollout.

Keep release test control disabled. The example configures the Android control port only for debug builds, and release environments must not set `FISSION_TEST_CONTROL_PORT`.
