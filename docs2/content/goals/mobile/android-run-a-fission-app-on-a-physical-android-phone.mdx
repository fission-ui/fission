## Create the project and add the target

Create the project and add the target used by this guide. Fission generates the native host; the app and its behaviour stay in shared Rust code.

```sh
cargo install cargo-fission
fission init android-run-a-fission-app-on-a-physical-android-phone
cd android-run-a-fission-app-on-a-physical-android-phone
fission add-target android --project-dir .
```

## Files created by Fission

This is the starter tree Fission generates. Keep shared app code in `src/`; the generated platform files handle native launch and packaging.

```text
android-run-a-fission-app-on-a-physical-android-phone/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── android/              # generated Android host
```

Keep the screen, shared state, reducers and reusable `fission_component!` components in the Rust project. Add a feature-specific state, service or effect module only when it gives the feature a useful boundary. The generated platform files handle native launch and packaging; shared components do not need to import platform APIs.

## Run a Fission app on a physical Android phone

On the Android phone, enable Developer options and USB debugging, unlock the phone, and approve this computer. Run `adb devices -l`; if the serial is marked `unauthorized`, accept the prompt and run the command again. Copy the authorized serial into `fission run --target android --device <serial> --project-dir .`. Confirm the app opens on the phone. An emulator checks layout and reducer behavior, but it cannot prove that a physical camera, NFC antenna, biometric sensor or radio works.

## Verify the Android development setup

The browser preview cannot inspect your computer. Run the target-specific `fission doctor` command below from the generated project root, then fix the first missing SDK, runtime, compiler target or device prerequisite it reports before trying the build again.

When the checks pass, run the generated app and keep the complete command output if it fails. A host smoke test confirms the scaffold can start; it does not prove release signing, device permissions or hardware behavior.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Android tools, `fission run` launches the selected emulator or connected device, and `fission test` checks that the generated host can start. A release build checks packaging, but none of these commands proves a physical permission or hardware flow works.


### Emulator and connected-device commands

Run these emulator checks from the generated project root:

```sh
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
```


For a real capability check, use an Android phone that has the required hardware and permission. Connect it with USB or Wi-Fi debugging, confirm its serial, then run the app on that device:

```sh
adb devices -l
fission run --target android --device <adb-serial> --project-dir .
```

An emulator can exercise the UI and memory-provider outcomes; it is not evidence that physical hardware or an OS permission flow works.
