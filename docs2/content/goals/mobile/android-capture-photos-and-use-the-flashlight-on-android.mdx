At Northbank Food Hub, Ada is inspecting **compressor bank A7** before the evening delivery window. The access panel is cracked near its lower hinge. The next technician needs a clear photo and a short note explaining why the compressor must remain isolated until the guard is replaced.

We will build that work order screen rather than a button that merely says “photo captured.” The entered equipment details identify the subject of the report; the evidence area stays empty until the camera returns a real image. In the Android app, Fission requests camera permission and then captures through the native provider. In a browser that supports `getUserMedia`, the same preview asks the browser for access to its actual camera. When a camera or flashlight is unavailable, the report remains available and the screen explains what can still be done.

The photo is kept as a Fission data stream while the app reads it for display. The note and photo stay in app memory for this tutorial session; this example does not persist or upload them. A production service would store the report and stream separately.

## Create the Android work-order app

Complete [Android SDK and NDK setup](/blog/set-up-rust-android-gui-development-with-fission/) and either [create an emulator](/blog/create-and-launch-a-fission-android-emulator/) or [connect a phone](/blog/run-a-fission-app-on-a-physical-android-phone/) first. Create the shared Rust project, add Android, and declare the camera capability. Fission uses that declaration when generating the Android camera permission configuration. The app code below stays in the shared crate, so the same report screen can run in the browser preview and on Android.

The app module separates state and camera reducers, the stream-reading job, the work-order form, and reusable widgets. Keep the generated `src/main.rs`; the shared shell setup supplies the actual screen and job registration on native and Web.

A capture has two asynchronous stages: obtaining a camera stream and reading the bounded display preview. Both count as pending work. Otherwise a second capture could start before the first image has been read and an older result could replace newer evidence.

## Build the work order and capture real photo evidence

Both shells start without a work order. Enter its reference, location, asset and instructions before capturing evidence. This makes the actual Android app usable without a fixture hidden in the browser entrypoint. In a connected product, an authorised work-order service would supply that record instead. On startup, the app asks the host which camera features are available. It only shows a flashlight control when a camera reports a torch, so the browser preview does not offer a hardware action it cannot perform. **Capture site photo** requests camera permission and calls `capture_photo` only after the host returns `Granted`.

The app state keeps the current note, photo bytes, capability availability, and pending operations together because they all belong to this open work order. A startup action checks camera availability without blocking the first screen. The camera returns a stream ID. A registered job reads it asynchronously with a 4 MiB limit because `Image::memory` needs a contiguous display buffer. This is a deliberately bounded preview boundary, not a pattern for collecting arbitrary media into action payloads. Stream large originals directly to their storage destination instead. The last attached photo and its metadata remain together until the replacement has been read successfully.

use fission::i18n::{Locale, TranslationBundle};
use fission::prelude::Env;

const SOURCES: [(&str, &str); 2] = [
    ("en-US", include_str!("../../i18n/en-US.yaml")),
    ("es-ES", include_str!("../../i18n/es-ES.yaml")),
];

pub fn create_env() -> Env {
    let mut env = Env::default();
    env.locale = Locale::from("en-US");
    for (locale, source) in SOURCES {
        let messages: HashMap<String, String> =
            serde_yaml::from_str(source).expect("valid field-report translations");
        env.i18n.add_bundle(TranslationBundle {
            locale: Locale::from(locale),
            messages,
        });
    }
    env
}

use fission::core::{DataStreamId, JobCtx, JobRef, JobSpec};
use serde::{Deserialize, Serialize};

#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]
pub struct EvidenceBytesRequest {
    pub stream: DataStreamId,
}

#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]
pub struct EvidenceBytes {
    pub bytes: Vec<u8>,
}

#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]
pub struct EvidenceReadError {
    pub message: String,
}

#[derive(Debug)]
pub struct ReadEvidenceBytesJob;

impl JobSpec for ReadEvidenceBytesJob {
    type Request = EvidenceBytesRequest;
    type Ok = EvidenceBytes;
    type Err = EvidenceReadError;

    const NAME: &'static str = "northbank.work-order.read-evidence";
}

pub const READ_EVIDENCE_BYTES_JOB: JobRef<ReadEvidenceBytesJob> =
    JobRef::new(ReadEvidenceBytesJob::NAME);

pub async fn read_evidence_bytes(
    request: EvidenceBytesRequest,
    ctx: JobCtx,
) -> Result<EvidenceBytes, EvidenceReadError> {
    let mut stream = ctx.open_data_stream(request.stream).map_err(|error| EvidenceReadError {
        message: error.to_string(),
    })?;
    // Image::memory needs a contiguous preview buffer. Bound it rather than
    // treating an arbitrary media stream as a small result.
    const MAX_PREVIEW_BYTES: usize = 4 * 1024 * 1024;
    let mut bytes = Vec::new();
    while let Some(chunk) = std::future::poll_fn(|cx| stream.as_mut().poll_next(cx)).await {
        let chunk = chunk.map_err(|error| EvidenceReadError { message: error.to_string() })?;
        if chunk.len() > MAX_PREVIEW_BYTES.saturating_sub(bytes.len()) {
            return Err(EvidenceReadError { message: "Image exceeds the 4 MiB preview limit".into() });
        }
        bytes.extend_from_slice(&chunk);
    }
    Ok(EvidenceBytes { bytes })
}

## Test permission, capture, and flashlight on Android

A browser preview checks the shared Fission reducers against the browser camera provider. It cannot prove that Android has a camera, that the OS permission is configured correctly, or that a physical flashlight is available. Test the installed app on an Android emulator for layout and permission behavior, then use a physical device for the actual camera and torch.

Enter and open the report, wait for the availability check and capture the damaged panel. Confirm that the real photo appears before wiring persistence; this sample does not save it. Deny camera access and repeat: the note and any previously attached photo should remain, and the screen should explain how to recover. Before the first successful capture the count stays zero; a cancelled replacement must not erase earlier evidence. Cancel a capture if the system UI offers cancellation. On hardware without a torch, confirm no flashlight action is shown while photo evidence remains available.

The example stores its note and current photo bytes in app state for the duration of this tutorial session. A production work-order system should persist the note and stream, associate them with the authenticated technician, and submit them to an authorized service. Keep that network request in an asynchronous effect or job; do not mark the work order submitted just because a local camera capture succeeded.
