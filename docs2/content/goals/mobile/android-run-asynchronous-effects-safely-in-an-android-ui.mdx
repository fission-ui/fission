## Create the project and add the target

Create a project and add Android as a target. The screen and effect logic stay in shared Rust; the generated Android host is what builds and launches them on the device.

```sh
cargo install cargo-fission
fission init android-run-asynchronous-effects-safely-in-an-android-ui
cd android-run-asynchronous-effects-safely-in-an-android-ui
fission add-target android --project-dir .
```

## Files created by Fission

This is the tree Fission creates. Shared app code belongs under `src/`, while `platforms/android/` holds the generated host for launch and packaging. We will add feature-specific pieces only when the example needs them.

```text
android-run-asynchronous-effects-safely-in-an-android-ui/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── android/              # generated Android host
```

Keep the screen, state, reducers and reusable `fission_component!` components in the shared Rust project. Add a separate state, service or effect module when it gives the feature a useful boundary, and name it for that feature. The Android host handles platform launch and packaging; shared components do not need Android APIs.

## Run asynchronous effects safely in an Android UI

The tricky case is not starting the request; it is getting an old response after a newer one. Give each request an ID and keep the current ID in app state. When a response arrives, the reducer can ignore it if the user has already started another request or left the screen. While work is running, show a pending state and keep useful existing data visible. Handle both success and failure with typed actions, and offer a retry after an error. Only offer cancel if the underlying service can actually cancel the work.

You can test the ordering without a network connection: start two requests in a Rust test, return the newer result first, then return the older result. The old response must not replace the newer state. Effects run outside reducers, so keep sleep, file access, SQL and network work out of the UI thread.

## Check delayed and interrupted work on Android

In a Rust test, use a fake service so you choose when each request completes. Start two requests, return the newer result first, then return the older one. Because state records the latest request ID, the reducer should ignore that late response and leave the newer result on screen.

Also background the app while a request is pending, then return to it. Check that the UI reaches a clear success or error state, and that retrying does not make the user repeat work that has already been saved.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

`cargo test` runs the Rust tests you write; the generated project does not create tests for this feature. `fission doctor` checks the Android tools, `fission run` launches an emulator or connected phone, and `fission test` checks that the generated host starts. A release build checks packaging. It does not prove a device-specific permission or hardware flow works.


### Emulator and connected-device commands

Run these checks from the generated project root with an emulator or phone connected:
