"The host" can mean several different things. Here it means the generated iOS packaging and launch scaffold around the shared Rust app. It is not another place to implement the journey planner's state or a promise that every platform capability has a Swift implementation.

We will trace a working Compose app from its entrypoint to a simulator bundle. This is more useful than an architecture card which changes its caption: we can identify which code supplies an interaction and which generated file makes that code launch on iOS.

## Create a project to inspect

Complete [iOS setup](/blog/set-up-rust-ios-development-with-fission/) first.

```sh
cargo install cargo-fission
fission init ios-understand-fissions-generated-ios-host
cd ios-understand-fissions-generated-ios-host
fission add-target ios --project-dir .
cargo add serde_yaml
```

The generated directory includes these responsibilities:

```text
fission.toml                       target, capability and package inputs
src/main.rs                        target-aware Rust entrypoint
src/lib.rs                         shell setup and shared app modules
platforms/ios/README.md             instructions for this generated host
platforms/ios/Info.plist            native bundle metadata
platforms/ios/Package.swift         generated Swift host package
platforms/ios/NativeModules/        configured native-module staging
platforms/ios/LaunchScreen.storyboard
platforms/ios/package-sim.sh        Rust build and simulator .app assembly
platforms/ios/run-sim.sh            simulator install and launch
platforms/ios/test-sim.sh           launch/control-endpoint smoke test
platforms/ios/package-ipa.sh         device IPA packaging and signing path
```

Read the generated README rather than assuming the host is an Xcode project with a conventional app target. The current scaffold is a simulator-bundle template and scripts, with generated Swift packages for native integration. The existence of `Package.swift` alone does not prove that a particular native module is linked and callable from Rust.

## Follow an actual shared component

Use the journey editor from [the component tutorial](/blog/compose-an-ios-app-from-reusable-fission-widgets/) as the app under inspection. It accepts real input and prepares a snapshot, so we can distinguish shared interaction behavior from native launch machinery.

Keep the generated `src/main.rs`. On iOS it calls `run_mobile` in the shared library. That function constructs `MobileApp<JourneyState, _>` with the same `JourneyScreen` and translation setup used by Web and desktop.

                        on_press: reduce { state.locale = Locale::from("es-ES"); },
                    ),
                ]),
                FormControl(
                    label: Some(cx.tr("journey.origin")),
                    required: true,
                    child: TextInput(
                        value: screen.origin.clone(),
                        bind(on_input): to(screen.origin),

                ),
                FormControl(
                    label: Some(cx.tr("journey.destination")),
                    required: true,
                    child: TextInput(
                        value: screen.destination.clone(),

use fission::i18n::{Locale, TranslationBundle};
use fission::prelude::*;
use std::collections::HashMap;

pub fn create_env() -> Env {
    let mut env = Env::default();
    env.locale = Locale::from("en-US");
    for (locale, source) in [
        ("en-US", include_str!("../i18n/en-US.yaml")),
        ("es-ES", include_str!("../i18n/es-ES.yaml")),
    ] {
        let messages: HashMap<String, String> =
            serde_yaml::from_str(source).expect("valid journey translations");
        env.i18n.add_bundle(TranslationBundle {
            locale: Locale::from(locale),
            messages,
        });
    }
    env
}

pub fn sync_env(state: &crate::app::JourneyState, env: &mut Env) {
    env.locale = state.locale.clone();
}

## Trace the output rather than inferring it from names

The simulator packaging script runs Cargo for the configured iOS simulator target, obtains Cargo's actual target directory through metadata and copies the resulting executable into a `.app` bundle. It then installs the bundle metadata and image resources and compiles the launch storyboard with `ibtool`. The simulator run script installs and launches that bundle with `simctl`.

Run the generated entrypoint on your Mac:

```sh
fission doctor ios --project-dir .
./platforms/ios/package-sim.sh
```

The script prints the resulting bundle path. Inspect that bundle's executable, `Info.plist`, icon and compiled storyboard. Looking only at `platforms/ios/Info.plist` checks an input; it does not establish that the packaged metadata contains the same intended values after the packaging substitutions.

Keep configuration in `fission.toml` where the CLI exposes the setting. For example, capability commands synchronize privacy metadata and the documented splash/icon tables supply generated assets. Editing a copied resource in the output bundle changes one artifact, not the project's authority, and can disappear on the next build.

Native-module source is a separate integration boundary. Read its generated README before adding code, and prove the generated package is built, linked and invoked. Do not move ordinary state transitions there just because a `NativeModules` folder exists.

## Separate launch, interaction and device distribution

```sh
fission devices --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
```

Follow [the simulator guide](/blog/choose-boot-and-launch-an-ios-simulator-with-fission/) for target selection. After launch, repeat the journey task and language switch. A healthy control endpoint proves the host reached its event loop; it does not prove a button updates the correct record or the keyboard leaves it reachable.

A physical iPhone uses the device target and signing path, not the simulator binary with another filename. Follow [the installation guide](/blog/install-a-fission-app-on-a-physical-iphone/) and [the TestFlight guide](/blog/package-and-prepare-a-fission-ios-app-for-testflight/) rather than treating simulator packaging as release qualification.

When a failure occurs, keep its boundary clear. A Cargo compile error belongs before bundle assembly; a missing storyboard resource belongs to packaging; an installation/signature rejection occurs later; an incorrect prepared journey is shared app behavior. Starting from the real failing step avoids changing an unrelated layer merely because it contains an iOS-looking filename.
