## Create the project and add the target

```sh
cargo install cargo-fission
fission init mobile-build-a-multi-screen-mobile-sign-in-and-account-flow
cd mobile-build-a-multi-screen-mobile-sign-in-and-account-flow
fission add-target android ios --project-dir .
fission add-capability passkeys --project-dir .
```

## Files created by Fission

Fission generates Android and iOS hosts alongside the shared Rust project:

```text
mobile-build-a-multi-screen-mobile-sign-in-and-account-flow/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    ├── android/              # generated Android host
    └── ios/                  # generated iOS host
```

Keep sign-in state, validation, and route decisions in shared Rust. The generated hosts launch the same account flow with each target’s Passkeys provider.

Start with a person signing in to Northbank. This first stage makes the account and the server-verification boundary visible; it does not pretend that reading a label is a sign-in action. The next stage connects the passkey button to Fission and renders pending, result and recovery states in the same view. The browser preview uses an in-memory host and does not claim to authenticate the user.

## Run the Passkey operation through Fission

Keep host work out of component conversion. The button dispatches a typed action, its reducer queues the capability request, and separate completion reducers update the screen. The Web preview installs `MemoryPasskeyHost` and sends the same operation through Fission’s typed capability path. Its deterministic response is not a claim about device hardware, OS permission or native platform support.

The preview's MemoryPasskeyHost returns synthetic assertion data. The app refuses to open the passkey prompt until it has a challenge; the preview injects deterministic bytes only to exercise the UI. A real sign-in attempt fetches a fresh challenge from the relying-party server, consumes it for one passkey request, and sends the returned assertion back for verification. Keep the assertion in memory only; do not persist or log it, and do not treat it as a signed-in session. A retry needs a new challenge from the server.

```rust
use fission::prelude::*;

#[derive(Debug)]
pub enum SignInError {
    ChallengeMissing,
    MissingAssertion,
    Host(String),
    HostWithoutDetails,
}

#[derive(Debug, Default)]
pub struct AccountSignInState {
    pub pending: bool,
    /// Fresh challenge supplied by the relying-party server for this attempt.
    pub challenge: Option<Vec<u8>>,
    /// Keep the response only long enough to send it to the server for verification.
    pub assertion: Option<PasskeyAuthenticationResult>,
    pub error: Option<SignInError>,
}

impl GlobalState for AccountSignInState {}

#[fission_reducer(RunCapability)]
pub fn run_capability(state: &mut AccountSignInState, ctx: &mut ReducerContext<AccountSignInState>) {
    if state.pending || state.assertion.is_some() {
        return;
    }

    state.error = None;
    let Some(challenge) = state.challenge.take() else {
        state.error = Some(SignInError::ChallengeMissing);
        return;
    };
    state.pending = true;
    state.assertion = None;

    let ok: ActionEnvelope = CapabilitySucceeded.into();
    let err: ActionEnvelope = CapabilityFailed.into();

    ctx.effects
        .passkeys().authenticate(PasskeyAuthenticationRequest {
            relying_party_id: "example.com".into(),
            challenge,
            allow_credentials: Vec::new(),
            user_verification: PasskeyUserVerification::Preferred,
            mediation: PasskeyMediation::Required,
            timeout_ms: Some(60_000),
        })
        .on_ok(ok)
        .on_err(err);
}

#[fission_reducer(CapabilitySucceeded)]
pub fn capability_succeeded(
    state: &mut AccountSignInState,
    ctx: &mut ReducerContext<AccountSignInState>,
) {
    state.pending = false;
    if let Some(assertion) = ctx.input.capability_ok(AUTHENTICATE_PASSKEY) {
        state.assertion = Some(assertion);
        state.error = None;
    } else {
        state.assertion = None;
        state.error = Some(SignInError::MissingAssertion);
    }
}

#[fission_reducer(CapabilityFailed)]
pub fn capability_failed(
    state: &mut AccountSignInState,
    ctx: &mut ReducerContext<AccountSignInState>,
) {
    state.pending = false;
    state.assertion = None;
    let code = ctx
        .input
        .capability_error(AUTHENTICATE_PASSKEY)
        .map(|error| error.code);
    state.error = Some(code.map(SignInError::Host).unwrap_or(SignInError::HostWithoutDetails));
}

pub fn callback_registry() -> ActionRegistry<AccountSignInState> {
    let mut registry = ActionRegistry::new();
    registry.register(reduce_with!(capability_succeeded));
    registry.register(reduce_with!(capability_failed));
    registry
}

fission_component! {
    pub AccountSignInScreen<AccountSignInState> {}
    view(_screen, state, cx) {
        let tokens = &cx.view.env().theme.tokens;
        let action = with_reducer!(cx.build, RunCapability, run_capability);
        let status = if state.pending {
            cx.tr("auth.waiting")
        } else if let Some(error) = &state.error {
            match error {
                SignInError::ChallengeMissing => cx.tr("auth.challenge_missing"),
                SignInError::MissingAssertion => cx.tr("auth.missing"),
                SignInError::Host(code) => cx.tr(match code.as_str() {
                    "cancelled" | "canceled" | "user_cancel" | "not_allowed" => "auth.error.cancelled",
                    "unsupported" | "unavailable" => "auth.error.unavailable",
                    "security_error" => "auth.error.domain",
                    _ => "auth.error.generic",
                }),
                SignInError::HostWithoutDetails => cx.tr("auth.error_unknown"),
            }
        } else if state.assertion.is_some() {
            cx.tr("auth.assertion")
        } else if state.challenge.is_none() {
            cx.tr("auth.challenge_missing")
        } else {
            cx.tr("auth.ready")
        };
    } =>
    SemanticsRegion(
        identifier: Some("account-passkey-sign-in".to_string()),
        label: Some(cx.tr("auth.title")),
        child: Container(
            Column(gap: tokens.spacing.m, children: [
                Text(cx.tr("auth.account"))
                    .weight(tokens.typography.font_weight_bold),
                Text(cx.tr("auth.title"))
                    .size(tokens.typography.heading2_size),
                Text(cx.tr("auth.identity"))
                    .color(tokens.colors.text_secondary),
                Text(cx.tr("auth.context")),
                Button(
                    child: Text(cx.tr("auth.action")),
                    key: "run-capability",
                    variant: ButtonVariant::Primary,
                    disabled: state.pending || state.challenge.is_none() || state.assertion.is_some(),
                    loading: state.pending,
                    on_press: action,
                ),
                Container(Text(status))
                    .padding_all(tokens.spacing.m)
                    .bg(tokens.colors.background)
                    .border(tokens.colors.border, 1.0)
                    .border_radius(tokens.radii.medium),
            ])
        )
        .padding_all(tokens.spacing.l)
        .bg(tokens.colors.surface)
        .border(tokens.colors.border, 1.0)
        .border_radius(tokens.radii.large),
    )
}
```

## Verify the native request on Android and iOS

The website preview cannot exercise the native provider. Build and launch this target in an Android emulator, an iOS Simulator or on a physical device, then use the feature action from the component above. Check the result the host actually returns, including cancellation, no matching credential, an unavailable provider or a domain-association error where those apply.

Repeat with no matching credential and with the user cancelling the prompt. Confirm the screen remains signed out and offers a recovery path. Use a physical device when the behavior depends on native passkey support or an operating-system prompt.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

`cargo test` runs Rust tests you add for reducer or stale-completion rules; the generated scaffold does not create those feature tests. `fission doctor` checks each target’s toolchain, `fission run` launches its emulator or Simulator, and `fission test` checks that the generated host can start. A release build validates packaging, not real hardware behavior.


### Run the shared project on both mobile targets

Run both target checks from the generated project root:

```sh
fission doctor android --project-dir .
fission run --target android --project-dir .
fission doctor ios --project-dir .
fission run --target ios --project-dir .
fission test --target android --project-dir .
fission test --target ios --project-dir .
```


Verify the relevant hardware on a connected Android phone and a signed iPhone build. Use `adb devices -l` and `fission run --target android --device <adb-serial> --project-dir .` for Android. For iOS, use `fission package --project-dir . --target ios --format ipa --release` and install through Xcode Devices and Simulators. The iOS `fission run` path is simulator-only.
