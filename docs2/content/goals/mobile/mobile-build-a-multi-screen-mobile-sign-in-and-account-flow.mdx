## Create the project and add the target

Install the Fission command line, create the app, and add its native target.

```sh
cargo install cargo-fission
fission init mobile-build-a-multi-screen-mobile-sign-in-and-account-flow
cd mobile-build-a-multi-screen-mobile-sign-in-and-account-flow
fission add-target android ios --project-dir .
fission add-capability passkeys --project-dir .
```

## Files created by Fission

This is the starter tree after `fission init` and `fission add-target`; the component and state used for this task are additions in the steps below. Keep shared Rust behavior under `src/` and leave target launch and packaging in the generated Android and iOS hosts.

```text
mobile-build-a-multi-screen-mobile-sign-in-and-account-flow/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    ├── android/              # generated Android host
    └── ios/                  # generated iOS host
```

Keep `src/app.rs`, shared state, reducers and reusable `fission_component!` components in the common Rust project. Add a state, service or effect module only when this feature needs that boundary, and use a name tied to the feature. The generated Android and iOS hosts own launch and packaging details; shared components describe the user task without importing either platform API.

## Connect the Passkeys provider to the user action

This is the real Fission request path for this feature. Keep permission and hardware work outside the component view: the component dispatches one intent, the reducer queues the request, and success or error reducers store the returned result.

Start with task data and status in the app state. Keep a text-field draft, open flag or selected tab in the owning component instead of duplicating that temporary state here:

```rust
#[derive(Debug, Default)]
struct PasskeyState {
    // Add these fields to your existing app state.
    login_challenge: Vec<u8>,
    known_credentials: Vec<PasskeyCredentialDescriptor>,
    pending_assertion: Option<PasskeyAuthenticationResult>,
    login_error: Option<String>,
}

impl GlobalState for PasskeyState {}
```

Handle successful and failed results separately so the screen can explain denied permission, cancellation, unsupported hardware and provider errors:

```rust
#[fission_reducer(PasskeyAssertionReady)]
fn on_passkey_assertion_ready(state: &mut PasskeyState, assertion: PasskeyAuthenticationResult) {
    state.pending_assertion = Some(assertion);
    state.login_error = None;
}

#[fission_reducer(PasskeySignInFailed)]
fn on_passkey_sign_in_failed(state: &mut PasskeyState, error: PasskeyError) {
    state.pending_assertion = None;
    state.login_error = Some(error.message);
}
```

Queue the operation after the user presses the named control. The host completes asynchronously and dispatches the matching reducer:

```rust
ctx.effects
    .passkeys()
    .authenticate(PasskeyAuthenticationRequest {
        relying_party_id: "example.com".into(),
        challenge: state.login_challenge.clone(),
        allow_credentials: state.known_credentials.clone(),
        user_verification: PasskeyUserVerification::Preferred,
        mediation: PasskeyMediation::Conditional,
        timeout_ms: Some(60_000),
    })
    .on_ok(ctx.effects.bind(
        PasskeyAssertionReady(PasskeyAuthenticationResult::default()),
        reduce_with!(on_passkey_assertion_ready),
    ))
    .on_err(ctx.effects.bind(
        PasskeySignInFailed(PasskeyError::default()),
        reduce_with!(on_passkey_sign_in_failed),
    ));
```

Bind the user action from a reusable Fission component. Keep the visible label in the same control so it works with touch, keyboard and assistive technology:

```rust
fission_component!
{
    pub PasskeySignInButton<PasskeyState> {
    }
    view(component, _state, _cx) => rust {
        let (ctx, view) = fission::build::current::<PasskeyState>();
                let run = with_reducer!(ctx, SignInWithPasskey, on_sign_in_with_passkey);

                Button::new("Sign in with passkey")
                    .disabled(false)
                    .on_press(run)
                    .into()
    }
}
```

The [complete Passkeys guide](/docs/capabilities/passkeys/) explains configuration and expected platform behaviour. Test a successful memory-provider response and an unavailable or denied response before relying on the physical-device check below. The preview is read-only. The native target uses Fission’s provider to perform the request and report the result.

Keep platform-only code behind the generated target boundary or a typed provider; the shared component should describe the user task rather than call an operating-system API directly.

### Keep authentication and navigation separate

Use a form component for the email and password draft, a reducer for submission state, and a service or effect for the remote request. Do not navigate to a protected route until the service returns a valid session. Store the session in the chosen persistent store only after success; route guards should read the resulting app state, not a boolean that the form sets optimistically. On logout or expiry, clear the session and return to the sign-in route. Verify invalid input, failed credentials, an expired session, direct access to a protected URL, a cold-start deep link and logout.

## Verify the native request on Android and iOS

The website preview cannot exercise the native provider. Build and launch this target on a supported emulator or device, then use the feature action from the component above. Check the result the host actually returns, including denial, cancellation or unsupported hardware where those outcomes apply.

Repeat with the feature unavailable, denied or cancelled, as applicable. Confirm the screen preserves the user’s existing data and offers the right recovery step. Use a physical device when the behavior depends on real hardware or an operating-system prompt.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

`cargo test` runs Rust tests you add for reducer or stale-completion rules; the generated scaffold does not create those feature tests. `fission doctor` checks each target’s toolchain, `fission run` launches its emulator or Simulator, and `fission test` checks that the generated host can start. A release build validates packaging, not real hardware behavior.


### Run the shared project on both mobile targets

Run both target checks from the generated project root:

```sh
fission doctor android --project-dir .
fission run --target android --project-dir .
fission doctor ios --project-dir .
fission run --target ios --project-dir .
fission test --target android --project-dir .
fission test --target ios --project-dir .
```


Verify the relevant hardware on a connected Android phone and a signed iPhone build. Use `adb devices -l` and `fission run --target android --device <adb-serial> --project-dir .` for Android. For iOS, use `fission package --project-dir . --target ios --format ipa --release` and install through Xcode Devices and Simulators. The iOS `fission run` path is simulator-only.
