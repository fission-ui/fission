## Create the project and add the target

Install the Fission command line, create the app, and add its native target.

```sh
cargo install cargo-fission
fission init android-persist-android-app-state-with-fission-store-and-sqlite
cd android-persist-android-app-state-with-fission-store-and-sqlite
fission add-target android --project-dir .
fission add-capability storage --project-dir .
```

The generated Android host owns launch and packaging details; shared components describe the user task without importing Android APIs.

## Persist a typed preference through Fission Store

Use the high-level Store API for a small typed value such as a theme choice. A namespaced `StoreKey<String>` keeps the key and value type explicit; call it from a reducer and render **Saved** only after the asynchronous result returns:

```rust
const SETTINGS: &str = "settings";

#[fission_reducer(SaveTheme)]
fn save_theme(
    _state: &mut AppState,
    action: SaveTheme,
    ctx: &mut ReducerContext<AppState>,
) {
    let key = StoreKey::<String>::new(SETTINGS, "theme");
    ctx.effects
        .store()
        .set(key, &action.theme)
        .expect("String is serialisable")
        .on_ok(ActionEnvelope::from(ThemeSaved))
        .on_err(ActionEnvelope::from(StorageFailed));
}
```

At startup, load the saved value before showing it as the current preference. Keep a visible loading state while hydration is pending, use the default only when no value exists, and show a recoverable error if the provider cannot open the database. Run the same flow after a full app restart to verify persistence.

## Verify saved data on Android

Save one change, close the app completely, and launch it again. The screen should load the saved value before presenting it as current. Test the empty database and an unreadable or incompatible database separately so loading, default and error states are not confused.

For SQL migrations, open both a fresh database and one created by the previous schema version. For offline workflows, disconnect the network, edit locally, reconnect, and confirm a failed or stale response does not erase the newer local change.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Android tools, `fission run` launches the selected emulator or connected device, and `fission test` checks that the generated host can start. A release build checks packaging, but none of these commands proves a physical permission or hardware flow works.
