An Android launch has several stages: Rust compilation, Gradle packaging, installation and starting the app process. A failure at one stage says little about the later stages. If Rust did not link, changing an Android permission cannot fix the immediate problem.

Here, we start at the first failing command, identify the stage it belongs to, and collect enough evidence to reproduce it. The aim is not to make the error disappear by changing unrelated settings; it is to understand why that command failed.

## Work in the project that failed

Start in your existing app and preserve its configuration and logs. Do not run `fission init` over it. Complete the [Android setup guide](/blog/set-up-rust-android-gui-development-with-fission/) if the SDK and NDK have not been installed.

The embedded example is a small diagnostic-note app, not a simulated device inspector. If you want to run that separate reproduction, create a new scratch project:

```sh
fission init android-diagnose-android-build-install-and-launch-failures
cd android-diagnose-android-build-install-and-launch-failures
fission add-target android --project-dir .
cargo add serde_yaml
```

## Keep a useful diagnostic note

Record the command, device and first relevant error yourself. The app never claims to have inspected the SDK, installed a package or fixed the toolchain. Its preview and native shell run the same Compose form; the note is retained for this session and is not uploaded or persisted.

```rust
use fission::prelude::*;

fission_component! {
    pub DiagnosticNote<()> {
        state {
            command: String = String::new(),
            device: String = String::new(),
            first_error: String = String::new(),
            reviewed: bool = false,
        }
    }
    view(note, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
        let complete = !note.command.trim().is_empty() && !note.first_error.trim().is_empty();
        let summary = cx.tr("diagnostic.summary")
            .replace("{command}", &note.command)
            .replace("{device}", &note.device)
            .replace("{error}", &note.first_error);
    } =>
    Container(SafeArea(child: Scroll(child:
        Container(Column(gap: tokens.spacing.m, children: [
            Text(cx.tr("diagnostic.title")).size(tokens.typography.heading1_size),
            Text(cx.tr("diagnostic.scope")).color(tokens.colors.text_secondary),
            TextInput(
                label: Some(cx.tr("diagnostic.command").into()),
                bind: note.command,
                required: true,
                semantics_identifier: "diagnostic.command".to_string(),
            ),
            TextInput(
                label: Some(cx.tr("diagnostic.device").into()),
                bind: note.device,
                semantics_identifier: "diagnostic.device".to_string(),
            ),
            TextInput(
                label: Some(cx.tr("diagnostic.error").into()),
                bind: note.first_error,
                required: true,
                multiline: true,
                semantics_identifier: "diagnostic.error".to_string(),
            ),
            Button(
                child: Text(cx.tr("diagnostic.review")),
                key: "review-diagnostic-note",
                on_press: reduce { note.reviewed = true; },
            ).semantics_identifier("diagnostic.review"),
            if note.reviewed {
                if complete { Code(text: summary) }
                else { Text(cx.tr("diagnostic.invalid")).color(tokens.colors.error) }
            },
        ]))
        .padding_all(tokens.spacing.l)
        .width_length(Length::percent(100.0))
        .max_width(760.0),
    )))
    .height_length(Length::vh(100.0))
}
```

```rust
use std::collections::HashMap;
use fission::prelude::*;

pub fn create_env() -> Env {
    let mut env = Env::default();
    env.locale = Locale::from("en-US");
    for (locale, source) in [
        ("en-US", include_str!("../i18n/en-US.yaml")),
        ("es-ES", include_str!("../i18n/es-ES.yaml")),
    ] {
        let messages: HashMap<String, String> =
            serde_yaml::from_str(source).expect("valid checked-in translations");
        env.i18n.add_bundle(TranslationBundle { locale: Locale::from(locale), messages });
    }
    env
}
```

## Separate setup, compilation, packaging, installation and launch

Run prerequisite checks before the build, and separate a package build from installation:

```sh
fission doctor android --project-dir .
fission build --target android --project-dir .
fission devices --project-dir .
adb devices -l
```

Read the first meaningful error in context. A later “build failed” line is a summary, not its cause. Keep the exact command, source revision, target, selected device ID and the preceding diagnostic lines. Do not clear build caches as a first response to a reproducible error.

If packaging succeeds, select the intended emulator or phone explicitly:

```sh
fission run --target android --device <adb-serial> --project-dir .
```

An ADB device listed as unauthorised is a device-connection problem, not a Rust compiler failure. Follow the [physical-phone setup guide](/blog/run-a-fission-app-on-a-physical-android-phone/) to authorise debugging. For an installation failure, retain the install error and check free space, package identity and the signing identity of an existing installation. Do not uninstall an app containing data you need merely to hide a signing conflict.

If installation succeeds but the app exits or never becomes usable, attach to that device's logs:

```sh
fission logs --target android --device <adb-serial> --project-dir . --follow
```

For additional Android runtime context, use ADB directly:

```sh
adb -s <adb-serial> logcat -v threadtime
```

Reproduce once while collecting the logs, then stop the command. Look for the app process and the earliest relevant Rust panic, native-linker failure or Android exception rather than treating every system warning as the cause. Avoid clearing logcat before collecting a failure you cannot easily reproduce.

Review logs before sharing them publicly: remove credentials, tokens, personal data and proprietary payloads without deleting the surrounding error context.

## Verify the fix at the stage that failed

After fixing the first failure, rerun the same command against the same device. Then move to the next stage. A working package build cannot establish that installation succeeds, and a started process cannot establish that the UI is responsive.

```sh
cargo test
fission test --target android --project-dir .
```

Use the diagnostic-note app only in a scratch reproduction project. Enter text, review it and edit it again on the emulator or phone. That confirms an interaction path, not the correctness of your production app. Keep your real application and its state intact whilst reducing a bug to a reproducible case.

The generated smoke test is useful after the host starts. Follow it with the actual failing workflow, including permission prompts or hardware on a physical device when those are involved.
