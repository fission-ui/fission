Keep the operation and its request ID in shared app state so a screen rebuild does not lose the pending work. Reducers can then ignore a late result after the user resumes or moves to another screen.

## Handle mobile lifecycle changes while effects are in flight

When the app pauses, keep product state in GlobalState or persistent storage; do not expect a component conversion or a background thread to preserve an unfinished operation. On resume, re-check the request ID, refresh transient permission status and ignore results from an obsolete screen. Persist an edit before starting sync if losing it would harm the user. Test pausing during a request, process termination, restart with a pending record, and a late response after the user navigates away. Do not promise background execution unless the operating system service has been configured for it.

The component below is a browser-safe version of this screen. It uses Fission's retained component state and widgets to make the task visible; it does not call a native provider or operating-system API.

<!-- fission:file path="src/app.rs" -->
```rust
use fission::prelude::*;

fission_component! {
    pub MobileLifecycleChangesEffectsAre<()> {
        props {
            title: String,
            step: String,
            goal: String,
        }
        state {
            draft_revision: u32 = 0,
            sync_pending: bool = false,
            sync_error: bool = false,
        }
    }
    view(screen, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
    } =>
    SemanticsRegion(
        identifier: Some("offline-workflow".to_string()),
        label: Some(screen.title.clone()),
        child: Container(
            Column(gap: tokens.spacing.m, children: [
                Text(screen.title.clone())

                    .weight(tokens.typography.font_weight_bold),
                Text(screen.goal.clone()),
                Text(format!("Local draft revision {}", screen.draft_revision)),
                Button(
                    child: Text("Save a local edit"),
                    key: "edit-draft",
                    on_press: reduce {
                        screen.draft_revision += 1;
                        screen.sync_pending = true;
                        screen.sync_error = false;
                    },
                ),
                Button(
                    child: Text("Simulate sync response"),
                    key: "sync-response",
                    on_press: reduce {
                        screen.sync_pending = false;
                        screen.sync_error = true;
                    },
                ),
                Text(if screen.sync_pending {
                    "Saved locally; waiting for sync."
                } else if screen.sync_error {
                    "Sync failed; the local draft is still available to retry."
                } else {
                    "All local changes are saved."
                }),
            ])
        )
        .padding_all(tokens.spacing.l)
        .bg(tokens.colors.surface)
        .border(tokens.colors.border, 1.0)
        .border_radius(tokens.radii.large),
    )
}
```

## Check delayed and interrupted work on Android and iOS

In a Rust test, a fake service returns the result you choose instead of making a network request. Start two requests, return the newer result first, and then return the older one. Because the app stores the newest request ID, the reducer should ignore that stale response and keep the newer result on screen.

Also background the app while work is pending, then return to it. The loading state should finish or recover, errors should remain visible, and a retry should not require the user to repeat work that was already saved.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

`cargo test` runs Rust tests you add for reducer or stale-completion rules; the generated scaffold does not create those feature tests. `fission doctor` checks each target’s toolchain, `fission run` launches its emulator or Simulator, and `fission test` checks that the generated host can start. A release build validates packaging, not real hardware behavior.


### Run the shared project on both mobile targets

Run both target checks from the generated project root:
