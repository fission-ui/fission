A maintenance queue is useful because the queue and its detail screens describe the same repairs. If resolving a job only changes the detail screen's local state, returning to the queue shows an old result. Navigation makes that mistake visible; it does not cause it.

Here, we keep work orders in shared app state and use Fission's `Router` to select a queue or a detail route. Android Back changes the shell's route history. A single route handler mirrors those changes into app state, including changes that did not start in a Compose button.

The app starts empty. Enter your own reports rather than relying on preview fixtures. Records last for this run; [persistent Android storage](/blog/persist-android-app-state-with-fission-store-and-sqlite/) is a separate step, and this guide does not claim to save repairs across restarts.

## Build a queue from reports the user enters

A report needs a recognisable problem, a location and enough detail for the technician. The form owns its draft locally. Adding a valid report creates a record in `GlobalState` and clears the draft; an incomplete report leaves the input intact.

The record ID is allocated once when the record is created. It is not the row position. We use it for the route and the row's retained widget identity, so changing the list cannot attach an old row to a different repair. This in-memory sequence is sufficient for one app run; a shared service would supply its own durable IDs.

use fission::prelude::*;

#[derive(Clone, Debug, PartialEq, Eq)]
pub struct WorkOrder {
    pub id: u64,
    pub title: String,
    pub location: String,
    pub report: String,
    pub resolved: bool,
}

#[derive(Clone, Debug, PartialEq, Eq)]
pub struct WorkOrderState {
    pub current_path: String,
    pub orders: Vec<WorkOrder>,
    next_id: u64,
}

impl Default for WorkOrderState {
    fn default() -> Self {
        Self { current_path: "/".into(), orders: Vec::new(), next_id: 1 }
    }
}
impl GlobalState for WorkOrderState {}

impl WorkOrderState {
    pub fn add(&mut self, title: String, location: String, report: String) -> bool {
        if title.trim().is_empty() || location.trim().is_empty() || report.trim().is_empty() {
            return false;
        }
        let Some(next_id) = self.next_id.checked_add(1) else { return false };
        self.orders.push(WorkOrder {
            id: self.next_id,
            title: title.trim().to_owned(),
            location: location.trim().to_owned(),
            report: report.trim().to_owned(),
            resolved: false,
        });
        self.next_id = next_id;
        true
    }

    pub fn resolve(&mut self, id: u64) {
        if let Some(order) = self.orders.iter_mut().find(|order| order.id == id) {
            order.resolved = true;
        }
    }
}

pub fn route_changed(
    state: &mut WorkOrderState,
    action: fission::core::action::ShellRouteChanged,
    _cx: &mut ReducerContext<WorkOrderState>,
) {
    state.current_path = action.location.pathname;
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn invalid_report_does_not_allocate_an_id() {
        let mut state = WorkOrderState::default();
        assert!(!state.add("Boiler".into(), "Basement".into(), " ".into()));
        assert!(state.add("Boiler".into(), "Basement".into(), "Pressure is dropping".into()));
        assert_eq!(state.orders[0].id, 1);
    }

    #[test]
    fn resolving_only_changes_the_matching_record() {
        let mut state = WorkOrderState::default();
        state.add("Boiler".into(), "Basement".into(), "Pressure is dropping".into());
        state.add("Window".into(), "Flat 2A".into(), "Latch will not close".into());
        state.resolve(1);
        assert!(state.orders[0].resolved);
        assert!(!state.orders[1].resolved);
        let before = state.clone();
        state.resolve(9999);
        assert_eq!(state, before);
    }
}

    Container(SafeArea(child: Scroll(child:

                ])

## Open a repair and update the same record

The detail route reads its ID from `RouteParams`, parses it, then looks up the record. A matching path alone is not proof that the work order exists. Missing and malformed IDs therefore show a not-found state rather than a default repair.

Opening a repair requests navigation; it does not also assign `current_path`. The shell route handler is the one place that updates that field. Consequently, an app button, browser Back and Android Back feed the same route state.

The record-specific actions below use explicit owned IDs. They do not capture a reference to a row from a completed build.

pub use state::{route_changed, WorkOrderState};

use fission::prelude::*;

fission_component! {
    pub WorkOrdersApp<WorkOrderState> {}
    view(_app, state, cx) {
        let missing = cx.tr("orders.not_found");
        let router = Router::<WorkOrderState>::new()
            .with_path(state.current_path.clone())
            .route_component("/", queue::WorkOrderQueue)
            .route_component("/work-orders/:id", detail::WorkOrderDetail)
            .not_found(move || Text::new(missing.clone()));
    } =>
        router
}

use fission::prelude::*;

use super::state::WorkOrderState;

#[fission_reducer(OpenOrder)]
pub fn open_order(state: &mut WorkOrderState, id: u64, cx: &mut ReducerContext<WorkOrderState>) {
    if state.orders.iter().any(|order| order.id == id) {
        cx.effects.navigate(format!("/work-orders/{id}"));
    }
}

#[fission_reducer(ResolveOrder)]
pub fn resolve_order(state: &mut WorkOrderState, id: u64) {
    state.resolve(id);
}

use fission::prelude::*;

use super::actions::{ResolveOrder, resolve_order};
use super::state::WorkOrderState;

fission_component! {
    pub WorkOrderDetail<WorkOrderState> {}
    view(_detail, state, cx) {
        let tokens = &cx.view.env().theme.tokens;
        let params = fission::build::read::<RouteParams>();
        let order = params.get("id")
            .and_then(|value| value.parse::<u64>().ok())
            .and_then(|id| state.orders.iter().find(|order| order.id == id));
    } =>
    Container(SafeArea(child: Scroll(child:
        Container(Column(gap: tokens.spacing.m, children: [
            Button(
                child: Text(cx.tr("orders.back")),
                key: "back-to-queue",
                variant: ButtonVariant::Outline,
                on_press: reduce { cx.effects.navigation_back(); },
            ).semantics_identifier("orders.back"),
            if let Some(order) = order {
                Column(gap: tokens.spacing.m, children: [
                    Text(order.title.clone()).size(tokens.typography.heading1_size),
                    Text(order.location.clone()),
                    Text(order.report.clone()),
                    Text(cx.tr(if order.resolved { "orders.resolved" } else { "orders.open" })),
                    Button(
                        child: Text(cx.tr("orders.resolve")),
                        key: "resolve-order",

                        on_press: with_reducer!(cx.build, ResolveOrder(order.id), resolve_order),

## Verify the system Back action on Android

The native shell already installs `app::route_changed`; there is no additional Android-only copy of the route logic. Test the installed app now, because a working browser history does not establish that the Android host is connected correctly.

```sh
cargo test
fission doctor android --project-dir .
fission devices --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

To select a particular emulator or phone, use its ID from `fission devices`:

```sh
fission run --target android --device <device-id> --project-dir .
```

Add two reports, open one, resolve it and press the Android system Back action. You should return to the queue with the changed status. Repeat using the visible Back button. At the initial queue, Back belongs to the shell's normal root-history behaviour; the app does not manufacture another queue route to trap the user.

Test `/work-orders/9999` and `/work-orders/not-a-number` as well. Both must show the not-found state, not a different report. A direct detail link has no preceding queue entry in history, so its Back behaviour can differ from opening that detail from the queue. Persistence and loading a repair by ID are separate requirements before promising that such links survive an app restart.

The Rust tests exercise validation, ID allocation and updating only the matching record. `fission test` checks host startup; it does not replace the manual Android Back checks.
