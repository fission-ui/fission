Riverside Property Services handles repairs across several apartment buildings. The coordinator needs to open a job, check where the problem is, mark it resolved, and get back to the queue. Android’s system Back action should do the same thing as the app’s own Back button. If those two routes behave differently, navigation will feel broken.

We’ll build that flow around three work orders. Fission’s `Router` selects the queue or a detail screen from the current path. `RouteParams` supplies the work-order ID, and a reducer marks the repair complete. The route handler also updates app state when Android changes the path through system Back. It is one route state shared by the UI and the shell, not a second navigation model just for Android.

## Build the maintenance queue

The coordinator needs to recognise a job before opening it, so each row shows its ID, location, priority, status, and reported problem. We’ll keep three records in memory for this tutorial. The important part is that the queue layout doesn’t own where those records come from; a service or database can replace them later.

`WorkOrderCard` presents one repair request. `WorkOrderList` counts the open and urgent jobs and keys each row by its work-order ID. That stable identity matters once the list changes: a row should remain attached to the same job, not whichever item happens to move into its old position.

## Open a work order and return with Android Back

Now make each row open its work order. The queue and detail screen are two routes in the same app, so `WorkOrderState` keeps the current path and `Router` builds the matching screen. `/work-orders/4201` carries the record ID. The detail route reads it from `RouteParams` and checks that the record exists before showing its details.

Marking a repair resolved goes through a reducer, so the queue and detail screen both read the same updated record. Opening a job pushes its route with `ctx.effects.navigate`. When Android Back changes the shell route, `with_route_handler` copies the new path into `current_path`; `Router` then builds the queue again. That is the key connection between native Back and the app’s own route state.

Replace `src/app.rs` with this version. The queue looks familiar, but its cards can now open typed detail routes, and the detail screen can update the repair status.

#[fission_reducer(OpenWorkOrder)]
pub fn on_open_work_order(
    state: &mut WorkOrderState,
    work_order_id: u32,
    cx: &mut ReducerContext<WorkOrderState>,
) {
    if state.work_orders.iter().any(|order| order.id == work_order_id) {
        let path = format!("/work-orders/{work_order_id}");
        state.current_path = path.clone();
        cx.effects.navigate(path);
    }
}

#[fission_reducer(MarkWorkOrderResolved)]
pub fn on_mark_work_order_resolved(state: &mut WorkOrderState, work_order_id: u32) {
    let Some(order) = state.work_orders.iter_mut().find(|order| order.id == work_order_id) else {
        return;
    };
    if order.status == WorkOrderStatus::Resolved {
        return;
    }
    order.status = WorkOrderStatus::Resolved;
    state.notice = Some(WorkOrderNotice::Resolved(order.id));
}

#[fission_reducer(BackToWorkOrders)]
pub fn on_back_to_work_orders(
    _state: &mut WorkOrderState,
    _work_order_id: u32,
    cx: &mut ReducerContext<WorkOrderState>,
) {
    cx.effects.navigation_back();
}

pub fn on_shell_route_changed(
    state: &mut WorkOrderState,
    action: fission::core::action::ShellRouteChanged,
    _cx: &mut ReducerContext<WorkOrderState>,
) {
    state.current_path = action.location.pathname;
}

## Connect the route handler to the Android shell

The components can render both routes now. There is one piece left: the app must hear about route changes that didn’t come from one of its buttons. Register `on_shell_route_changed` when creating the app. Android calls it after system Back, and it copies the new path into `WorkOrderState` so the next render gives `Router` the right route.

Put this setup in `src/lib.rs`. Leave the generated `src/main.rs` and `platforms/android/` files alone; they already handle starting and packaging the app.
