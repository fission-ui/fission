An app launch crosses a boundary that is easy to miss when developing the screen itself. Android draws the launcher icon and native splash before Fission can draw anything. A correct Compose screen therefore tells us nothing about whether the packaged launch assets are correct.

Here, we give a field-service app its launcher identity and a short native splash, then hand over to the visit screen. The screen has one real action: starting the visit. It remains usable in the browser, but the browser cannot verify Android resources.

## Create the project and add the target

Complete [Android SDK and NDK setup](/blog/set-up-rust-android-gui-development-with-fission/) and either [create an emulator](/blog/create-and-launch-a-fission-android-emulator/) or [connect a phone](/blog/run-a-fission-app-on-a-physical-android-phone/) first. Fission generates the host; the visit screen stays in shared Rust.

```sh
cargo install cargo-fission
fission init android-add-an-android-app-icon-and-native-splash-screen
cd android-add-an-android-app-icon-and-native-splash-screen
cargo add serde_yaml
fission add-target android --project-dir .
```

## Files created by Fission

This is the starter tree Fission generates. Keep shared app code in `src/`; the generated platform files handle native launch and packaging.

```text
android-add-an-android-app-icon-and-native-splash-screen/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── android/              # generated Android host
```

Keep the screen, shared state, reducers and reusable `fission_component!` components in the Rust project. Add a feature-specific state, service or effect module only when it gives the feature a useful boundary. The generated platform files handle native launch and packaging; shared components do not need to import platform APIs.

## Create the app screen

The native splash ends when the first frame is ready. That makes it unsuitable for onboarding or for showing progress on a network request. Our first frame is the visit arrival screen; starting a visit changes retained local state rather than holding the splash open.

Replace the generated `src/lib.rs` as well as `src/app.rs`. Otherwise `fission run --target android` would still launch the scaffold counter whilst the embedded Web preview showed a different app. The two shells below use the same screen and translation bundles.

pub mod app;
mod translations;

use app::VisitArrival;
use fission::prelude::*;

#[cfg(not(any(target_arch = "wasm32", target_os = "android", target_os = "ios")))]
pub fn run_desktop() -> anyhow::Result<()> {
    DesktopApp::<(), _>::new(VisitArrival::new())
        .with_env(translations::create_env())
        .run()
}

#[cfg(any(target_os = "android", target_os = "ios"))]
fn mobile_app() -> MobileApp<(), VisitArrival> {
    let app = MobileApp::<(), _>::new(VisitArrival::new())
        .with_env(translations::create_env());
    #[cfg(all(target_os = "android", debug_assertions))]
    let app = app.with_test_control_port(48761);
    app
}

#[cfg(any(target_os = "android", target_os = "ios"))]
pub fn run_mobile() -> anyhow::Result<()> {
    mobile_app().run()
}

#[cfg(target_os = "android")]
#[no_mangle]
fn android_main(app_handle: AndroidApp) {
    let _ = mobile_app().run_with_android_app(app_handle);
}

#[cfg(target_arch = "wasm32")]
#[wasm_bindgen::prelude::wasm_bindgen(start)]
pub fn run_web() -> Result<(), wasm_bindgen::JsValue> {
    console_error_panic_hook::set_once();
    WebApp::<(), _>::new(VisitArrival::new())
        .with_env(translations::create_env())
        .run()
        .map_err(|error| wasm_bindgen::JsValue::from_str(&error.to_string()))
}

use std::collections::HashMap;

use fission::prelude::*;

pub fn create_env() -> Env {
    let mut env = Env::default();
    env.locale = Locale::from("en-US");
    for (locale, source) in [
        ("en-US", include_str!("i18n/en-US.yaml")),
        ("es-ES", include_str!("i18n/es-ES.yaml")),
    ] {
        let messages: HashMap<String, String> =
            serde_yaml::from_str(source).expect("valid checked-in translations");
        env.i18n.add_bundle(TranslationBundle {
            locale: Locale::from(locale),
            messages,
        });
    }
    env
}

## Configure generated launcher assets and splash settings

Treat the Android launcher icon and native splash as separate assets. The icon may use adaptive foreground and background art; the splash is the short operating-system-owned frame shown before Fission starts. Configure the actual files in `fission.toml`, then run the Android package command and inspect the generated resources. Keep onboarding and loading progress in a Fission route after startup rather than stretching the native splash into an app screen. Force-stop and cold-launch an emulator to check icon cropping, splash contrast and the transition into the first frame.

```toml
[package.icons.android]
foreground = "assets/android/icon-foreground.png"
background = "assets/android/icon-background.png"

[app.splash]
image = "assets/android/splash-mark.png"
background_color = "#F8FAFC"
android_animated_icon = "assets/android/splash-animated.xml"
android_animation_duration_ms = 800
```

Create those asset files before packaging; the paths are project-relative and the animated icon must be an Android vector-drawable XML file, not an animated GIF or SVG. Omit `android_animated_icon` and `android_animation_duration_ms` when you only need the static splash image. Changing these paths does not create artwork for you.

The Web preview deliberately stays the same in this step. It is still the app's first frame, not an imitation of Android's splash.

## Check the launch experience on Android

Build and install the target package, then cold-launch it. Confirm the launcher icon uses the intended foreground and background, the native splash stays legible, and it hands off to the first Fission frame without showing a blank screen.

Repeat after changing the asset paths so you know the generated package picked up the new files. Keep onboarding and loading progress in the app’s first route; the operating-system splash is only a short launch frame.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Android tools, `fission run` launches the selected emulator or connected device, and `fission test` checks that the generated host can start. A release build checks packaging, but none of these commands proves a physical permission or hardware flow works.


### Emulator and connected-device commands
