This tutorial shows how to capture or scan an item, edit its record, attach a file and provide useful permission-denied paths. The runnable example uses shared Rust code and Fission’s fission_component! API, then checks the parts that need a real Android and iOS target. It assumes basic Rust syntax and explains app state, reducers and host work before using them.

## What you will build

You will build this workflow: capture or scan an item, edit its record, attach a file and provide useful permission-denied paths. The browser preview demonstrates the component and its state; it does not claim to run native permissions, sensors or device APIs. The final steps identify which checks need a real Android and iOS target.


### The Fission pieces in this example

A component describes a part of the screen. fission_component! declares that component, its inputs and any retained local interaction state. GlobalState holds product data or routes used beyond one component. A typed action names something that happened; a reducer applies the state change synchronously. When an operation needs a file, database, network or operating-system API, the reducer queues an effect or capability request and a later action reports success or failure. This keeps slow work out of the UI rendering path.


## Create the project and add the target

Install the Fission command line, create the app, and add its native target. The Android and iOS setup tutorials linked below cover their SDKs and device prerequisites.

```sh
cargo install cargo-fission
fission init mobile-build-a-mobile-inventory-workflow-with-camera-and-barcode-scanning
cd mobile-build-a-mobile-inventory-workflow-with-camera-and-barcode-scanning
fission add-target android ios --project-dir .
fission add-capability camera --project-dir .
```

## Final project layout

The commands generate the shared Rust entrypoints and the selected native host. Add the focused modules shown below as you implement the feature; keep file, database, network and operating-system work out of component conversion and queue it through reducers and asynchronous effects.

├── Cargo.toml                    # generated Rust dependencies
├── fission.toml                  # app identity, targets and capabilities
├── src/
│   ├── main.rs                   # generated desktop entrypoint

│   ├── components/
│   │   └── feature_screen.rs     # named, reusable presentation component
│   ├── effects/

│   └── services/
│       └── feature.rs            # typed host boundary when needed
├── platforms/

└── tests/
    └── feature_flow.rs           # reducer/provider and flow checks

`src/app.rs` is the shared Fission application, not a platform-specific copy. Put one reusable view in a named `fission_component!` component, keep app truth in `GlobalState`, and keep a one-screen draft or open flag in that component’s retained state. A reducer records the user’s intent; an effect, job, service or capability performs work after the view is built. Show pending, success, denied or failed outcomes in the screen.

The live preview compiles the complete `src/app.rs` component to WebAssembly. It lets you try retained state and normal or unavailable UI states in the browser. The preview does not call Android or iOS hardware. Use the target commands and device checks below to verify native behaviour.

## Implement the main Android and iOS workflow

Treat the preview action as a user intent. In the real app, send a typed action to a reducer and let the reducer update `GlobalState` or request an asynchronous effect. Keep the view function limited to reading state and composing widgets. For **Capture or scan an item, edit its record, attach a file and provide useful permission-denied paths**, work through these files in order:

1. In `src/state.rs`, define the product data and a status type with at least `Idle`, `Pending`, `Ready` and `Failed` variants. Keep durable records and active routes in `GlobalState`; keep only the current field draft or selected tab in local component state.
2. In `src/components/feature_screen.rs`, create a named `fission_component!` view. Give controls text labels, set a semantic label where an icon needs context, and make the primary action usable with keyboard, touch and an assistive technology action.
3. In `src/effects/feature.rs`, request slow or host-owned work after the reducer receives the action. Dispatch a typed success or error action when the effect completes. Do not block the UI thread, and attach a request id or revision when an older completion could overwrite a newer edit.
4. In `src/app.rs`, compose the screen with the state and reducer bindings. Render a pending message while work is running, the returned value on success, and a retry or alternate action on failure.


### Connect the Camera provider to the user action

This is the real Fission request path for this feature. Keep permission and hardware work outside the component view: the component dispatches one intent, the reducer queues the request, and success or error reducers store the returned result.

Start with task data and status in the app state. Keep a text-field draft, open flag or selected tab in the owning component instead of duplicating that temporary state here:

```rust
#[derive(Default)]
struct CameraDemoState {
    // Add these fields to your existing app state.
    profile_photo_stream: Option<DataStreamId>,
    camera_error: Option<String>,
    capturing: bool,
}

impl GlobalState for CameraDemoState {}
```

Handle successful and failed results separately so the screen can explain denied permission, cancellation, unsupported hardware and provider errors:

```rust
#[fission_reducer(PhotoCaptured)]
fn on_photo_captured(state: &mut CameraDemoState, capture: CameraCapture) {
    state.capturing = false;
    state.profile_photo_stream = Some(capture.stream);
    state.camera_error = None;
}

#[fission_reducer(PhotoCaptureFailed)]
fn on_photo_capture_failed(state: &mut CameraDemoState, error: CameraError) {
    state.capturing = false;
    state.camera_error = Some(error.message);
}
```

Queue the operation after the user presses the named control. The host completes asynchronously and dispatches the matching reducer:

```rust
state.capturing = true;
ctx.effects
    .camera()
    .capture_photo(CameraCaptureRequest {
        facing: CameraFacing::Back,
        resolution: Some(CameraResolution { width: 1280, height: 720 }),
        format: CameraImageFormat::Jpeg,
        flash: CameraFlashMode::Auto,
        quality: Some(90),
        ..Default::default()
    })
    .on_ok(ctx.effects.bind(
        PhotoCaptured(CameraCapture::default()),
        reduce_with!(on_photo_captured),
    ))
    .on_err(ctx.effects.bind(
        PhotoCaptureFailed(CameraError::default()),
        reduce_with!(on_photo_capture_failed),
    ));
```

Bind the user action from a reusable Fission component. Keep the visible label in the same control so it works with touch, keyboard and assistive technology:

```rust
fission_component!
{
    pub CaptureProfilePhotoButton<CameraDemoState> {
    }
    view(component, _state, _cx) => rust {
        let (ctx, view) = fission::build::current::<CameraDemoState>();
                let run = with_reducer!(ctx, CaptureProfilePhoto, on_capture_profile_photo);

                Button::new("Take photo")
                    .disabled(view.state().capturing)
                    .on_press(run)
                    .into()
    }
}
```

The [complete Camera guide](/docs/capabilities/camera/) explains configuration and expected platform behaviour. Test a successful memory-provider response and an unavailable or denied response before relying on the physical-device check below. The browser preview exercises the component state only; it does not invoke this native provider.

Keep platform-only code behind the generated target boundary or a typed provider; the shared component should describe the user task rather than call an operating-system API directly.

### Turn a scan into a safe inventory update

A scanner result is input, not a confirmed inventory change. Store the decoded SKU as a draft, look up the matching product asynchronously, and render the product name and current quantity before the user confirms. If the SKU is unknown, show a manual SKU field; if it already exists in the pending batch, focus the existing row instead of adding a duplicate. Only the Confirm action should dispatch the inventory update reducer. Test a known SKU, an unknown SKU, a duplicate scan, camera denial and manual entry with the camera provider unavailable.

## Handle errors, accessibility and target verification

Test the denied, unavailable or empty path as deliberately as the success path. In the browser preview, choose **Show an unavailable state** and confirm the message explains why the action cannot continue. In the native app, distinguish permission denial, cancellation, unsupported hardware and provider failure; offer a retry only when retrying can help.

Before publishing the screen, check it at a narrow phone width and a larger tablet or desktop width. Keep the primary action visible without horizontal scrolling, preserve readable focus order, and make status changes available to TalkBack or VoiceOver. For list screens, test an empty collection and give repeated stateful rows stable IDs based on durable record IDs.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

Expected result: `cargo test` runs the shared reducer and provider tests; `fission doctor` reports Android prerequisites; `fission run` launches the selected Android emulator or device; `fission test` checks its generated host; and the release build completes for that target. The separate iOS commands below check its simulator host. A host smoke check does not prove a physical permission or hardware flow works.

For iOS, use `fission package --project-dir . --target ios --format ipa --release` and install through Xcode Devices and Simulators. The iOS `fission run` path is simulator-only.
