## Create the project and add the target

Create a shared Rust app and add the iOS target. Fission generates the native host; keep the app behaviour in Rust.

```sh
cargo install cargo-fission
fission init ios-add-haptic-feedback-to-an-ios-app
cd ios-add-haptic-feedback-to-an-ios-app
fission add-target ios --project-dir .
fission add-capability haptics --project-dir .
```

## Files created by Fission

Fission creates this starter tree. Shared Rust code stays in `src/`; the generated host under `platforms/ios/` handles iOS launch and packaging.

```text
ios-add-haptic-feedback-to-an-ios-app/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── ios/                  # generated iOS host
```

Keep app behaviour in shared Rust. Add a feature module only when it creates a useful boundary, and keep iOS APIs behind the generated host.

## Confirm a completed inspection

Start with the technician finishing a compressor inspection. The screen records that inspection as complete; the next step adds a haptic response to the same action. The browser preview updates app state but cannot vibrate a device.

use fission::prelude::*;

fission_component! {
    pub WorkOrderScreen<()> {
        state {
            inspection_complete: bool = false,
        }
    }
    view(screen, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
        let step_status = if screen.inspection_complete {
            cx.tr("work.complete")
        } else {
            cx.tr("work.pending")
        };
        let button_label = if screen.inspection_complete {
            cx.tr("work.recorded")
        } else {
            cx.tr("work.mark")
        };
    } =>
    SemanticsRegion(
        identifier: Some("work-order-screen".to_string()),
        label: Some(cx.tr("work.title")),
        child: Container(
            Column(gap: tokens.spacing.m, children: [
                Text(cx.tr("work.site"))
                    .weight(tokens.typography.font_weight_bold),
                Text(cx.tr("work.title"))
                    .size(tokens.typography.heading2_size),
                Text(cx.tr("work.asset"))
                    .color(tokens.colors.text_secondary),
                Container(
                    Column(gap: tokens.spacing.s, children: [
                        Text(cx.tr("work.context")),
                        Text(step_status),
                    ])
                )
                .padding_all(tokens.spacing.m)
                .bg(tokens.colors.background)
                .border(tokens.colors.border, 1.0)
                .border_radius(tokens.radii.medium),
                Button(
                    child: Text(button_label),
                    key: "complete-compressor-inspection",
                    variant: ButtonVariant::Primary,
                    disabled: screen.inspection_complete,
                    on_press: reduce {
                        screen.inspection_complete = true;
                    },
                )
                .semantics_identifier("work-order.complete-inspection"),
            ])
        )
        .padding_all(tokens.spacing.l)
        .bg(tokens.colors.surface)
        .border(tokens.colors.border, 1.0)
        .border_radius(tokens.radii.large),
    )
}

## Run the Haptic operation through Fission

Keep host work out of component conversion. The button dispatches a typed action, its reducer queues the capability request, and separate completion reducers update the screen. The Web preview installs `MemoryHapticHost` and sends the same operation through Fission’s typed capability path. Its deterministic response is not a claim about device hardware, OS permission or native platform support.

The Web preview uses MemoryHapticHost and displays the completed request. It cannot produce a physical vibration.

use fission::prelude::*;

#[derive(Debug, Default)]
pub struct WorkOrderState {
    pub pending: bool,
    pub result: Option<String>,
    pub error: Option<String>,
}

impl GlobalState for WorkOrderState {}

#[fission_reducer(RunCapability)]
pub fn run_capability(state: &mut WorkOrderState, ctx: &mut ReducerContext<WorkOrderState>) {
    state.pending = true;
    state.result = None;
    state.error = None;

    let ok: ActionEnvelope = CapabilitySucceeded.into();
    let err: ActionEnvelope = CapabilityFailed.into();

    ctx.effects
        .haptics().notification(HapticNotificationRequest {
            kind: HapticNotificationKind::Success,
        })
        .on_ok(ok)
        .on_err(err);
}

#[fission_reducer(CapabilitySucceeded)]
pub fn capability_succeeded(
    state: &mut WorkOrderState,
    ctx: &mut ReducerContext<WorkOrderState>,
) {
    state.pending = false;
    state.error = None;
    state.result = ctx
        .input
        .capability_ok(HAPTIC_NOTIFICATION)
        .map(|value| "Success feedback request completed.".to_string());
    if state.result.is_none() {
        state.error = Some("The host completed without the expected typed result.".into());
    }
}

#[fission_reducer(CapabilityFailed)]
pub fn capability_failed(
    state: &mut WorkOrderState,
    ctx: &mut ReducerContext<WorkOrderState>,
) {
    state.pending = false;
    state.result = None;
    state.error = Some(ctx
        .input
        .capability_error(HAPTIC_NOTIFICATION)
        .map(|error| format!("{}: {}", error.code, error.message))
        .or_else(|| {
            ctx.input
                .capability_error_message(HAPTIC_NOTIFICATION)
                .map(str::to_owned)
        })
        .unwrap_or_else(|| "The host returned an error without details.".into()));
}

pub fn callback_registry() -> ActionRegistry<WorkOrderState> {
    let mut registry = ActionRegistry::new();
    registry.register(reduce_with!(capability_succeeded));
    registry.register(reduce_with!(capability_failed));
    registry
}

fission_component! {
    pub WorkOrderScreen<WorkOrderState> {}
    view(_screen, state, cx) {
        let tokens = &cx.view.env().theme.tokens;
        let action = with_reducer!(cx.build, RunCapability, run_capability);
        let status = if state.pending {
            cx.tr("work.waiting")
        } else if let Some(error) = &state.error {
            format!("{}: {error}", cx.tr("work.error"))
        } else if let Some(result) = &state.result {
            format!("{}: {result}", cx.tr("work.result"))
        } else {
            cx.tr("work.ready")
        };
    } =>
    SemanticsRegion(
        identifier: Some("work-order-haptic".to_string()),
        label: Some(cx.tr("work.title")),
        child: Container(
            Column(gap: tokens.spacing.m, children: [
                Text(cx.tr("work.site"))
                    .weight(tokens.typography.font_weight_bold),
                Text(cx.tr("work.title"))
                    .size(tokens.typography.heading2_size),
                Text(cx.tr("work.asset"))
                    .color(tokens.colors.text_secondary),
                Text(cx.tr("work.context")),
                Button(
                    child: Text(cx.tr("work.action")),
                    key: "run-capability",
                    variant: ButtonVariant::Primary,
                    disabled: state.pending,
                    loading: state.pending,
                    on_press: action,
                ),
                Container(Text(status))
                    .padding_all(tokens.spacing.m)
                    .bg(tokens.colors.background)
                    .border(tokens.colors.border, 1.0)
                    .border_radius(tokens.radii.medium),
            ])
        )
        .padding_all(tokens.spacing.l)
        .bg(tokens.colors.surface)
        .border(tokens.colors.border, 1.0)
        .border_radius(tokens.radii.large),
    )
}

## Verify the native request on iOS

The website preview cannot exercise the native provider. Build and launch this target on a supported emulator or device, then use the feature action from the component above. Check the result the host actually returns, including denial, cancellation or unsupported hardware where those outcomes apply.

Repeat with the feature unavailable, denied or cancelled, as applicable. Confirm the screen preserves the user’s existing data and offers the right recovery step. Use a physical device when the behavior depends on real hardware or an operating-system prompt.

### Run, test and build

```sh
cargo test
fission doctor ios --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
fission build --target ios --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Xcode, simulator SDK or Rust targets, `fission run` launches an iOS Simulator, and `fission test` checks that the generated host can start. A release build checks the simulator package; it does not verify iPhone signing or physical-device behavior.


### Simulator and device commands

Fission’s run command discovers iOS simulators. Run these checks from the generated project root:

```sh
fission doctor ios --project-dir .
fission devices --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
```


To verify a hardware-dependent path on an iPhone, configure development signing and Developer Mode, create a signed release IPA, then install it through Xcode Devices and Simulators:

```sh
fission package --project-dir . --target ios --format ipa --release
```

`fission run --target ios` remains simulator-only; it does not launch directly on a physical iPhone. A simulator preview cannot prove NFC, camera, biometrics or other physical capability behaviour.
