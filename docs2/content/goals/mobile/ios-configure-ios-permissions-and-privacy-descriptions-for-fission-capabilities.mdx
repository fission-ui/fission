A capability declaration, permission grant and completed operation are three different facts. A camera usage description lets iOS explain a request; it does not grant access, take a photograph or prove the app has a working provider.

We will implement a real camera-permission request beside an editable photo-caption draft. The draft remains useful when access is denied or restricted. No status will say a photo was attached merely because the operating system allowed the next step.

## Configure only the capability this app requests

Complete [iOS setup](/blog/set-up-rust-ios-development-with-fission/) first if needed.

```sh
cargo install cargo-fission
fission init ios-configure-ios-permissions-and-privacy-descriptions-for-fission-capabilities
cd ios-configure-ios-permissions-and-privacy-descriptions-for-fission-capabilities
fission add-target ios --project-dir .
fission add-capability camera --project-dir .
cargo add serde_yaml
```

Inspect `platforms/ios/Info.plist` and its `NSCameraUsageDescription`. The current CLI inserts a generic purpose string when the key is absent and preserves an existing key during capability synchronization. Replace that string with an accurate explanation for this app, keep the intended platform input under version control and inspect regeneration diffs. Do not invent a `fission.toml` privacy-description field which the current configuration does not expose.

For example, this permission-readiness screen can explain: "Camera access is requested when you choose to prepare a photo attachment." A production capture screen should describe the actual photograph's use, not imply every feature needs unrestricted access.

## Request access from the user's action

Keep the generated `src/main.rs` and add the shared files below. Both normal native and Web launchers use the real provider available to that target. The view never requests permission during conversion or automatically retries after denial.

A granted response is labelled as the last permission response, not a permanent promise about device state. Requesting again after a Settings change asks the host for its current result; it does not reuse an invented grant from app state.

use fission::prelude::*;

#[derive(Clone, Debug, PartialEq, Eq)]
pub struct PhotoAccessState {
    pub locale: Locale,
    pub pending: bool,
    pub permission: Option<CameraPermission>,
    pub status_key: String,
    pub error: Option<String>,
}

impl Default for PhotoAccessState {
    fn default() -> Self {
        Self {
            locale: Locale::from("en-US"),
            pending: false,
            permission: None,
            status_key: "photo.ready".into(),
            error: None,
        }
    }
}
impl GlobalState for PhotoAccessState {}

pub fn request_access(state: &mut PhotoAccessState, cx: &mut ReducerContext<PhotoAccessState>) {
    if state.pending {
        return;
    }
    state.pending = true;
    state.error = None;
    state.status_key = "photo.pending".into();
    let ok = cx
        .effects
        .bind(PermissionReturned, reduce_with!(permission_returned));
    let err = cx
        .effects
        .bind(PermissionFailed, reduce_with!(permission_failed));
    cx.effects
        .camera()
        .request_permission(CameraPermissionRequest { reason: None })
        .on_ok(ok)
        .on_err(err);
}

#[fission_reducer(PermissionReturned)]
fn permission_returned(state: &mut PhotoAccessState, cx: &mut ReducerContext<PhotoAccessState>) {
    state.pending = false;
    state.permission = cx.input.capability_ok(REQUEST_CAMERA_PERMISSION);
    state.status_key = match state.permission {
        Some(CameraPermission::Granted) => "photo.granted",
        Some(CameraPermission::Denied) => "photo.denied",
        Some(CameraPermission::Restricted) => "photo.restricted",
        Some(CameraPermission::Unknown) => "photo.unknown",
        None => "photo.unexpected",
    }
    .into();
}

#[fission_reducer(PermissionFailed)]
fn permission_failed(state: &mut PhotoAccessState, cx: &mut ReducerContext<PhotoAccessState>) {
    state.pending = false;
    let error = cx.input.capability_error(REQUEST_CAMERA_PERMISSION);
    state.status_key = if error
        .as_ref()
        .is_some_and(|error| error.code == "unsupported")
    {
        "photo.unsupported"
    } else {
        "photo.failed"
    }
    .into();
    state.error = error
        .map(|error| format!("{}: {}", error.code, error.message))
        .or_else(|| {
            cx.input
                .capability_error_message(REQUEST_CAMERA_PERMISSION)
                .map(str::to_owned)
        });
}

use fission::i18n::{Locale, TranslationBundle};
use fission::prelude::*;
use std::collections::HashMap;

pub fn create_env() -> Env {
    let mut env = Env::default();
    env.locale = Locale::from("en-US");
    for (locale, source) in [
        ("en-US", include_str!("../i18n/en-US.yaml")),
        ("es-ES", include_str!("../i18n/es-ES.yaml")),
    ] {
        let messages: HashMap<String, String> =
            serde_yaml::from_str(source).expect("valid photo access translations");
        env.i18n.add_bundle(TranslationBundle {
            locale: Locale::from(locale),
            messages,
        });
    }
    env
}

pub fn sync_env(state: &crate::app::PhotoAccessState, env: &mut Env) {
    env.locale = state.locale.clone();
}

## Map platform metadata without confusing it with provider support

The current generator uses these native inputs for declared capabilities. Add only those the application needs, not the whole list as a precaution.

| Declared capability | Generated iOS metadata or additional requirement |
| --- | --- |
| Camera or barcode scanner | `NSCameraUsageDescription` |
| Geolocation | `NSLocationWhenInUseUsageDescription` |
| Microphone | `NSMicrophoneUsageDescription` |
| Biometric | `NSFaceIDUsageDescription`; a description does not supply the currently missing native provider |
| Bluetooth | `NSBluetoothAlwaysUsageDescription`; a real iOS Bluetooth provider is separate |
| NFC | `NFCReaderUsageDescription` and NDEF reader entitlement; a real Core NFC provider is separate |
| Wi-Fi | Location purpose text and Wi-Fi-related entitlements; default iOS Wi-Fi operations remain unsupported |
| Passkeys | Product-specific Associated Domains/`webcredentials` configuration is separate; the capability command does not implement AuthenticationServices |
| Local notifications | No Info.plist usage-description key from this scaffold; notification authorization is a runtime request |
| Haptics or volume control | No iOS usage-description key from this scaffold; that does not imply every volume operation is implemented |

The Rust translation bundles localize this screen. They do not automatically localize iOS privacy-purpose strings or package `InfoPlist.strings` resources. Treat native prompt localization as a separate resource and packaging check rather than assuming the Spanish screen changes the operating system's purpose text.

Permission denial and restriction also have different recovery paths. An ordinary denial may be changed in Settings; a restriction may come from management or parental policy which the user cannot change in the app. Neither result should produce repeated automatic prompts or erase their work.

## Verify the prompt and the recovery path on iOS

```sh
fission doctor ios --project-dir .
fission devices --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
```

Use [the simulator guide](/blog/choose-boot-and-launch-an-ios-simulator-with-fission/) for selection and [the iPhone guide](/blog/install-a-fission-app-on-a-physical-iphone/) for signed-device qualification. Test a first request, denial, a later Settings change and an unavailable or restricted context where you can reproduce it. Do not record an untested restriction as a pass just because the enum has that variant.

The browser exercises its own permission policy, not iOS's Info.plist or entitlement enforcement. A launch smoke test does not interact with the prompt or listen to VoiceOver. Check both languages, the actual native prompt and whether the user can continue writing when access is unavailable.

For the next operation after permission, use [camera capture](/blog/capture-photos-and-use-the-flashlight-on-ios/). Keeping this step about permission makes its result precise; capturing, consuming and exporting image bytes is a separate task.
