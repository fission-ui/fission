## Create the project and add the target

Create the project and add the target used by this guide. Fission generates the native host; the app and its behaviour stay in shared Rust code.

```sh
cargo install cargo-fission
fission init android-route-android-app-links-and-deep-links-into-fission
cd android-route-android-app-links-and-deep-links-into-fission
fission add-target android --project-dir .
```

## Files created by Fission

This is the starter tree Fission generates. Keep shared app code in `src/`; the generated platform files handle native launch and packaging.

```text
android-route-android-app-links-and-deep-links-into-fission/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── android/              # generated Android host
```

Keep the screen, shared state, reducers and reusable `fission_component!` components in the Rust project. Add a feature-specific state, service or effect module only when it gives the feature a useful boundary. The generated platform files handle native launch and packaging; shared components do not need to import platform APIs.

## Accept a product URL and reduce it to route state

Deep links are inbound shell events, so there is no button that should parse a URL. Configure the schemes and domain at app startup, then turn the accepted link into a normal route in one reducer. Android still needs the matching intent filter or App Links verification, and iOS needs its URL scheme or Associated Domains configuration; check the generated platform README and domain association file before testing.

```rust
fn on_deep_link(state: &mut AppState, action: DeepLinkReceived) {
    let url = action.link.url;
    if let Some(id) = url.strip_prefix("fission://document/") {
        if !id.is_empty() {
            state.path = Some(format!("/documents/{id}"));
            state.route_error = None;
            return;
        }
    }
    state.route_error = Some("This document link is not recognised.".to_string());
}

let app = MobileApp::<AppState, _>::new(App)
    .with_deep_link_config(
        DeepLinkConfig::new()
            .scheme("fission")
            .domain("example.com")
            .path_prefix("/document"),
    )
    .on_deep_link(on_deep_link as fn(&mut AppState, DeepLinkReceived));
```

Use Fission `Router` and `RouterParams` to resolve the stored route. Test a cold launch and a link received while the app is open, then test an unrecognised document ID. The route component should render a useful missing-document state rather than constructing private content before access checks succeed.

## Test in-app and inbound routes on Android

Open the destination from inside the app, return to the previous screen, then open the same destination from its external URL. The external route should use the same typed route state as an in-app link rather than creating a second copy of the screen logic.

Try an unknown record ID and a malformed link as well as a valid one. The app should show a useful not-found or recovery screen, preserve unsaved work when required, and never render a blank route.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Android tools, `fission run` launches the selected emulator or connected device, and `fission test` checks that the generated host can start. A release build checks packaging, but none of these commands proves a physical permission or hardware flow works.


### Emulator and connected-device commands

Run these emulator checks from the generated project root:

```sh
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
```


For a real capability check, use an Android phone that has the required hardware and permission. Connect it with USB or Wi-Fi debugging, confirm its serial, then run the app on that device:

```sh
adb devices -l
fission run --target android --device <adb-serial> --project-dir .
```

An emulator can exercise the UI and memory-provider outcomes; it is not evidence that physical hardware or an OS permission flow works.
