## Create the project and add the target

Create the project and add the target used by this guide. Fission generates the native host; the app and its behaviour stay in shared Rust code.

```sh
cargo install cargo-fission
fission init ios-use-sql-transactions-and-migrations-in-an-ios-app
cd ios-use-sql-transactions-and-migrations-in-an-ios-app
fission add-target ios --project-dir .
fission add-capability storage --project-dir .
```

## Files created by Fission

This is the starter tree Fission generates. Keep shared app code in `src/`; the generated platform files handle native launch and packaging.

```text
ios-use-sql-transactions-and-migrations-in-an-ios-app/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── ios/                  # generated iOS host
```

Keep app state, reducers and components in shared Rust. Put direct iOS API calls in the generated host or a typed provider, and split a feature into modules when that boundary helps.

## Bind values and commit related writes together

Use named or positional SQL parameters for user data. A transaction keeps the item write and its audit record atomic; if any statement fails, SQLite rolls the whole transaction back:

```rust
let mut transaction = SqlTransaction::new();
transaction.execute(
    SqlStatement::new("UPDATE projects SET name = :name WHERE id = :id")
        .bind_named(":name", project.name.clone())
        .bind_named(":id", project.id),
);
transaction.execute(
    SqlStatement::new("INSERT INTO audit(message) VALUES (:message)")
        .bind_named(":message", "Project renamed".to_string()),
);

ctx.effects
    .sql()
    .transaction(transaction)
    .on_ok(ActionEnvelope::from(ProjectCommitted))
    .on_err(ActionEnvelope::from(DatabaseFailed));
```

Create ordered `SqlMigration` entries for schema changes, apply them with `ctx.effects.sql().migrate(...)`, and test opening both a fresh database and one created by the previous migration. Never concatenate user-entered values into an SQL string.

## Verify saved data on iOS

Save one change, close the app completely, and launch it again. The screen should load the saved value before presenting it as current. Test the empty database and an unreadable or incompatible database separately so loading, default and error states are not confused.

For SQL migrations, open both a fresh database and one created by the previous schema version. For offline workflows, disconnect the network, edit locally, reconnect, and confirm a failed or stale response does not erase the newer local change.

### Run, test and build

```sh
cargo test
fission doctor ios --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
fission build --target ios --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Xcode, simulator SDK or Rust targets, `fission run` launches an iOS Simulator, and `fission test` checks that the generated host can start. A release build checks the simulator package; it does not verify iPhone signing or physical-device behavior.


### Simulator and device commands

Fission’s run command discovers iOS simulators. Run these checks from the generated project root:

```sh
fission doctor ios --project-dir .
fission devices --project-dir .

```
