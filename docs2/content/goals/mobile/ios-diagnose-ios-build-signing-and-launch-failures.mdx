"iOS failed to launch" describes an outcome, not its cause. The app may never have compiled, its bundle may not have been assembled, signing may have been rejected or a successfully launched process may have crashed. Changing all those layers at once removes the evidence needed to tell them apart.

We will follow one real Compose app through those boundaries. Start at the earliest failing operation and keep its command, target and first useful error. A later summary line is not a reason to regenerate an unrelated host or expose signing material in a bug report.

## Start with the failing project

For an existing app, use its root and preserve its current state. Create a separate practice project only if you need a small candidate:

```sh
cargo install cargo-fission
fission init ios-diagnose-ios-build-signing-and-launch-failures
cd ios-diagnose-ios-build-signing-and-launch-failures
fission add-target ios --project-dir .
cargo add serde_yaml
```

Follow [iOS setup](/blog/set-up-rust-ios-development-with-fission/) for the toolchain. The diagnostic below is not a reason to initialize over an existing application or reset changes which may explain the failure.

## Give the candidate a useful interaction to verify

The journey editor from [the component tutorial](/blog/compose-an-ios-app-from-reusable-fission-widgets/) provides a small shared app with real text entry and snapshot behavior. Its normal `src/lib.rs` starts the same screen on native and Web targets. The browser launcher does not hide missing native wiring behind a sample work order.

Keep the generated `src/main.rs`. For your product, keep the actual failing core; this worked example is a separate control candidate, not a replacement which makes the problem disappear.

    state::{Journey, JourneyState},
    summary::JourneySummary,

fission_component! {
    pub JourneyScreen<JourneyState> {
        state {
            origin: String = String::new(),
            destination: String = String::new(),
        }
    }
    view(screen, state, cx) {
        let tokens = &cx.view.env().theme.tokens;
    } => SafeArea(
        child: Scroll(
            child: Container(Column(gap: tokens.spacing.m, children: [
                Text(cx.tr("journey.heading")).size(tokens.typography.heading2_size),
                Text(cx.tr("journey.explanation")),
                Row(gap: tokens.spacing.s, children: [
                    Button(
                        child: Text(cx.tr("language.english")), key: "english",
                        on_press: reduce { state.locale = Locale::from("en-US"); },
                    ),
                    Button(
                        child: Text(cx.tr("language.spanish")), key: "spanish",
                        on_press: reduce { state.locale = Locale::from("es-ES"); },
                    ),
                ]),
                FormControl(
                    label: Some(cx.tr("journey.origin")),
                    required: true,
                    child: TextInput(
                        value: screen.origin.clone(),
                        bind(on_input): to(screen.origin),
                    ),
                ),
                FormControl(
                    label: Some(cx.tr("journey.destination")),
                    required: true,
                    child: TextInput(
                        value: screen.destination.clone(),
                        bind(on_input): to(screen.destination),
                    ),
                ),
                if !screen.origin.trim().is_empty() && !screen.destination.trim().is_empty() {
                    Column(gap: tokens.spacing.s, children: [
                        Text(cx.tr("journey.draft")),
                        JourneySummary(
                            Journey {
                                origin: screen.origin.trim().to_owned(),
                                destination: screen.destination.trim().to_owned(),
                            },
                            key: "draft-summary",
                        ),
                    ])
                },
                Button(
                    child: Text(cx.tr("journey.prepare")), key: "prepare-journey",
                    disabled: screen.origin.trim().is_empty() || screen.destination.trim().is_empty(),
                    on_press: reduce {
                        state.prepared = Some(Journey {
                            origin: screen.origin.trim().to_owned(),
                            destination: screen.destination.trim().to_owned(),
                        });
                    },
                ),
                if let Some(journey) = &state.prepared {
                    Column(gap: tokens.spacing.s, children: [
                        Text(cx.tr("journey.prepared")),
                        JourneySummary(journey.clone(), key: "prepared-summary"),
                    ])
                },
            ]))
            .padding_all(tokens.spacing.l),
        ),
    )
}

use fission::i18n::{Locale, TranslationBundle};
use fission::prelude::*;
use std::collections::HashMap;

pub fn create_env() -> Env {
    let mut env = Env::default();
    env.locale = Locale::from("en-US");
    for (locale, source) in [
        ("en-US", include_str!("../i18n/en-US.yaml")),
        ("es-ES", include_str!("../i18n/es-ES.yaml")),
    ] {
        let messages: HashMap<String, String> =
            serde_yaml::from_str(source).expect("valid journey translations");
        env.i18n.add_bundle(TranslationBundle {
            locale: Locale::from(locale),
            messages,
        });
    }
    env
}

pub fn sync_env(state: &crate::app::JourneyState, env: &mut Env) {
    env.locale = state.locale.clone();
}

## Stop at the first boundary which fails

Check the toolchain before the app:

```sh
fission doctor ios --project-dir .
xcode-select -p
xcrun --sdk iphonesimulator --show-sdk-path
rustup target list --installed
```

If Xcode or its simulator SDK cannot be resolved, fix that selection before changing Rust application code. If the app reaches a Rust compile or linker error, keep the first diagnostic and use [the target/linker guide](/blog/fix-rust-ios-target-and-linker-mismatches/) when an archive or platform is incompatible.

```sh
fission build --target ios --project-dir .
fission devices --project-dir .
fission run --target ios --project-dir .
```

A successful compile does not establish successful bundle assembly or installation. Read the subsequent package, `simctl` and process output. Select a known simulator using [the simulator guide](/blog/choose-boot-and-launch-an-ios-simulator-with-fission/) rather than starting another build against an unknown destination.

If a simulator process starts and then exits, retain the attached runtime output. Do not call it a signing failure merely because signing is another iOS topic. Conversely, a rejected device installation has not reached the component whose layout you were about to debug.

## Treat device signing as its own path

The CLI's normal iOS run command targets the simulator. A physical iPhone needs a device build and signed IPA:

```sh
fission readiness package --project-dir . --target ios --format ipa --release
fission package --project-dir . --target ios --format ipa --release
```

Follow [the iPhone installation guide](/blog/install-a-fission-app-on-a-physical-iphone/) and [the TestFlight guide](/blog/package-and-prepare-a-fission-ios-app-for-testflight/) for the intended distribution path. Verify the bundle identifier, registered device, Developer Mode, selected identity and provisioning requirements as applicable. The simulator executable cannot become a device executable by being renamed.

Supply `IOS_SIGNING_IDENTITY` and the required provisioning profile through protected local or CI configuration. Do not commit private keys, certificates with private material, profiles or secret values, and do not paste their contents into an issue. Report the failing command, tool versions, target and a redacted diagnostic instead.

Once installation and launch work, repeat the real journey flow, both languages and keyboard interactions. The generated smoke test checks host launch/control health; it does not qualify product behavior or prove a future store submission will pass.

Keep these outcomes separate in your report: compiled, packaged, signed, installed, launched and interaction-checked. Doing so makes the next failure easier to locate without claiming that an earlier green step proved more than it did.
