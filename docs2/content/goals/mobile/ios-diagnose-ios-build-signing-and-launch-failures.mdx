## Create the project and add the target

Create a shared Rust app and add the iOS target. Fission generates the native host; keep the app behaviour in Rust.

```sh
cargo install cargo-fission
fission init ios-diagnose-ios-build-signing-and-launch-failures
cd ios-diagnose-ios-build-signing-and-launch-failures
cargo add serde_yaml
fission add-target ios --project-dir .
```

## Files created by Fission

Fission creates this starter tree. Shared Rust code stays in `src/`; the generated host under `platforms/ios/` handles iOS launch and packaging.

```text
ios-diagnose-ios-build-signing-and-launch-failures/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── ios/                  # generated iOS host
```

Keep app behaviour in shared Rust. Add a feature module only when it creates a useful boundary, and keep iOS APIs behind the generated host.

## Preview a real field-work screen

Use the same kind of task a technician would open on a phone: a named work order, location, due time, one clear inspection step and a status the user can change. The preview keeps that status in memory and lets you switch languages. It does not read a device sensor, call the SDK or prove that a native build, signature or package is valid; the target-specific steps below do that.

use std::collections::HashMap;

use fission::i18n::{Locale, TranslationBundle};
use fission::prelude::*;

pub fn create_env() -> Env {
    let mut env = Env::default();
    env.locale = Locale::from("en-US");

    for (locale, source) in [
        ("en-US", include_str!("../i18n/en-US.yaml")),
        ("es-ES", include_str!("../i18n/es-ES.yaml")),
    ] {
        let messages: HashMap<String, String> =
            serde_yaml::from_str(source).expect("valid Northbank translations");
        env.i18n.add_bundle(TranslationBundle {
            locale: Locale::from(locale),
            messages,
        });
    }

    env
}

## Diagnose iOS build, signing and launch failures

Work from the earliest failing stage so each check narrows the problem. `fission build --target ios` builds the Simulator host; it does not test iPhone signing. If the Simulator build fails, keep the first Xcode/Rust error and check `fission doctor ios`, the selected Xcode, and the installed Rust targets. If simulator launch fails after a successful build, check the selected simulator and its logs. For an iPhone install or launch failure, first create the signed IPA and verify the device's Developer Mode, provisioning profile, bundle identifier, and signing identity. Keep the failing command and first useful error; do not paste certificates, profiles, or signing secrets into a bug report.

## Narrow down the failing stage

```sh
fission doctor ios --project-dir .
rustup target list --installed | rg 'aarch64-apple-ios'
xcode-select -p
xcrun --sdk iphonesimulator --show-sdk-path
fission build --target ios --project-dir .
fission devices --project-dir .
fission run --target ios --project-dir .
```

`fission devices` and `fission run` operate on the iOS Simulator. For an iPhone IPA, check packaging prerequisites separately, then package it:

```sh
fission readiness package --project-dir . --target ios --format ipa --release
fission package --project-dir . --target ios --format ipa --release
```

IPA packaging requires `IOS_SIGNING_IDENTITY` and, by default, `IOS_PROVISIONING_PROFILE`. Supply those through a local secret store or CI secret variables, not a checked-in file. The package command's result is not proof that the app launches; install on a registered device through Xcode Devices and Simulators and inspect device logs if it still fails.
