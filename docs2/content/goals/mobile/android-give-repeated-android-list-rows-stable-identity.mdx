## Create the project and add the target

Create the project and add the target used by this guide. Fission generates the native host; the app and its behaviour stay in shared Rust code.

```sh
cargo install cargo-fission
fission init android-give-repeated-android-list-rows-stable-identity
cd android-give-repeated-android-list-rows-stable-identity
fission add-target android --project-dir .
```

## Files created by Fission

This is the starter tree Fission generates. Keep shared app code in `src/`; the generated platform files handle native launch and packaging.

```text
android-give-repeated-android-list-rows-stable-identity/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── android/              # generated Android host
```

Keep the screen, shared state, reducers and reusable `fission_component!` components in the Rust project. Add a feature-specific state, service or effect module only when it gives the feature a useful boundary. The generated platform files handle native launch and packaging; shared components do not need to import platform APIs.

```rust
use fission::prelude::*;

fission_component! {
    #[derive(Default)]
    pub TaskRow<()> {
        props {
            task_id: String,
            label: String,
        }
        state {
            complete: bool = false,
        }
    }
    view(row, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
    } =>
    Row(gap: tokens.spacing.m, children: [
        Text(row.label.clone()),
        Button(
            child: Text(if row.complete {
                cx.tr("rows.reopen")
            } else {
                cx.tr("rows.complete")
            }),
            key: format!("task-{}", row.task_id),
            handler: "toggle",
            on_press: reduce { row.complete = !row.complete; },
        ),
    ])
}

fission_component! {
    pub AndroidRepeatedListRowsStable<()>
    view(_preview, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
    } =>
    SemanticsRegion(
        identifier: Some("stable-list-example".to_string()),
        label: Some(cx.tr("rows.title")),
        child: Container(
            Column(gap: tokens.spacing.m, children: [
                Text(cx.tr("rows.title"))
                    .weight(tokens.typography.font_weight_bold),
                Text(cx.tr("rows.description")),
                for (task_id, label_key) in [("sensor", "rows.sensor"), ("photo", "rows.photo")] {
                    TaskRow(key: task_id, task_id: task_id.to_string(), label: cx.tr(label_key))
                },
                Text(cx.tr("rows.hint"))
                    .color(tokens.colors.text_secondary),
            ])
        )
        .padding_all(tokens.spacing.l)
        .bg(tokens.colors.surface)
        .border(tokens.colors.border, 1.0)
        .border_radius(tokens.radii.large),
    )
}
```

## Give repeated Android list rows stable identity

Give each retained row an ID derived from the record, for example `.id(WidgetId::explicit(&format!("record.{}", record.id)))`. `WidgetId::explicit` hashes the borrowed string immediately, so the temporary formatted value does not need to outlive the call. Never derive identity from the row index: filtering or sorting changes indices and can move a retained disclosure, selection or draft into another record. Keep the row's short-lived control state in its component and the actual record in `GlobalState`. Test by changing one row, filtering it out, inserting a record, sorting, then restoring the original list; the same record should keep its state throughout.

The component below is a browser-safe version of this screen. It uses Fission's retained component state and widgets to make the task visible; it does not call a native provider or operating-system API.

## Verify the user task on Android

On an Android emulator, repeat the feature path described above and check the expected result. If this task has an unavailable, denied or failure path, run that path too and confirm the screen offers a way to continue. The browser preview demonstrates component state only; the commands below verify the native host.

Use LiveTest with the semantic identifiers shown in the component to confirm focus and action behavior. If this screen adapts to window size, repeat the flow at a narrow phone width and a wider display.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Android tools, `fission run` launches the selected emulator or connected device, and `fission test` checks that the generated host can start. A release build checks packaging, but none of these commands proves a physical permission or hardware flow works.


### Emulator and connected-device commands

Run these emulator checks from the generated project root:

