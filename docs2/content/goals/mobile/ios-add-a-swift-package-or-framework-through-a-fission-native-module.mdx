A Swift package dependency and a Rust-callable capability are different boundaries. Fission can declare a package product in its generated Swift package and copy native source into it. Neither operation makes a Swift method appear in a Compose reducer.

This tutorial deliberately covers that dependency-wiring boundary, as its goal states. We will use a real package declaration rather than a fictitious scanner URL, inspect what the generator produces and keep the working Rust app independent of any unimplemented bridge.

## Create the project

Complete [iOS setup](/blog/set-up-rust-ios-development-with-fission/) if needed.

```sh
cargo install cargo-fission
fission init ios-add-a-swift-package-or-framework-through-a-fission-native-module
cd ios-add-a-swift-package-or-framework-through-a-fission-native-module
fission add-target ios --project-dir .
cargo add serde_yaml
```

For an existing product, add only a dependency it actually needs. The focused package below is a configuration example, not a recommendation to move ordinary collection work out of Rust.

                Text(cx.tr("journey.explanation")),

                    Button(

                        on_press: reduce { state.locale = Locale::from("en-US"); },
                    ),
                    Button(
                        child: Text(cx.tr("language.spanish")), key: "spanish",
                        on_press: reduce { state.locale = Locale::from("es-ES"); },
                    ),
                ]),
                FormControl(
                    label: Some(cx.tr("journey.origin")),
                    required: true,
                    child: TextInput(
                        value: screen.origin.clone(),
                        bind(on_input): to(screen.origin),
                    ),
                ),
                FormControl(
                    label: Some(cx.tr("journey.destination")),
                    required: true,
                    child: TextInput(
                        value: screen.destination.clone(),
                        bind(on_input): to(screen.destination),
                    ),
                ),
                if !screen.origin.trim().is_empty() && !screen.destination.trim().is_empty() {
                    Column(gap: tokens.spacing.s, children: [
                        Text(cx.tr("journey.draft")),

                        ),
                    ])
                },
                Button(
                    child: Text(cx.tr("journey.prepare")), key: "prepare-journey",

use fission::i18n::{Locale, TranslationBundle};
use fission::prelude::*;
use std::collections::HashMap;

pub fn create_env() -> Env {
    let mut env = Env::default();
    env.locale = Locale::from("en-US");
    for (locale, source) in [
        ("en-US", include_str!("../i18n/en-US.yaml")),
        ("es-ES", include_str!("../i18n/es-ES.yaml")),
    ] {
        let messages: HashMap<String, String> =
            serde_yaml::from_str(source).expect("valid journey translations");
        env.i18n.add_bundle(TranslationBundle {
            locale: Locale::from(locale),
            messages,
        });
    }
    env
}

pub fn sync_env(state: &crate::app::JourneyState, env: &mut Env) {
    env.locale = state.locale.clone();
}

## Declare a real product and inspect the generated package

Merge the following into the existing `fission.toml`:

```toml
[[native.modules]]
name = "algorithms-import-check"

[native.modules.ios]
source_dirs = ["native/ios/import-check/Sources"]

[[native.modules.ios.swift_packages]]
url = "https://github.com/apple/swift-algorithms"
product = "Algorithms"
from = "1.2.0"
```

Apple's [versioned package manifest](https://github.com/apple/swift-algorithms/blob/1.2.0/Package.swift) declares the `Algorithms` product. That release also depends on Swift Numerics, so this is not a dependency-free import. `from` is a minimum compatible version requirement, not an exact source pin; review the resolved package versions and their licenses for a real app.

Add a small native import check under the configured source directory:

```swift
// native/ios/import-check/Sources/PackageImportCheck.swift
import Algorithms

public enum PackageImportCheck {}
```

This is deliberately a qualification source, not a fake scanner implementation. A Swift compiler accepting that file would establish that the module is visible to that target. It would not establish an application feature or a call from Rust.

Regenerate/synchronize through the target command and inspect the package:

```sh
fission add-target ios --project-dir .
sed -n '1,180p' platforms/ios/NativeModules/Package.swift
swift package --package-path platforms/ios/NativeModules dump-package
```

The current generator writes a package dependency and an `Algorithms` product dependency into the `FissionNativeModules` target. It also copies configured Swift sources beneath `platforms/ios/NativeModules/Sources/FissionNativeModules`. Keep the original source directory as the authority; generated copies are not a second place to maintain the implementation.

## Do not promote manifest generation into runtime integration

The current simulator packaging path builds the Rust executable and assembles its bundle. Its success alone does not establish that a configured Swift package was compiled, linked into that executable or invoked. Qualify those steps explicitly in the native integration you supply.

```sh
fission doctor ios --project-dir .
fission build --target ios --project-dir .
fission run --target ios --project-dir .
```

Use [the native-module guide](/docs/build-and-package/native-modules/) and the generated host's README for the available integration boundary. A real asynchronous capability needs an owned request, a provider implementation, explicit completion/error delivery and a proven native linking path. Components should request that operation through effects; they should not store a build context or call blocking native work during conversion.

The `linked_frameworks` configuration field is currently accepted but not emitted as framework linker settings by this iOS package generator. Do not use it as evidence that a framework is linked. Adding a framework or a new bridge therefore needs separate implementation and qualification, not another unverified manifest entry.

Follow [the simulator guide](/blog/choose-boot-and-launch-an-ios-simulator-with-fission/) for launch and [the iPhone guide](/blog/install-a-fission-app-on-a-physical-iphone/) for the distinct device/signing path. Keep the final report precise: generated manifest, resolved dependency, compiled Swift, linked native code and exercised operation are separate outcomes. Only the first of those is the generator behavior demonstrated by this tutorial's configuration.
