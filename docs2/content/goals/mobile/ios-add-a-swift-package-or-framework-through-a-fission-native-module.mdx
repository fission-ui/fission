## Create the project and add the target

Create a shared Rust app and add the iOS target. Fission generates the native host; keep the app behaviour in Rust.

```sh
cargo install cargo-fission
fission init ios-add-a-swift-package-or-framework-through-a-fission-native-module
cd ios-add-a-swift-package-or-framework-through-a-fission-native-module
fission add-target ios --project-dir .
```

## Files created by Fission

Fission creates this starter tree. Shared Rust code stays in `src/`; the generated host under `platforms/ios/` handles iOS launch and packaging.

```text
ios-add-a-swift-package-or-framework-through-a-fission-native-module/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── ios/                  # generated iOS host
```

Keep app behaviour in shared Rust. Add a feature module only when it creates a useful boundary, and keep iOS APIs behind the generated host.

## Add a Swift package or framework through a Fission native module

Use a native module when an iOS SDK needs a Swift package product, linked framework or Swift source directory. Fission includes those inputs in the generated Xcode build, but it does not make Swift methods callable from Rust automatically. Read the vendor's iOS integration guide and `platforms/ios/README.md`, then describe the package and framework in `fission.toml`:

```toml
[[native.modules]]
name = "scanner-sdk"
path = "platforms/ios/scanner"

[native.modules.ios]
source_dirs = ["platforms/ios/scanner/Sources"]
linked_frameworks = ["AVFoundation.framework"]

[[native.modules.ios.swift_packages]]
url = "https://github.com/example/scanner-ios"
product = "ScannerSDK"
from = "1.2.3"
```

The package URL, product name and version are examples. Replace them with the vendor's values and confirm the package supports your deployment target. Keep the UI and product rules in shared Rust. If the SDK must return data to the Rust app, expose it through a typed host capability and request it from a reducer, so the same state and error handling can be previewed on Web. See the [native module guide](/docs/build-and-package/native-modules/) for the build boundary and the [iOS package guide](/docs/build-and-package/ios-packages/) for iOS-specific configuration.

## Confirm the native module is included in the iOS build

A successful Rust build does not prove the platform SDK was linked. Run the target build below and inspect its first native build output for the module name and dependency. Then launch the generated app on the target and exercise both a successful SDK result and the SDK’s documented error or cancellation path.

If Rust needs the SDK result, verify that the host returns it through the typed capability and that the reducer updates the visible state. A package declaration alone does not create that bridge.

### Run, test and build

```sh
cargo test
fission doctor ios --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
fission build --target ios --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Xcode, simulator SDK or Rust targets, `fission run` launches an iOS Simulator, and `fission test` checks that the generated host can start. A release build checks the simulator package; it does not verify iPhone signing or physical-device behavior.


### Simulator and device commands

Fission’s run command discovers iOS simulators. Run these checks from the generated project root:

```sh
fission doctor ios --project-dir .
fission devices --project-dir .
fission run --target ios --project-dir .
fission test --target ios --project-dir .
```
