## Create the project and add the target

Create a shared Rust app and add the iOS target. Fission generates the native host; keep the app behaviour in Rust.

```sh
cargo install cargo-fission
fission init ios-add-a-swift-package-or-framework-through-a-fission-native-module
cd ios-add-a-swift-package-or-framework-through-a-fission-native-module
cargo add serde_yaml
fission add-target ios --project-dir .
```

## Files created by Fission

Fission creates this starter tree. Shared Rust code stays in `src/`; the generated host under `platforms/ios/` handles iOS launch and packaging.

```text
ios-add-a-swift-package-or-framework-through-a-fission-native-module/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── ios/                  # generated iOS host
```

Keep app behaviour in shared Rust. Add a feature module only when it creates a useful boundary, and keep iOS APIs behind the generated host.

use std::collections::HashMap;

use fission::i18n::{Locale, TranslationBundle};
use fission::prelude::*;

pub fn create_env() -> Env {
    let mut env = Env::default();
    env.locale = Locale::from("en-US");

    for (locale, source) in [
        ("en-US", include_str!("../i18n/en-US.yaml")),
        ("es-ES", include_str!("../i18n/es-ES.yaml")),
    ] {
        let messages: HashMap<String, String> =
            serde_yaml::from_str(source).expect("valid Northbank translations");
        env.i18n.add_bundle(TranslationBundle {
            locale: Locale::from(locale),
            messages,
        });
    }

    env
}

## Add a Swift package through a Fission native module

Use a native module to add a Swift package product to the generated iOS host. Fission writes the package dependency into `platforms/ios/NativeModules/Package.swift`; `source_dirs` copies your Swift sources into that generated package. Neither step makes Swift methods callable from Rust. Read the vendor's iOS integration guide and `platforms/ios/README.md`, then declare the package in `fission.toml`:

```toml
[[native.modules]]
name = "scanner-sdk"

[native.modules.ios]
source_dirs = ["native/ios/scanner/Sources"]

[[native.modules.ios.swift_packages]]
url = "https://github.com/example/scanner-ios"
product = "ScannerSDK"
from = "1.2.3"
```

The URL, product name, version and source directory above are examples; replace them with paths and values from the package you actually use. The current iOS generator consumes `swift_packages` and `source_dirs`. Although `linked_frameworks` is accepted by the config type, the generated Swift package does not currently emit those framework links, so do not rely on that field to link a framework. This setup also does not generate a Rust-to-Swift bridge. If Rust needs data from the SDK, implement and test that boundary separately before wiring it into a reducer. See the [native module guide](/docs/build-and-package/native-modules/) for the build boundary and the [iOS package guide](/docs/build-and-package/ios-packages/) for iOS-specific configuration.

## Check the generated Swift package

A successful Rust build alone does not prove the Swift package resolved. Inspect the generated package after `fission build`; the command builds the iOS Simulator host. This verifies dependency resolution and compilation only, not SDK behavior or a Rust bridge.

```sh
fission doctor ios --project-dir .
fission build --target ios --project-dir .
sed -n '1,180p' platforms/ios/NativeModules/Package.swift
```

Then run the app in the simulator and exercise the Swift code you added from the generated host. The Northbank work-order browser preview exercises the shared Rust UI, not this native package; test the package integration from the generated host. Fission's current iOS `run` and `test` paths target the simulator; an iPhone IPA is a separate signed package workflow.
