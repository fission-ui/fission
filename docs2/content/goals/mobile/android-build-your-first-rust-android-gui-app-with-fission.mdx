Start with a value that is easy to see: a count that begins at zero. This tutorial builds a real `fission_component!` counter, then runs the same shared Rust app in the mobile target shell. The sections below explain why the count belongs to the component and what the native build adds.

## What you will build

You will create a counter that increments and resets, then run it on an Android emulator and a connected phone. The WebAssembly preview compiles the same `src/app.rs` component, so its buttons demonstrate the actual counter behavior. Use the target commands at the end to launch the native app.

### How the screen uses Fission

Throughout this guide, the screen is written as a `fission_component!`. That component owns its temporary interaction state and renders widgets from that state; a reducer changes it after a user action. Put durable facts shared across screens in `GlobalState`, and request native or service work through an effect or capability after the view is built.

## Create the project and add the target

Install the Fission command line, create the app, and add its native target. The [canonical Android setup tutorial](/blog/set-up-rust-android-gui-development-with-fission/) covers SDK installation and device prerequisites.

```sh
cargo install cargo-fission
fission init android-build-your-first-rust-android-gui-app-with-fission
cd android-build-your-first-rust-android-gui-app-with-fission
fission add-target android --project-dir .
```

## Files created by Fission

This is the starter tree after `fission init` and `fission add-target`; the component and state used for this task are additions in the steps below. Keep shared Rust behavior under `src/` and leave target launch and packaging in `platforms/android/`.

```text
android-build-your-first-rust-android-gui-app-with-fission/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── android/              # generated Android host
```

Keep `src/app.rs`, shared state, reducers and reusable `fission_component!` components in the common Rust project. Add a state, service or effect module only when this feature needs that boundary, and use a name tied to the feature. The generated Android host owns launch and packaging details; shared components describe the user task without importing Android APIs.

## Build the first Android screen

Start with a counter whose value begins at zero. The text label and count are visible without interaction, and the named Increase count and Reset counter buttons work with touch, keyboard and assistive technology. The retained count belongs in this component because it is only this screen’s temporary interaction state.

The complete root component below is the small interactive checkpoint used by the later steps. It reads Fission theme tokens and owns only the temporary state needed for this example.

<!-- fission:file path="src/app.rs" -->
```rust
use fission::prelude::*;

fission_component! {
    pub TutorialPreview<()> {
        props {
            title: String,
            step: String,
            goal: String,
        }
        state {
            count: u32 = 0,
        }
    }
    view(preview, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
    } =>
    SemanticsRegion(
        identifier: Some("counter-screen".to_string()),
        label: Some(preview.title.clone()),
        child: Container(
            Column(gap: tokens.spacing.m, children: [
                Text(preview.title.clone())
                    .size(tokens.typography.heading2_size)
                    .weight(tokens.typography.font_weight_bold),
                Text(preview.step.clone()).color(tokens.colors.text_secondary),
                Text(format!("Count: {}", preview.count)),
                Text(if preview.count == 0 {
                    "No count yet. Choose Increase count to begin.".to_string()
                } else {
                    format!("The counter has increased {} time(s).", preview.count)
                }),
                Button(
                    child: Text("Increase count".to_string()),
                    key: "counter-increment",
                    on_press: reduce { preview.count += 1; },
                ),
                Button(
                    child: Text("Reset counter".to_string()),
                    key: "counter-reset",
                    on_press: reduce { preview.count = 0; },
                ),
                Text(preview.goal.clone()).color(tokens.colors.text_secondary),
            ])
        )
        .padding_all(tokens.spacing.l)
        .bg(tokens.colors.surface)
        .border(tokens.colors.border, 1.0)
        .border_radius(tokens.radii.large),
    )
}
```

```rust
mod app;

use fission::prelude::*;
use wasm_bindgen::prelude::*;

#[wasm_bindgen(inline_js = "export function tutorial_title() { const parts = document.title.split(' — '); return parts.slice(1).join(' — ') || 'Fission tutorial'; } export function tutorial_step() { return document.title.split(' — ')[0] || 'Tutorial step'; } export function tutorial_goal() { return document.querySelector('meta[name=\"tutorial-goal\"]')?.content || 'Complete the task and verify it on the target.'; }")]
extern "C" {
    fn tutorial_title() -> String;
    fn tutorial_step() -> String;
    fn tutorial_goal() -> String;
}

#[wasm_bindgen(start)]
pub fn run() -> Result<(), JsValue> {
    console_error_panic_hook::set_once();
    let preview = app::TutorialPreview::new(tutorial_title(), tutorial_step(), tutorial_goal());
    WebApp::<(), _>::new(preview)
        .with_title("Fission tutorial preview")
        .mount("#fission-web-mount")
        .run()
        .map_err(|error| JsValue::from_str(&error.to_string()))
}
```

## Implement the main Android workflow

The counter belongs to one screen, so keeping its value in this component avoids adding unnecessary app-wide state. Each button has a stable key, and its reducer changes only the count. When the count changes, Fission rebuilds the view from the new value; the text and button labels then reflect the current state.

## Verify the user task on Android

Run the app on an ANDROID simulator and check that the count starts at zero, increases once per tap and returns to zero after Reset. Then connect a device and repeat the same short flow; this checks that the shared Rust component launches in the generated native host.

Use LiveTest with the `counter-screen` region and both named buttons to check focus and activation. Also rotate the simulator or resize its window to make sure the count and actions remain readable.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Android tools, `fission run` launches the selected emulator or connected device, and `fission test` checks that the generated host can start. A release build checks packaging, but none of these commands proves a physical permission or hardware flow works.


### Emulator and connected-device commands

The [Android SDK and NDK setup guide](/blog/set-up-rust-android-gui-development-with-fission/) is the single setup source. Check prerequisites and run the emulator with:

```sh
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
```


For a real capability check, use an Android phone that has the required hardware and permission. Connect it with USB or Wi-Fi debugging, confirm its serial, then run the app on that device:

```sh
adb devices -l
fission run --target android --device <adb-serial> --project-dir .
```

An emulator can exercise the UI and memory-provider outcomes; it is not evidence that physical hardware or an OS permission flow works.
