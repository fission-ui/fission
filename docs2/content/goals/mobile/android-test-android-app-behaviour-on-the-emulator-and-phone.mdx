## Create the project and add the target

Install the Fission command line, create the app, and add its native target.

```sh
cargo install cargo-fission
fission init android-test-android-app-behaviour-on-the-emulator-and-phone
cd android-test-android-app-behaviour-on-the-emulator-and-phone
fission add-target android --project-dir .
```

## Files created by Fission

This is the starter tree after `fission init` and `fission add-target`; the component and state used for this task are additions in the steps below. Keep shared Rust behavior under `src/` and leave target launch and packaging in `platforms/android/`.

```text
android-test-android-app-behaviour-on-the-emulator-and-phone/
├── Cargo.toml                 # Rust package and dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                # generated app entrypoint
│   ├── lib.rs                 # shared app setup
│   └── app.rs                 # shared Fission screen
└── platforms/
    └── android/              # generated Android host
```

Keep `src/app.rs`, shared state, reducers and reusable `fission_component!` components in the common Rust project. Add a state, service or effect module only when this feature needs that boundary, and use a name tied to the feature. The generated Android host owns launch and packaging details; shared components describe the user task without importing Android APIs.

## Test Android app behaviour on the emulator and phone

Use three different checks for three different risks: cargo test for Rust reducers and state rules, fission test --target android for the generated host smoke path, and a focused LiveTest against the running shell for a user journey. Then use a physical device only for behaviour that depends on the real sensor, permission prompt, radio or signed install. Keep the tested scenario and target version in the result; a passing smoke test must not be reported as proof that hardware behaviour works.

## Run the test layers for this task

Use a different check for each risk: `cargo test` for Rust rules you have written, `fission test` for the generated host smoke path, and LiveTest for the composed screen and user journey. A passing test at one layer does not replace the checks at the next layer.

Run the same critical journey on Android Emulator and iOS Simulator. Add a real-device check only for behavior the simulator cannot prove, such as a permission sheet, radio, camera, sensor or signed installation.

### Run, test and build

```sh
cargo test
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
fission build --target android --project-dir . --release
```

`cargo test` runs Rust tests you add; the generated scaffold does not create feature-specific tests. `fission doctor` reports missing Android tools, `fission run` launches the selected emulator or connected device, and `fission test` checks that the generated host can start. A release build checks packaging, but none of these commands proves a physical permission or hardware flow works.


### Emulator and connected-device commands

Run these emulator checks from the generated project root:

```sh
fission doctor android --project-dir .
fission run --target android --project-dir .
fission test --target android --project-dir .
```


For a real capability check, use an Android phone that has the required hardware and permission. Connect it with USB or Wi-Fi debugging, confirm its serial, then run the app on that device:

```sh
adb devices -l
fission run --target android --device <adb-serial> --project-dir .
```

An emulator can exercise the UI and memory-provider outcomes; it is not evidence that physical hardware or an OS permission flow works.
