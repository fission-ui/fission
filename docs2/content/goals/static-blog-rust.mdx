An article index, its search results and the article itself should not disagree about what was published. Keeping one copy of a post in Markdown and another in a Rust preview record makes that disagreement likely.

We will build Field Journal from authored Markdown files. The Static site shell generates the articles, archives and taxonomy routes from those same files. Compose supplies the custom homepage; the existing blog template supplies the reading interface. Every preview below is the actual generated site, including its navigation.

## Create the project

```sh
cargo install cargo-fission
fission init field-journal --template website
cd field-journal
cargo add serde_yaml
```

Keep the generated launcher, which calls `field_journal::build_site()`, and replace the modules and configuration shown below. Use your real origin before publishing: the example.com address is deliberately not a live publication.

<!-- fission:step id="journal-index" -->
## Publish the writing before adding an archive interface

Each content file owns a title, search description, taxonomy and complete body. The dated filename supplies its initial route. The examples are authored sample articles, not an in-memory fixture substituted for the published content.

The shell's current front-matter parser does not consume an authors field. Put a byline in the Markdown body if needed; do not promise an author filter that the template does not implement. The translation bundles below cover the custom homepage only, not a translated edition of every article.

pub mod home;
mod translations;
pub fn site_app() -> fission::site::FissionSite {
    fission::site::FissionSite::new().with_env(translations::create_env())
        .route_widget::<(), _>("/", "Field Journal",
            Some("Practical notes about building and maintaining small software projects.".into()),
            home::JournalHome::new())
}
pub fn build_site() -> anyhow::Result<()> {
    fission::site::build_from_cli(site_app())
}

```rust
use fission::i18n::{Locale, TranslationBundle};
use fission::prelude::*;
use std::collections::HashMap;
pub fn create_env() -> Env {
    let mut env = Env::default();
    env.locale = Locale::from("en-US");
    for (locale, source) in [
        ("en-US", include_str!("../i18n/en-US.yaml")),
        ("es-ES", include_str!("../i18n/es-ES.yaml")),
    ] {
        let messages: HashMap<String, String> =
            serde_yaml::from_str(source).expect("checked-in translations must be valid YAML");
        env.i18n.add_bundle(TranslationBundle { locale: Locale::from(locale), messages });
    }
    env
}
```

# Keep an article at a stable address

An article can be reached through a shared link, a search result or its archive. Those routes should identify the same piece of writing. A title copied into a separate Rust record becomes another value an editor has to remember to change.

## Keep content together
Put the title, description and body in one Markdown file. Use the description to state the question the article answers, not a second unrelated marketing claim. Its public URL then gives another writer a stable place to link.

## Change the structure carefully
A filename-based route can change when the file is renamed. Before reorganising a published archive, record the old URL and arrange an explicit redirect. A fresh sitemap is useful discovery information, but it does not repair someone else's saved link.

[The revision note](../2026-09-11-corrections/) explains what to record when the advice itself changes.

# Search the words a reader can remember

A reader may remember a problem without remembering its headline. Search needs enough meaningful content to connect that question to the article. Filling descriptions with repeated terms makes the result harder to judge.

## Try more than the headline
Search for a term from the explanation, then one from a heading. Open the returned route and check that it contains the answer, rather than merely repeating the query.

## Keep the article reachable
Search is one way into the archive. Category links, article links and direct URLs should remain usable when the search script cannot run. That separates the reading path from an optional discovery enhancement.

# Record what changed in a correction

Publication starts an article's maintenance period. Dependencies change and an example that once worked can become misleading. Replacing the text without an explanation leaves a returning reader unable to distinguish a correction from their own mistake.

## State the correction
Name the behaviour that was wrong, what now happens and whether readers need to act. Keep the original publication date distinct from a later review date.

## Preserve the route
A correction is normally still the same article. Keep its address and link to a replacement when advice has been retired. [Stable article addresses](../2026-09-18-markdown-to-pages/) explain the navigation consequence.

# Write a plan someone can review

A plan is useful when another person can tell what should happen next. A broad ambition such as “improve support” may be reasonable, but it is not enough to coordinate today's work.

## Name the result
Write “publish the handover guide reviewed by support”. That identifies an output and a reviewer. It does not prescribe every implementation detail.

## Identify the next action
Ask support which questions are missing. When that action is complete, replace it with the next decision rather than allowing this small record to become another backlog.

# Distinguish a failed request from a rejected write

A client can lose a response after a server has committed a change. Showing “nothing was saved” in that case claims knowledge the client does not have. Automatically repeating the request may create a duplicate.

## Preserve the user's input
Keep the draft while explaining that the outcome is uncertain. Reload the authoritative record before deciding whether another write is needed.

## Design a retry contract
If an operation needs safe automatic retries, define its identity and deduplication behaviour on the server. A spinner or retry button cannot establish that guarantee by itself.

---

# Write release notes for an upgrade decision

Someone reading release notes is usually deciding whether to upgrade and what the upgrade will require. A list of internal changes forces them to reconstruct the consequence.

## Put required actions first
Name a changed default, renamed setting or migration next to the command or edit needed. Separate those changes from improvements that require no action.

## Describe the result
A fix should identify the behaviour that changed and who encountered it. Avoid calling a release “more reliable” when the evidence only establishes one corrected failure path.

description: Why an edit that must survive filtering cannot depend only on a mounted row.
categories: [Rust guides]
tags: [state, identity]
show_adjacent_posts: true
---

# Put a draft where its lifetime belongs

A row's local state is useful while that row remains mounted. Filtering can remove the row entirely. Giving it a stable key does not, by itself, promise to preserve state after unmounting.

## Decide what must survive
If the user expects an unfinished note to return after clearing a filter, store the draft with the record ID in application state. Let the row observe and edit that value through reducers.

## Keep the boundary small
Hover state or an isolated open disclosure can remain local. The choice follows the information's lifetime and ownership, rather than a rule that all mutable values belong in one global structure.

## Make discovery output an explicit publishing responsibility

Fission generates the sitemap and robots file, but it does not generate an RSS feed. Copying feed.xml is not the same as keeping its entries up to date. This small feed deliberately includes one recent article; update it as part of the publication review, or add a separate generator with an explicit source contract later.

The page's RSS link and the copied feed are real outputs. Use canonical public URLs in the feed, not the local preview address. The adjacent-post flag on each article supplies real previous/next links; no selected_story field is involved.

## Inspect the publication

```sh
fission site build --project-dir .
fission site check --project-dir .
fission site routes --project-dir .
fission site serve --project-dir . --port 8123
curl http://127.0.0.1:8123/blog/2026-09-18-markdown-to-pages/
```

Inspect the article's title, description and body in the returned HTML. Check `dist/site/blog/page/2/index.html`, `dist/site/feed.xml` and `dist/site/sitemap.xml`. A successful build does not establish a useful archive: check long titles, code overflow and article line length at phone and desktop widths before publishing.

The feed is the one deliberate duplication in this small project. Treat its update as a review item rather than claiming that copying an asset synchronises it with Markdown.
