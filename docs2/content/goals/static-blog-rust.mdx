Build **Field Journal**, a small publication for practical Rust, product craft and the decisions that make software easier to use. A reader should be able to discover an article, understand what it covers before opening it, browse a topic, read the full post and continue when they reach the end.

We will keep article content in dated Markdown files and let Fission generate static article, category and tag routes. The journal interface in this tutorial uses named `fission_component!` components, so search, filters, pagination and article navigation all have working behavior. Its sample articles stay in memory for the interactive lesson; the production content route renders the authored files into crawlable pages before deployment.

## Create the site project

Use the website template to generate the site shell, then keep each concern in a small module. The compiled lesson app under `preview/` is a browser harness; copy the `src/` files into the generated project and keep the generated site entry point and `fission.toml` as the production shell.

The static-site shell owns route generation and page metadata. The components in `src/` own the journal experience. Keeping those boundaries clear means an editor can improve an article without changing its card layout, and the same article metadata can feed the index, taxonomy pages and sitemap.

### Mount the blog collection

Merge these settings into the template's existing `[site]` table. `base_url` lets Fission write absolute sitemap entries; `asset_dirs` copies the manually maintained feed into the final site. The blog content route creates an index, paginated archive pages, category and tag pages, and individual article URLs from the files in `content/blog/`.

## Give the journal a real front page

Start with the parts a reader needs before they choose a story: a publication identity, an editorial pick, a clear article list and enough information to judge each result. Field Journal has six articles across Rust guides, product design and field notes. Each card shows its title, category, summary, author, date and reading time; “Read story” opens the matching article instead of acting as a decorative button.

The `JournalStory` record keeps those fields together. `JournalState` holds only the selected article ID because both the card and article reader need to update or read that choice. Search and filter controls will belong to the page component in the next step, since they are temporary choices for this one view.

## Help readers find and browse stories

A journal becomes hard to use when its archive grows. Add a search field that checks the title, summary, category, author and tags, then add category filters for the three sections Field Journal publishes. The result count tells the reader how much the controls narrowed the archive, and the empty state leaves the search term visible with one action that restores all stories.

The search string, active category and page number are local state on `FieldJournal`: they are presentation choices, not durable article data. Changing category returns to page one. Search can make a previously selected page unavailable, so the view clamps the displayed page to the current result count. The previous/next actions repeat that calculation in their reducer, keeping the visible page valid even when the query changes.

Each story card uses its stable article ID as its key. If a search or category change reorders the list, Fission can still associate a rendered card with the same article instead of treating its position as its identity.

pub fn matches_story(story: &JournalStory, query: &str, category: &str) -> bool {
    let query = query.trim().to_lowercase();
    let matches_query = query.is_empty()
        || story.title.to_lowercase().contains(&query)
        || story.summary.to_lowercase().contains(&query)
        || story.author.to_lowercase().contains(&query)
        || story.category.to_lowercase().contains(&query)
        || story
            .tags
            .iter()
            .any(|tag| tag.to_lowercase().contains(&query));
    let matches_category = category == "All stories" || story.category == category;

    matches_query && matches_category
}
