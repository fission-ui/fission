We will build **Field Journal**, a small publication about Rust, product craft, and making software easier to use. Readers can find a story, see what it covers, browse a topic, read the full article, and move on to another one.

Article content lives in dated Markdown files. Fission generates the article, category, and tag routes. The journal interface uses named `fission_component!` components, so search, filters, pagination, and article navigation work in the lesson preview. Those sample stories stay in memory; the production content route renders the authored files into crawlable pages.

## Create the site project

Start with the website template and keep each part in a small module. The compiled app under `preview/` is only a browser harness for the lesson. Copy the `src/` files into the generated project, but keep its generated site entry point and `fission.toml` as the production shell.

The Static site shell generates routes and page metadata; the components in `src/` build the journal experience. Keep those jobs separate. An editor can then change an article without touching its card layout, and the same metadata can drive the index, category pages, tag pages, and sitemap.

### Mount the blog collection

Add these settings to the template's `[site]` table. `base_url` gives Fission the full URL for sitemap entries; `asset_dirs` copies the feed into the built site. The blog route creates the index, paginated archives, category and tag pages, and article URLs from `content/blog/`.

## Give the journal a real front page

Show readers what they need to choose a story: the publication name, a featured article, and a list with enough information to judge each result. Field Journal has six stories about Rust, product design, and field notes. Each card shows the title, category, summary, author, date, and reading time. “Read story” opens that article.

The `JournalStory` record keeps each article's fields together. `JournalState` stores the selected article ID because both the card and reader need it. Search and filter settings belong to the page component: they are temporary choices for this view, not article data.

#[derive(Clone, Debug, PartialEq)]
pub struct JournalState {
    pub selected_story: Option<u32>,
}

impl Default for JournalState {
    fn default() -> Self {
        Self {
            selected_story: None,
        }
    }
}

impl GlobalState for JournalState {}

#[fission_reducer(SelectJournalStory)]
pub fn on_select_journal_story(state: &mut JournalState, story_id: Option<u32>) {
    state.selected_story = story_id;
}

## Help readers find and browse stories

As the archive grows, readers need a way to narrow it down. Search the title, summary, category, author, and tags, then add filters for the three Field Journal categories. Show the result count. If nothing matches, keep the search term visible and offer one action to restore all stories.

The search string, selected category, and page number are local state on `FieldJournal`. They affect this view, not the articles. Changing the category returns to page one. A search can also remove results from the current page, so clamp the displayed page to the available results. The previous and next reducers use the same rule.

Use the article ID as each card's key. When a search or category filter changes the list, Fission can keep each card attached to its article instead of its old position.

pub fn matches_story(story: &JournalStory, query: &str, category: &str) -> bool {
    let query = query.trim().to_lowercase();
    let matches_query = query.is_empty()
        || story.title.to_lowercase().contains(&query)
        || story.summary.to_lowercase().contains(&query)
        || story.author.to_lowercase().contains(&query)
        || story.category.to_lowercase().contains(&query)
        || story
            .tags
            .iter()
            .any(|tag| tag.to_lowercase().contains(&query));
    let matches_category = category == "All stories" || story.category == category;

    matches_query && matches_category
}
