You are opening the stockroom at Harbour Supply in Troutdale. A delivery can only be put away safely when the receiver can identify the exact product, confirm its storage bin and compare the new count with the reorder point. A name alone is not enough: two products may come from the same supplier, and a misplaced box can leave the shelf empty even when the total warehouse count looks healthy.

We will build the screen the receiving team uses to check those details and record units as they arrive. The catalogue starts with five outdoor-shop products, with three products to review: the camp stove is out of stock and two others are below their reorder points. Search accepts a product name, SKU, category, supplier or bin. A receipt updates the selected product, the warehouse total and the reorder summary together; zero, invalid or overflowing quantities leave the stored count untouched and explain why.

All catalogue data stays in memory so you can see each state change immediately without configuring a service. The tutorial will show where the reducer owns inventory truth, where the dashboard keeps its temporary search and receipt fields, and what must move behind an asynchronous persistence boundary in a production app.

## Create the server-rendered project

Install the Fission command line tool if it is not already on your machine, then create an SSR project. The generated shell gives the site a server-rendered entry point; the dashboard itself stays in shared Rust code.

## Start with a useful stock catalogue

Before the receiver changes a count, the screen needs to make each product unmistakable. At Harbour Supply, the SKU is the reliable identifier; the product name, supplier and bin help the person match that record to the label on a carton or shelf. The row also shows the current quantity next to its reorder point, so “Reorder soon” has a visible reason instead of relying on colour alone.

We will put those details in `InventoryProduct` and render a row from each record. Unit cost is stored as cents rather than a floating-point number. That keeps money exact in Rust: 1,800 cents is always eighteen dollars, and formatting only happens when we display it.

## Find products and record stock receipts

When the delivery arrives, the receiver may know only the supplier name or the bin printed on a shelf label. The search field checks the product name, SKU, category, supplier and bin, and the stock filters help staff focus on the products that need a decision. “Needs reorder” compares the available quantity with the visible threshold; “Out of stock” is narrower and shows only a zero count.

For this first interaction, the row’s receive action adds five units. It is attached to the named product row, so the reducer receives that SKU’s product ID and cannot accidentally update a different item. In the next step we will let the receiver enter the amount from the packing slip and reject invalid quantities before any stock changes.

use crate::models::{sample_products, InventoryProduct};
use fission::prelude::*;

#[derive(Clone, Debug, PartialEq)]
pub struct InventoryState {
    pub products: Vec<InventoryProduct>,
    pub feedback: String,
    pub feedback_is_error: bool,
}

impl Default for InventoryState {
    fn default() -> Self {
        Self {
            products: sample_products(),
            feedback: "No stock receipt has been recorded yet.".to_string(),
            feedback_is_error: false,
        }
    }
}

impl GlobalState for InventoryState {}

#[fission_reducer(ReceiveStock)]
pub fn on_receive_stock(state: &mut InventoryState, product_id: u32, quantity: u32) {
    let result = if quantity == 0 {
        Err("Enter a whole number greater than zero before receiving stock.".to_string())
    } else if let Some(product) = state
        .products
        .iter_mut()
        .find(|product| product.id == product_id)
    {
        match product.stock.checked_add(quantity) {
            Some(next_stock) => {
                product.stock = next_stock;
                Ok(format!(
                    "Received {} units of {} ({}). Bin {} now holds {} units.",
                    quantity, product.name, product.sku, product.bin, next_stock
                ))
            }
            None => Err(format!(
                "The receipt for {} is too large. Stock was not changed.",
                product.sku
            )),
        }
    } else {
        Err("This product is no longer in the catalogue. Stock was not changed.".to_string())
    };

    match result {
        Ok(message) => {
            state.feedback = message;
            state.feedback_is_error = false;
        }
        Err(message) => {
            state.feedback = message;
            state.feedback_is_error = true;
        }
    }
}

## Validate receipts and make empty results recoverable

A receiving clerk should be able to use the count on the packing slip rather than accept a fixed quantity. The dashboard keeps the receipt field local because it is only a draft for this screen; when the receiver presses Receive, the action sends a parsed number and product ID to `on_receive_stock`. The reducer rejects zero and checks for integer overflow before it writes. On an error, the previous stock total stays intact and the message says what the receiver can correct.

Search can also produce an empty list when someone enters a partial SKU or supplier that is not in this warehouse. An empty result should explain that the filters caused it and provide one action to restore the whole catalogue. Clearing the view changes only search and filter state, so earlier receipts remain visible in the product count and reorder summary.

Product records belong in `GlobalState` because the summary cards, reorder notice and visible rows all depend on the same stock values. Search, the active filter and the current receipt quantity are local to the dashboard; they are temporary view choices, not warehouse facts. When the reducer accepts a receipt, every part of the screen derives from the updated product list. When it rejects a receipt, no count changes.

The example resets to its starting products when the page reloads. A production version would load inventory from a service and write receipts through an asynchronous effect, displaying a pending state until that service confirms or rejects the movement. The same product ID and quantity validation can stay in the domain action, while the service boundary owns persistence and network errors.
