A warehouse team needs more than a list of product names. Before placing an order or packing a shipment, staff need to know which item they are handling, where it is stored, how many units remain and when the team should reorder it.

In this tutorial, you will build a Rust inventory dashboard for a small outdoor shop. It starts with four recognisable products, then gains search, stock filters and actions for receiving goods and recording a sale. The sample catalogue stays in memory so we can focus on the screen and its state transitions. At the end, we will trace where persistent storage belongs when the dashboard connects to a real inventory service.

The page uses an `InventoryProduct` model and a `ProductInventoryDashboard` component. The component owns search text and filter selection because those values only affect this screen. Stock changes are explicit actions, and the interface always shows quantities and reorder points as text so status does not depend on colour alone.

## Create the server-rendered project

Install the Fission command line tool if it is not already on your machine, then create an SSR project. The generated shell gives the site a server-rendered entry point; the dashboard itself stays in shared Rust code.

## Start with a useful stock catalogue

First decide what a staff member needs to know before acting on a product. This dashboard shows the SKU, supplier, storage bin, current quantity, reorder point and unit cost together. A quantity of zero is labelled “Out of stock”; a positive quantity at or below the reorder point is labelled “Reorder soon”.

Keeping those values together makes the next interaction easier to understand: when we add a filter, it can use the same reorder threshold the person can already see. Define the product model once, then render each record from the sample catalogue.

## Find products and record stock movements

A catalogue becomes useful when staff can narrow it to the work in front of them. Add a search field that checks product names, SKUs and suppliers, plus filters for all products, reorder candidates and items that are out of stock. The filter uses the same `reorder_point` field shown on every row, so “Needs reorder” has a clear meaning.

Receiving goods and recording a sale are separate actions. Receiving five units changes the selected product’s count; recording a sale subtracts one and is disabled when the count is already zero. The update message names the product so a fast click still gives the person useful feedback.

```rust
use crate::models::{sample_products, InventoryProduct};
use fission::prelude::*;

#[derive(Clone, Debug, PartialEq)]
pub struct InventoryState {
    pub products: Vec<InventoryProduct>,
    pub feedback: String,
    pub feedback_is_error: bool,
}

impl Default for InventoryState {
    fn default() -> Self {
        Self {
            products: sample_products(),
            feedback: "Stock movements are in memory for this session.".to_string(),
            feedback_is_error: false,
        }
    }
}

impl GlobalState for InventoryState {}

#[fission_reducer(ReceiveStock)]
pub fn on_receive_stock(
    state: &mut InventoryState,
    product_id: u32,
    quantity: u32,
) {
    let result = if quantity == 0 {
        Err("Enter a quantity greater than zero.".to_string())
    } else if let Some(product) = state.products.iter_mut()
        .find(|product| product.id == product_id)
    {
        match product.stock.checked_add(quantity) {
            Some(next_stock) => {
                product.stock = next_stock;
                Ok(format!(
                    "Received {} units for {} ({}).",
                    quantity, product.name, product.sku
                ))
            }
            None => Err("That receipt exceeds the supported stock quantity.".to_string()),
        }
    } else {
        Err("The product is no longer in this catalogue.".to_string())
    };

    match result {
        Ok(message) => {
            state.feedback = message;
            state.feedback_is_error = false;
        }
        Err(message) => {
            state.feedback = message;
            state.feedback_is_error = true;
        }
    }
}

#[fission_reducer(RecordSale)]
pub fn on_record_sale(state: &mut InventoryState, product_id: u32) {
    let result = if let Some(product) = state.products.iter_mut()
        .find(|product| product.id == product_id)
    {
        if product.stock > 0 {
            product.stock -= 1;
            Ok(format!(
                "Recorded one sale for {} ({}).",
                product.name, product.sku
            ))
        } else {
            Err(format!("{} is already out of stock.", product.name))
        }
    } else {
        Err("The product is no longer in this catalogue.".to_string())
    };

    match result {
        Ok(message) => {
            state.feedback = message;
            state.feedback_is_error = false;
        }
        Err(message) => {
            state.feedback = message;
            state.feedback_is_error = true;
        }
    }
}
```

## Validate receipts and make empty results recoverable

A receiving form must not accept blank text, zero or a quantity that would overflow the stock counter. Add a quantity field and validate it when the person chooses a product. Keep the old stock value when validation fails, then explain what needs to change. This keeps the rule beside the action that depends on it.

Search and filters also need a useful recovery path. If nothing matches, explain that the current search and stock filter produced no rows, then let the staff member return to the full catalogue. Clearing the view must not undo stock movements they already recorded.

The finished screen keeps product records in `GlobalState`, so each reducer updates the stock and its feedback together. The search, active filter and receipt quantity stay local to the dashboard because they only affect this screen. The summary cards and reorder notice are derived from the same product records as the rows; after a receipt or sale, all three parts of the page agree. This tutorial keeps data in memory, so a reload restores the starting catalogue. A production inventory service can replace that boundary with asynchronous reads and writes while the screen keeps its loading, success and error states.

## Run the dashboard

Start the server target from the project root and open the local URL printed by the CLI:

```sh
fission doctor --project-dir .
fission run --target ssr --project-dir .
```

Test the stock workflow before packaging it. Search by SKU, check the reorder filter against each visible reorder point, receive a valid quantity, record a sale, and try to sell the out-of-stock stove. The disabled action and the textual stock status should agree.

The interactive lesson keeps its sample records in component state, so a reload restores them. To keep inventory changes across requests or share them with product-detail routes, move the catalogue into `GlobalState` and add an asynchronous repository service. Let a reducer request the write, render a pending state while it runs, and show the service result when it completes.
