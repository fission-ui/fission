Build a sprint-planning app in Rust for Harborline's Northstar checkout launch. We will start with the screen a teammate sees when a sprint has no work, add real tasks that open on their own routes, then let the team create and move work through the sprint. Each step leaves you with a useful screen; the final app keeps its task data and navigation in sync even when you use the browser's Back button.

The preview controls stay collapsed while you read. Open a step's result when you want to try the screen, then close it to return to the tutorial's full reading width. The app keeps changes in memory: its success and error messages come from the same validation and state transitions you would keep when a backend is added.

Install the Fission CLI and scaffold a Web project:

```sh
cargo install cargo-fission
fission init harbour-workspace
cd harbour-workspace
fission add-target web --project-dir .
```

## Project layout

```text
harbour-workspace/
├── Cargo.toml                 # generated dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                 # generated desktop entrypoint
│   ├── lib.rs                  # shared app setup
│   ├── app.rs                  # reusable Fission components
│   ├── state.rs                # sprint data and reducers
│   ├── router.rs               # routes and browser history
│   ├── pages/task_list.rs      # workspace screen
│   └── pages/task_detail.rs    # task detail screen
├── platforms/                  # generated host files after add-target
└── tests/                      # project-specific flow checks
```

`fission init` generates the project manifest and starter app files; `fission add-target web` adds the browser target. As the board grows, move the shared task model and reducers into `state.rs`, and keep each screen or reusable component in its own module. Data used by both the board and detail route belongs in `GlobalState`; short-lived text or filter selections belong to the component that owns them. A component's view describes what to render, while a reducer performs the state change after a user action.

## Lay out the workspace and explain the empty sprint

A blank board is still a real product state. Someone opening Northstar for the first time should know which project and sprint they are viewing, whether work has been planned, and what will appear after the first task is added. Render those parts before adding task cards; that gives us a useful layout to extend in the next step.

`SprintMetric` is a small reusable component for the three summaries. `TaskWorkspace` owns the screen composition, reads its colors and spacing from Fission's current theme, and gives the empty state enough context to explain what is missing. There is no inert button here: the app tells the team what to do, and we make that action work when the form arrives in the final step.

## Open a task from the sprint board

Now the board needs records that a teammate can actually open. Store the three checkout launch tasks in `TaskBoardState`, which implements `GlobalState` because both the list and detail page read the same records. Each card links to `/tasks/:id`; the route carries the selected task's id, while the shared state supplies its title, owner and delivery context.

The detail route is built with `RouterParams`, so a URL such as `/tasks/241` can select task 241 without copying task data into a second screen. Fission's Web shell reports browser history changes to `route_changed`, which updates the router's current path. Try a card, then use Back and Forward: the URL and the page should move together.

## Add validated work and move it through the sprint

A useful board also needs to accept the next piece of work. Keep the title and context drafts inside `SprintTaskBoard`, because no other screen needs them before the teammate submits the form. Keep saved tasks and feedback in `TaskBoardState`, because the board and detail route must see the same result.

`AddSprintTask` checks the title before changing the sprint. If the title is too short, the reducer returns an actionable error and leaves the task list untouched. A valid title creates a new Ready task, then reports its assigned id. From the detail route, `AdvanceSprintTask` moves it to the next lane. These are local state changes, so the preview shows realistic validation without pretending to contact a server. The same reducer boundary is where a production app can later request an asynchronous save.

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum TaskStatus {
    Ready,
    InProgress,
    InReview,
    Done,
}

impl TaskStatus {
    pub fn label(self) -> &'static str {
        match self {
            Self::Ready => "Ready",
            Self::InProgress => "In progress",
            Self::InReview => "In review",
            Self::Done => "Done",
        }
    }

    pub fn next(self) -> Self {
        match self {
            Self::Ready => Self::InProgress,
            Self::InProgress => Self::InReview,
            Self::InReview => Self::Done,
            Self::Done => Self::InReview,
        }
    }
}

fn task_matches(task: &SprintTask, query: &str, filter: &str) -> bool {
    let query = query.trim().to_lowercase();
    let matches_query = query.is_empty()
        || task.title.to_lowercase().contains(&query)
        || task.owner.to_lowercase().contains(&query)
        || task.team.to_lowercase().contains(&query)
        || format!("NS-{}", task.id).to_lowercase().contains(&query);
    let matches_filter = match filter {
        "mine" => task.owner == "Mara Chen",
        "high" => task.priority == "High",
        _ => true,
    };
    matches_query && matches_filter
}

#[derive(Clone, Debug, PartialEq)]
pub struct TaskBoardState {
    pub current_path: String,
    pub tasks: Vec<SprintTask>,
    pub next_task_id: u32,
    pub feedback: Option<String>,
    pub feedback_is_error: bool,
}

impl Default for TaskBoardState {
    fn default() -> Self {
        Self {
            current_path: "/projects/northstar".into(),
            tasks: sample_tasks(),
            next_task_id: 251,
            feedback: None,
            feedback_is_error: false,
        }
    }
}

impl GlobalState for TaskBoardState {}

#[fission_reducer(AddSprintTask)]
pub fn on_add_sprint_task(state: &mut TaskBoardState, title: String, context: String) {
    let title = title.trim();
    if title.chars().count() < 5 {
        state.feedback =
            Some("Use at least five characters so the task is clear to the team.".into());
        state.feedback_is_error = true;
        return;
    }

    let id = state.next_task_id;
    state.next_task_id += 1;
    state.tasks.insert(
        0,
        task(
            id,
            title,
            "Product",
            "Mara Chen",
            "Normal",
            "Unscheduled",
            if context.trim().is_empty() {
                "Add acceptance details before work begins."
            } else {
                context.trim()
            },
            TaskStatus::Ready,
        ),
    );
    state.feedback = Some(format!("NS-{id} was added to Ready."));
    state.feedback_is_error = false;
}

#[fission_reducer(AdvanceSprintTask)]
pub fn on_advance_sprint_task(state: &mut TaskBoardState, task_id: u32) {
    if let Some(task) = state.tasks.iter_mut().find(|task| task.id == task_id) {
        task.status = task.status.next();
        state.feedback = Some(format!("NS-{} moved to {}.", task.id, task.status.label()));
        state.feedback_is_error = false;
    } else {
        state.feedback = Some("That task is no longer in this sprint.".into());
        state.feedback_is_error = true;
    }
}
