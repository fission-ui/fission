When a support supervisor opens the admin panel, they need to know who is waiting, what happened, who owns the issue, and what they can safely do next. A table of labels is not enough. We’ll build a small workspace with the queue and selected conversation side by side, then add the checks and history that make a resolution clear to the next person.

The example uses sample records for a fictional team at Harbour Support. They live in the browser, so you can try the screen without an account or server. Search, filters, the role demo, and unfinished note belong to this screen, so keep them local. The selected ticket ID belongs in shared app state because both panes use it. A real app loads tickets from a service and makes permission decisions on the server.

## Create the Web project

Install the Fission CLI if needed, then scaffold the Web target. The generated shell starts the app; the screen belongs in shared Rust code.

## Start with the support queue

Start with the queue. Each row should show who raised the issue, what it is about, its category and priority, and who owns the next action. Summary cards give a sense of the backlog, but the ticket list is still the main work surface.

The queue is a named component with a clear job. Keep the sample records nearby for this preview; when a service supplies real records, move the model and shared state into their own modules.

## Find a ticket and inspect its history

Supervisors often start with a name, ticket number, or queue such as “urgent” or “assigned to me.” Search customer and issue text so a partial name finds the right conversation. Keep the detail panel visible when filters change; otherwise the person reviewing a case can lose their place.

Search text and the active filter only affect this screen, so retain them locally. The selected ticket ID belongs in `SupportState` because both the queue and detail pane depend on it. Give each row a stable key based on the ticket ID; filtering or sorting must not change which ticket owns its retained state.

<!-- fission:step id="resolve-with-context" -->
Finding the ticket is only part of the job. Resolving it should leave an internal note that explains what the supervisor checked, and an agent without permission should not be able to perform that action.

The note is an unfinished screen draft. The preview also keeps its resolved status locally; a real app sends the action to an authorised service, which checks the user’s role before changing the stored ticket.

## Resolve the issue with a documented action

A disabled button needs an explanation. Here, the supervisor must write at least eight characters of internal context, and the role switch demonstrates why an agent cannot resolve a ticket. The button is available only when both checks pass. After resolving, the right pane adds the note to the activity history so the next operator knows why the case was closed.

The preview keeps the draft and role in local component state; neither should survive leaving the screen. A real server must authorize the user and append the audit event atomically with the status change. Disabling the browser button improves the interaction, but it does not provide security.

## Connect the screen to real application data

The preview uses a fixed set of tickets so you can try the workbench immediately. In your app, move `SupportTicket` and data loading into model and service modules, and put records shared by routes in `GlobalState`. Search text, the selected row, and an unfinished note still belong to this screen.

In production, the UI dispatches an action, an async effect calls the ticket service, the service checks the signed-in user’s permission, and a reducer records the returned status and activity event. Show a loading state while the request runs. If the service rejects it, keep the note and selected ticket and explain what the operator can do next. The client-side role switch only demonstrates the interaction; never use it as the permission check.
