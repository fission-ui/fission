A support supervisor opening an admin panel needs to answer a few connected questions: which customer is waiting, what happened, who owns the issue, and what action is safe to take? A table of labels does not answer those questions. We will build a small support workspace that keeps the ticket queue and the selected conversation in view, then adds the checks that make a resolution understandable to the next person.

The example follows a fictional team at Harbour Support. Its records are sample data held in the browser for this lesson, so the preview can be used without an account or server. The same screen structure can connect to a ticket service later. Search, filters, the role demonstration and the unfinished note belong to this screen, so the component retains them locally. The selected ticket ID belongs in shared app state because the queue and detail pane both read it. In a real application, ticket records come from a service and permission decisions are made on the server.

## Create the Web project

Install the Fission command line tool if it is not already available, then scaffold the browser target. The generated shell starts the app; the screen we build below lives in shared Rust code.

## Start with the support queue

Start from the queue a supervisor sees when opening the workspace. Each row answers a different part of the triage question: the customer and subject explain the issue, the category and priority describe its impact, and the assignee shows who should act next. The summary cards give a quick sense of the backlog, but the ticket list remains the main content.

Notice that the queue is a reusable screen component with a domain name. The sample records are kept near the screen for now because they are only preview data; when records are loaded from a service, move the model and shared state into their own modules.

## Find a ticket and inspect its history

The supervisor’s work usually begins with a name, a ticket number or a queue such as “urgent” or “assigned to me.” Search across both customer and issue text so a partial name still finds the right conversation. When a row is selected, keep the detail panel visible even while filters change; otherwise the user can lose the issue they were reading.

This step gives every selectable row a stable key based on its ticket id. That key matters because these rows are generated from data and their order may change as the query or filter changes.

<!-- fission:step id="resolve-with-context" -->
Selection and search solve the “find the case” part of the task. A realistic admin screen also needs an accountable change. Resolving a customer issue should leave an internal note describing what the supervisor checked, and it should be unavailable to an agent who lacks that permission.

The note field below belongs to this screen as an unfinished draft. The resolved status shown in the preview is also local demonstration state; an application should send the action to an authorised service, which verifies the role again before changing the stored ticket.

## Resolve the issue with a documented action

A disabled button needs an explanation beside it. Here, the supervisor must write at least eight characters of internal context, and the role switch lets you see why an agent cannot resolve tickets. The button becomes available only when both conditions are met. After resolving, the right pane displays the note in the activity history so the next operator can see why the case was closed.

The preview keeps that draft and role in component-local state because neither should survive leaving this screen. In a real application, the server must authorize the current user and append an audit event atomically with the status change. A disabled browser button improves the interaction; it does not provide security.

## Connect the screen to real application data

The browser preview uses a fixed ticket set so the workbench is immediately usable. In your own project, move SupportTicket and its data loading to a model or service module, and put records shared by multiple routes in GlobalState. Search text, the selected row and an unfinished note still belong to this screen.

A production resolution should follow this sequence: the UI dispatches an action, an asynchronous effect calls the ticket service, the service checks the signed-in user’s permission, and a reducer records the returned status and activity event. Keep the screen in a loading state while that work runs; if the service rejects it, retain the note and selected ticket and explain how the operator can recover. The client-side role switch in this lesson only demonstrates the interaction, and must never be used as the permission check.
