What should happen when someone edits a task on a train, then reconnects after another device has changed the same task? We will build an offline-first task list that opens from local data, accepts edits without a connection and makes queued work and conflicts visible. The browser preview demonstrates those states; the real app persists through Fission Store and sends sync work through an asynchronous effect.

Keep the local edit usable while sync is pending. When a reply arrives, compare it with the current task state before applying it so an older request cannot overwrite newer work.

Install the Fission CLI and scaffold the Web, Android and iOS project:

```sh
cargo install cargo-fission
fission init harbour-offline
cd harbour-offline
fission add-target web android ios --project-dir .
fission add-capability storage --project-dir .
```

```text

├── src/

│   ├── app.rs                  # the Fission component shown in this tutorial
│   ├── state.rs
│   ├── storage.rs
│   ├── effects/sync.rs
│   └── components/sync_status.rs
├── platforms/                  # generated host files after add-target
└── tests/                      # project-specific flow checks
```

`fission init` generates `Cargo.toml`, `fission.toml`, `src/main.rs`, `src/lib.rs` and `src/app.rs`. Add the task modules in the tree as you build the feature. Keep data shared across routes in `GlobalState`, and keep retained interaction such as a disclosure or draft field in the owning `fission_component!`. Request database, filesystem, network and session work through a reducer effect, job or service; never run host work while a component view is being built.

`preview/lib.rs` compiles the complete `src/app.rs` into WebAssembly so you can try the shared screen here. Its host responses are predictable; use the target-specific steps below to test real host work.

## Accept edits while offline

Load persisted state once during startup and show an explicit loading state until hydration finishes. Do not start file or database work while a component is being converted. Keep local edits available when the network request fails.

This preview keeps the online toggle, queue count, and error locally. In the app, task data, revisions, and pending sync status belong in `GlobalState` because results may arrive after this screen changes.
### Save locally first and reject stale sync results

Treat the local record as the source the screen renders. When a user edits a note, increment its revision, persist that revision locally, and show the edit immediately. Queue a sync effect only after the local write succeeds. Include the revision in the request and apply a network response only when it still matches the latest local revision; a slow response must not overwrite a newer edit.

Render four distinct states: **Saved on this device**, **Syncing**, **Synced**, and **Could not sync**. Keep the offline edit after a failed request and offer **Retry sync** without requiring the user to re-enter it. On restart, hydrate the local queue before starting network work, then retry only records that remain pending.

For deterministic tests, use a fake service that completes requests out of order: make revision 1 finish after revision 2, and assert that revision 2 stays visible. Also test no network, a successful retry and an app restart with an unsent edit.

```rust
use fission::prelude::*;
fission_component! {
    pub OfflineNotes<()> {
        props {
            title: String,
            detail: String,
            action: String,
            success: String,
            empty: String,
        }
        state {
            online: bool = false,
            queued: usize = 1,
            has_error: bool = false,
        }
    }
    view(preview, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
    } =>
    Container(
        Column(
            gap: tokens.spacing.m,
            children: [
                Text(preview.title.clone()).weight(tokens.typography.font_weight_bold),
                Text(preview.detail.clone()).color(tokens.colors.text_secondary),
                Text(if preview.online { "Connection: Online" } else { "Connection: Offline" }),
                Button(child: Text(preview.action.clone()),
                    key: "queue-change",
                    on_press: reduce { preview.queued += 1; }),
                Button(child: Text(if preview.online { "Go offline".to_string() } else { "Go online".to_string() }),
                    key: "connection",
                    on_press: reduce { preview.online = !preview.online; }),
                if preview.online && preview.queued > 0 { Button(child: Text("Sync changes"),
                        key: "sync-queue",
                        on_press: reduce { preview.queued = 0; }) },
                Text(format!("{} change(s) waiting",
                        preview.queued)),
                Button(child: Text(if preview.has_error { "Try again".to_string() } else { "Preview a sync conflict".to_string() }),
                    key: "preview-error",
                    on_press: reduce { preview.has_error = !preview.has_error; }),
                if preview.has_error { Text("The server has a newer version. Keep the local draft and review both versions.") } else { Text(preview.success.clone()) },
                Text(preview.empty.clone()).color(tokens.colors.text_secondary),
            ]
        )
    )
    .padding_all(tokens.spacing.l)
    .bg(tokens.colors.surface)
    .border(tokens.colors.border, 1.0)
    .border_radius(tokens.radii.large)
}
```

## Retry sync and explain conflicts

Give every local change a stable id and version. When local and remote writes finish in a different order, compare versions before accepting a completion so an old response cannot overwrite a newer edit. Show pending, synced and failed states in words.

Keep I/O outside component conversion. Use reducers for explicit state transitions, then queue host work through an asynchronous effect, capability, job or service so the UI stays responsive.
The preview control below simulates an unsuccessful host result. It demonstrates the message and recovery path; it does not perform authentication, database, network, or filesystem work.

## Run, test and build the finished project

From the project root, run the checks in order:

```sh
fission doctor --project-dir .
cargo test
fission build --target web --project-dir .
fission build --target android --project-dir .
fission build --target ios --project-dir .
fission test --target web --project-dir .
```

Expected result: Users can edit offline, see queued work, retry after reconnecting, and resolve conflicts without losing a draft.
