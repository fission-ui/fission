Build a Rust SSR sign-in flow with accessible fields, server-side validation, signed form actions, rotated sessions and safe return navigation. This tutorial takes you from project setup to a runnable result in three steps. Each step’s `src/app.rs` component is compiled into the WebAssembly preview shown beside its code, so you can try the same Fission component while you read. The preview checks input shape and shows success or failure states only. Keep credentials, session cookies, authorization and return redirects on the server.

## What you will build

Build a server-rendered sign-in flow with email and password fields, validation feedback, a pending submit state and a safe return path after success.

Install the Fission CLI and scaffold the SSR project:

```sh
cargo install cargo-fission
fission init harbour-auth
cd harbour-auth
fission add-target ssr --project-dir .
```

## Project layout

```text
harbour-auth/
├── Cargo.toml                 # generated dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                 # generated desktop entrypoint
│   ├── lib.rs                  # shared app setup
│   ├── app.rs                  # the Fission component shown in this tutorial
│   ├── state.rs
│   ├── auth/session.rs
│   ├── server/login.rs
│   ├── components/login_form.rs
├── platforms/                  # generated host files after add-target
└── tests/                      # project-specific flow checks
```

`fission init` generates `Cargo.toml`, `fission.toml`, `src/main.rs`, `src/lib.rs` and `src/app.rs`. Add the task modules in the tree as you build the feature. Keep data shared across routes in `GlobalState`, and keep retained interaction such as a disclosure or draft field in the owning `fission_component!`. Request database, filesystem, network and session work through a reducer effect, job or service; never run host work while a component view is being built.

`preview/lib.rs` is a documentation harness. The page compiles each complete `src/app.rs` component into WebAssembly so you can use the same UI while reading. Its host results are deterministic preview states; the target-specific host work described in this tutorial runs in each target project code, not in the browser preview.

## Add labelled email and password fields

Begin with the screen needed for this task. The first render gives you a concrete checkpoint before you add interaction state.

Use props for page copy and read theme tokens through cx.view.env(). The component below keeps presentation aligned with the active design system.

<Tabs>
<TabItem label="src/app.rs">
<!-- fission:file path="src/app.rs" -->
```rust
use fission::prelude::*;
fission_component! {
    pub LoginForm<()> {
        props {
            title: String,
            detail: String,
            action: String,
            success: String,
            empty: String,
        }
    }
    view(preview, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
    } =>
    Container(
        Column(
            gap: tokens.spacing.m,
            children: [
                Text(preview.title.clone()).weight(tokens.typography.font_weight_bold),
                Text(preview.detail.clone()).color(tokens.colors.text_secondary),
                TextInput(label: Some("Email address".into()),
                    placeholder: Some("you@example.com".into())),
                TextInput(label: Some("Password".into()),
                    placeholder: Some("Enter your password".into()),
                    obscure_text: true),
                Text(format!("Next action: {}",
                        preview.action)),
                Text(preview.empty.clone()).color(tokens.colors.text_secondary),
            ]
        )
    )
    .padding_all(tokens.spacing.l)
    .bg(tokens.colors.surface)
    .border(tokens.colors.border, 1.0)
    .border_radius(tokens.radii.large)
}
```

## Validate input and show submission state

Keep credential checks on the server. Validate the submitted fields there, sign the action token, and rotate the session after a successful authentication. Return a clear field-level error for an invalid submission without echoing a password or telling an attacker which account exists.

The source below makes the main task interactive using retained component state and explicit controls.
This state belongs to the component because it only remembers this view's interaction. Durable data shared across routes belongs in GlobalState and changes through reducers.
<Tabs>
<TabItem label="src/app.rs">
<!-- fission:file path="src/app.rs" -->
```rust
use fission::prelude::*;
fission_component! {
    pub LoginForm<()> {
        props {
            title: String,
            detail: String,
            action: String,
            success: String,
            empty: String,
        }
        state {
            email: String = String::new(),
            password: String = String::new(),
            submitted: bool = false,
            has_error: bool = false,
        }
    }
    view(preview, _state, cx) {
        let tokens = &cx.view.env().theme.tokens;
    } =>
    Container(
        Column(
            gap: tokens.spacing.m,
            children: [
                Text(preview.title.clone()).weight(tokens.typography.font_weight_bold),
                Text(preview.detail.clone()).color(tokens.colors.text_secondary),
                TextInput(label: Some("Email address".into()),
                    placeholder: Some("you@example.com".into()),
                    bind: preview.email,
                    semantics_identifier: "tutorial.login.email".to_string()),
                TextInput(label: Some("Password".into()),
                    placeholder: Some("Enter your password".into()),
                    bind: preview.password,
                    obscure_text: true,
                    semantics_identifier: "tutorial.login.password".to_string()),
                Button(child: Text(preview.action.clone()),
                    key: "sign-in",
                    disabled: preview.email.trim().is_empty() || !preview.email.contains('@') || preview.password.is_empty(),
                    on_press: reduce { preview.submitted = true; }),
                if preview.submitted { Text(preview.success.clone()) } else { Text(preview.empty.clone()) },
                Button(child: Text(if preview.has_error { "Try again".to_string() } else { "Preview a rejected sign-in".to_string() }),
                    key: "preview-error",
                    on_press: reduce { preview.has_error = !preview.has_error; }),
                if preview.has_error { Text("The email or password was not accepted. Check both fields and try again.") } else { Text(preview.success.clone()) },
                Text(preview.empty.clone()).color(tokens.colors.text_secondary),
            ]
        )
    )
    .padding_all(tokens.spacing.l)
    .bg(tokens.colors.surface)
    .border(tokens.colors.border, 1.0)
    .border_radius(tokens.radii.large)
}
```

## Keep authentication and redirects on the server

Accept a return destination only when it is a local path on this application. Preserve the entered email after a recoverable validation error, but clear secrets. Test an invalid password, a missing field, a session rotation and a hostile external return URL.

Keep I/O outside component conversion. Use reducers for explicit state transitions, then queue host work through an asynchronous effect, capability, job or service so the UI stays responsive.
The preview control below simulates an unsuccessful host result. It demonstrates the message and recovery path; it does not perform authentication, database, network, or filesystem work.

Configure the server-managed session cookie in `fission.toml`:

<!-- fission:file path="fission.toml" -->
```toml
[server.sessions]
cookie_name = "harbour_session"
signing_key_env = "HARBOUR_SESSION_SECRET"
secure = true
same_site = "lax"
```

Fission signs and protects the session cookie. Your authentication service still verifies credentials and stores the authenticated user id server-side; the cookie does not prove who the user is by itself.

## Run, test and build the finished project

From the project root, run the checks in order:

```sh
fission doctor --project-dir .
fission run --target ssr --project-dir .
cargo test
fission build --target ssr --project-dir .
fission test --target ssr --project-dir .
```

Expected result: The preview blocks obviously invalid input and shows recoverable failure feedback without sending credentials. Connect an SSR form action to your authentication service, then accept only a local return URL after the server confirms the user.
