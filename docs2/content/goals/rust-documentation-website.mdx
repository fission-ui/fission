A guide and a reference page answer different questions. A guide explains how to reach an outcome; a reference specifies the fields or operations involved. Mixing both into one flat list forces the reader to reconstruct that distinction each time.

We will build Atlas Docs with a Compose homepage and authored Markdown pages. Fission's documentation template already supplies the sidebar, article and page outline. Rebuilding those pieces as a separate app would give us two navigation systems to maintain, so we will configure the existing one.

## Create the project

```sh
cargo install cargo-fission
fission init atlas-docs --template website
cd atlas-docs
cargo add serde_yaml
```

Keep the generated launcher, which calls `atlas_docs::build_site()`. The following checkpoints contain the actual configuration, Rust modules and Markdown. Their previews are the generated HTML, not a collection of hard-coded articles held in app state. Replace the reserved example.com origin before publishing.

## Give the reader a task and a real route

The homepage explains where to start. The learning pages then teach a concrete, small planning workflow; they are not placeholder cards. Each Markdown file owns its title, description, headings and body.

The Rust component uses theme tokens and translated chrome. These English articles remain English: loading a Spanish bundle translates the component's labels, not the Markdown. A translated edition needs separate authored pages and intentional locale routes.

```rust
pub mod home;
mod translations;

pub fn site_app() -> fission::site::FissionSite {
    fission::site::FissionSite::new().with_env(translations::create_env())
        .route_widget::<(), _>("/", "Atlas Docs",
            Some("Create a first project, then find the exact configuration contract.".into()),
            home::DocumentationHome::new())
}
pub fn build_site() -> anyhow::Result<()> {
    fission::site::build_from_cli(site_app())
}
```

```rust
    } =>
```

```rust
use fission::i18n::{Locale, TranslationBundle};
use fission::prelude::*;
use std::collections::HashMap;
pub fn create_env() -> Env {
    let mut env = Env::default();
    env.locale = Locale::from("en-US");
    for (locale, source) in [
        ("en-US", include_str!("../i18n/en-US.yaml")),
        ("es-ES", include_str!("../i18n/es-ES.yaml")),
    ] {
        let messages: HashMap<String, String> =
            serde_yaml::from_str(source).expect("checked-in translations must be valid YAML");
        env.i18n.add_bundle(TranslationBundle { locale: Locale::from(locale), messages });
    }
    env
}
```

````md
---
title: Create a first Atlas project
description: Create a project directory, define one outcome and check who owns the next step.
---
A project needs an outcome before it needs a dashboard. This small example creates a plain-text plan that a teammate can review without installing a service.

## Create the directory
```sh
mkdir atlas-project
cd atlas-project
```

Create `plan.txt` with these contents:

```text
Outcome: publish the support handover guide
Owner: the person coordinating the release
Next step: ask support which questions are missing
```

## Check the plan
Open the file and check that the next step can actually be performed. “Finish the project” is not a useful next step: it repeats the outcome without explaining what comes first.

## Review changes
Keep the plan with the project's other files. When the outcome changes, update this file rather than leaving a second version in a chat message.

[Return to the learning overview](../../overview/).
````

## Separate explanation from lookup

Add Reference as another content mount rather than another branch in a local active_page enum. The sidebar explicitly orders its entries; the article still comes from Markdown.

Search is an enhancement over the generated content. Enabling it emits the index and browser search assets. It does not turn this Static site into a search server, and the articles remain readable without JavaScript.

````md
---
title: Atlas project record
description: Fields and constraints for the plan.txt record used by the first-project guide.
---
This is the contract used by our example plan, not a Fission manifest schema.

## Outcome
Required. One sentence naming the result the project should produce. Keep implementation steps in Next step instead.

## Owner
Required. The person responsible for coordinating the next decision. This label does not grant access or establish an authenticated identity.

## Next step
Required. One action someone can take now. Replace it when that action is complete; do not keep several conflicting next steps.

## Example
```text
Outcome: publish the support handover guide
Owner: the release coordinator
Next step: ask support which questions are missing
```

[Create a first project](/docs/learn/quickstart/) explains why these fields are useful.
````

## Add recovery information where the reader needs it

A reference contract can be correct while leaving a reader stuck. Add a short troubleshooting guide for an ambiguous owner or an unactionable next step, and put it after the first-project guide. That gives the learning navigation a deliberate order rather than alphabetical filenames.

````md
---
title: Resolve an unclear project plan
description: Check an ambiguous owner, conflicting next steps and an outcome that cannot be reviewed.
---
## The owner is a department
Choose the person who can coordinate the next decision. A department name does not tell a reader whom to contact.

## There are several next steps
Pick the first action that can be completed independently. Put later work in the team's task list instead of turning this field into another backlog.

## Nobody can tell whether the outcome is done
Write down what a reviewer should be able to observe. “Improve support” is broad; “publish the handover guide reviewed by support” identifies a result.
````

## Build the files the reader will receive

```sh
fission site build --project-dir .
fission site check --project-dir .
fission site routes --project-dir .
fission site serve --project-dir . --port 8123
curl http://127.0.0.1:8123/docs/learn/quickstart/
```

Inspect the returned article text and real heading anchors. A green Rust build does not prove that a sidebar destination exists; the site check and browser checks cover that separate concern. Keep old published paths when restructuring a live site, or add explicit redirects before changing them.
