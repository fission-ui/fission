Sharing Rust code does not make Android and iOS identical. The app state and reducers can stay shared, while each target still needs its own host, build and device checks. The browser preview shows the shared component; it cannot confirm native launch or device-capability behaviour.

Build a shared field-work app that runs on Android and iOS. Keep the work order and its transitions in shared Rust, then check the generated host on each platform.

Install the Fission CLI and scaffold the Android and iOS project:

```sh
cargo install cargo-fission
fission init harbour-mobile
cd harbour-mobile
cargo add serde_yaml
fission add-target android ios --project-dir .
```

## Project layout

```text
harbour-mobile/
├── Cargo.toml                 # generated dependencies
├── fission.toml               # app identity, targets and capabilities
├── src/
│   ├── main.rs                 # generated shared app entrypoint
│   ├── lib.rs                  # shared app setup
│   ├── app.rs                  # the Fission component shown in this tutorial
│   ├── state.rs
│   ├── components/task_list.rs
├── i18n/
│   ├── en-US.yaml
│   └── es-ES.yaml
├── platforms/
│   ├── android/
│   └── ios/
└── tests/                      # project-specific flow checks
```

`fission init` generates `Cargo.toml`, `fission.toml`, `src/main.rs`, `src/lib.rs` and `src/app.rs`. Add the task modules in the tree as you build the feature. Keep data shared across routes in `GlobalState`, and keep retained interaction such as a disclosure or draft field in the owning `fission_component!`. Request database, filesystem, network and session work through a reducer effect, job or service; never run host work while a component view is being built.

`preview/lib.rs` compiles the complete `src/app.rs` into WebAssembly so you can try the shared screen here. Its host responses are predictable; use the target-specific steps below to test real host work.

The preview seeds one work order in `preview/lib.rs`. `MobileTaskState::default()` stays empty; demo data does not become a production default.

Keep user-facing labels in checked-in English and Spanish bundles. The Android and iOS shells should install both bundles and select the supported device locale; the browser preview below starts in English. The work-order details come from the dispatcher, so they are app data rather than UI labels.

## Build a touch-friendly work-order screen

Start with the work a technician actually needs to do: identify the site, equipment and due time before touching the inspection. The app state owns the work order, so the same screen and data model are used by both native targets.

use std::collections::HashMap;

use fission::i18n::{Locale, TranslationBundle};
use fission::prelude::*;

pub fn create_env(locale: &str) -> Env {
    let mut env = Env::default();
    env.locale = Locale::from(locale);
    for (bundle_locale, source) in [
        ("en-US", include_str!("../i18n/en-US.yaml")),
        ("es-ES", include_str!("../i18n/es-ES.yaml")),
    ] {
        let messages: HashMap<String, String> =
            serde_yaml::from_str(source).expect("valid work-order translations");
        env.i18n.add_bundle(TranslationBundle {
            locale: Locale::from(bundle_locale),
            messages,
        });
    }
    env
}

#[derive(Clone, Debug, PartialEq, Eq)]
pub struct InspectionTask {
    pub reference: String,
    pub title: String,
    pub site: String,
    pub equipment: String,
    pub due: String,
    pub instructions: String,
    pub complete: bool,
}

#[derive(Clone, Debug, Default, PartialEq, Eq)]
pub struct MobileTaskState {
    pub task: Option<InspectionTask>,
    pub latest_note: Option<String>,
}

impl GlobalState for MobileTaskState {}

fission_component! {
    pub MobileTaskPlanner<MobileTaskState>
    view(_planner, state, cx) {
        let tokens = &cx.view.env().theme.tokens;
        let shift_status = match &state.task {
            Some(task) if task.complete => cx.tr("shift.no_due"),
            Some(_) => cx.tr("shift.one_due"),
            None => cx.tr("shift.no_work"),
        };
    } =>
    Container(SafeArea(
        child: Scroll(
            direction: FlexDirection::Column,
            show_scrollbar: true,
            flex_grow: 1.0,
            child: Container(
                SemanticsRegion(
                    identifier: Some("mobile-field-work".to_string()),
                    label: Some(cx.tr("work.screen_label")),
                    child: Column(gap: tokens.spacing.l, children: [
                        Row(gap: tokens.spacing.m, align_items: ir_op::AlignItems::Center, children: [
                            Column(gap: tokens.spacing.xs, children: [
                                Text(cx.tr("shift.team"))
                                    .weight(tokens.typography.font_weight_bold),
                                Text(cx.tr("shift.morning"))
                                    .color(tokens.colors.text_secondary),
                            ]),
                            Spacer(flex_grow: 1.0),
                            Badge(text: shift_status.to_string()),
                        ]),
                        match &state.task {
                            Some(task) => Container(Column(gap: tokens.spacing.m, children: [
                                Row(gap: tokens.spacing.s, wrap: ir_op::FlexWrap::Wrap, children: [
                                    Text(task.reference.clone())
                                        .weight(tokens.typography.font_weight_semibold),
                                    Badge(text: if task.complete {
                                        cx.tr("work.complete")
                                    } else {
                                        format!("{} {}", cx.tr("work.due"), task.due)
                                    }),
                                ]),
                                Text(task.title.clone())
                                    .size(tokens.typography.heading2_size)
                                    .weight(tokens.typography.font_weight_bold),
                                Text(format!("{} · {}", task.site, task.equipment))
                                    .color(tokens.colors.text_secondary),
                                Text(task.instructions.clone()),
                            ]))
                                .padding_all(tokens.spacing.l)
                                .bg(tokens.colors.surface)
                                .border(tokens.colors.border, 1.0)
                                .border_radius(tokens.radii.large),
                            None => Column(gap: tokens.spacing.s, children: [
                                Text(cx.tr("work.empty.title"))
                                    .weight(tokens.typography.font_weight_semibold),
                                Text(cx.tr("work.empty.body"))
                                    .color(tokens.colors.text_secondary),
                            ]),
                        },
                    ]),
                ),
            )
                .padding_all(tokens.spacing.l),
        )
    ))
    .height_length(Length::vh(100.0))
    .bg(tokens.colors.background)
}

## Share state across Android and iOS

Use shared state and component modules for the product workflow. Give touch targets comfortable space, make the main action reachable without precise gestures, and keep labels visible when a control is selected. Check the same route or screen with long translated text.

The work order is shared application data, so changing its status updates `GlobalState`. The reducer stays beside the action here because this tutorial uses it only once; a transition shared by several screens should be a named reducer.

## Keep an unsent note local and save it to shared state

The note draft belongs to this editor, so keep it in the component's retained `state`. Once the technician saves it, it becomes work-order data in `GlobalState` and both Android and iOS render the same result. The preview shows that state transition without pretending to save to a server or device.

## Run, test and build the finished project

Before running the app, follow the [Android development setup guide](/blog/set-up-rust-android-gui-development-with-fission/) to install the SDK and NDK, and the [iOS development setup guide](/blog/set-up-rust-ios-development-with-fission/) to install Xcode and the Rust targets. Those guides also cover starting an emulator or Simulator and connecting a device.

From the project root, list available devices, launch each target, then run the checks:

```sh
fission doctor --project-dir .
fission devices --project-dir .
fission run --target android --project-dir .
fission run --target ios --project-dir .
cargo test
fission build --target android --project-dir .
fission build --target ios --project-dir .
fission test --target android --project-dir .
fission test --target ios --project-dir .
```

Expected result: The same work-order model and reducers build for Android and iOS. The screen adapts to each shell, shared status changes remain app data, and the unsaved note stays local to its editor.

`fission run --target android` launches the selected emulator or connected Android device. `fission run --target ios` launches an iOS Simulator; it does not install the app on a physical iPhone. Use the [Android emulator guide](/blog/create-and-launch-a-fission-android-emulator/) or [Android phone guide](/blog/run-a-fission-app-on-a-physical-android-phone/) when you need those setup steps, and the [iOS Simulator guide](/blog/choose-boot-and-launch-an-ios-simulator-with-fission/) or [physical iPhone guide](/blog/install-a-fission-app-on-a-physical-iphone/) for iOS.
