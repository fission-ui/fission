# Add accessible semantics

A control has one purpose whether it is activated by pointer, keyboard, screen
reader, or a test. Start from the standard widget that already owns those
interaction semantics, then add the product's name and stable identifier.

This recipe uses contact preferences. The form has an editable draft and a
separate set of applied session preferences; Apply copies the draft rather
than turning on a loading flag for work that never completes.

## Step 1: start from meaningful state and actions

```rust
use fission::prelude::*;

#[derive(Debug, Clone, Default, PartialEq, Eq)]
pub struct ContactPreferences {
    pub email: String,
    pub marketing_enabled: bool,
}

#[derive(Debug, Clone, Default, PartialEq, Eq)]
pub struct SettingsState {
    pub draft: ContactPreferences,
    pub applied: ContactPreferences,
    pub applied_notice: bool,
}

impl GlobalState for SettingsState {}
```

The app reads `applied` when it needs current session preferences. This example
does not persist them or change a server account. Those operations would need
their own effects and completion states. Draft edits remain separate so Apply
has a real, inspectable consequence.

## Step 2: resolve labels from the current locale

`cx.tr("settings.email")` resolves a translation key against the active
environment and returns a String for a visible or semantic label. Prepare
English and Spanish bundles at startup as described in
[Theming and i18n](/docs/guides/theming-and-i18n/).

Keep labels meaningful after the user starts typing. A placeholder is not a
replacement for an input label, and concatenating translated fragments can
produce the wrong sentence order.

## Step 3: make the section a semantic region

```rust
fission_component! {
    pub AccountSettings<SettingsState> {}
    view(_settings, state, cx) {
        let tokens = &cx.view.env().theme.tokens;
    } =>
    SemanticsRegion(
        identifier: Some("settings.account".into()),
        label: cx.tr("settings.account"),
        child: Column(gap: tokens.spacing.m, children: [
            Text(cx.tr("settings.account"), font_size: tokens.typography.heading1_size),
            TextInput(
                value: state.draft.email.clone(),
                label: cx.tr("settings.email"),
                bind(on_input): to(state.draft.email),
            ).semantics_identifier("settings.email"),
            Checkbox(
                label: cx.tr("settings.marketing"),
                bind: state.draft.marketing_enabled,
            ).semantics_identifier("settings.marketing"),
            Button(
                child: Text(cx.tr("settings.apply")),
                key: "apply",
                disabled: state.draft.email.trim().is_empty(),
                on_press: reduce {
                    if !state.draft.email.trim().is_empty() {
                        state.draft.email = state.draft.email.trim().to_owned();
                        state.applied = state.draft.clone();
                        state.applied_notice = true;
                    }
                },
            ).semantics_identifier("settings.apply"),
            if state.applied_notice && state.applied == state.draft {
                Text(cx.tr("settings.applied_this_session"))
            },
        ]),
    )
}
```

The standard input, checkbox, and button supply their roles and supported
actions. The region groups them without pretending to be another control.
`settings.account` identifies the panel, while the control identifiers survive
translation and layout changes.

The required-text guard is not an email-verification scheme. An account server
must validate addresses and authorise account updates independently.

## Step 4: add explicit labels for visual-only controls

An icon-only button still needs an accessible name. `ButtonIconContent` owns
that relationship, so use it instead of an unlabelled glyph:

```rust
fission_component! {
    pub CloseSettingsButton<()> {
        props { close: ActionEnvelope }
    }
    view(button, _state, cx) =>
    Button(
        child: ButtonIconContent(
            Icon::svg(material::navigation::close::regular()),
            cx.tr("settings.close"),
        ),
        on_press: button.close.clone(),
    ).semantics_identifier("settings.close")
}
```

The parent supplies the actual close action through `CloseSettingsButton(close)`.
There is no separate accessibility-only close path. Use the same rule for
toolbar icons, drag handles, and custom controls: pixels do not supply a name.

## Step 5: keep focus predictable

Most buttons should take focus normally. A formatting toolbar is different:
activating Bold by pointer should not move focus out of the editor whose
selection it modifies.

```rust
fission_component! {
    pub BoldToolbarButton<()> {
        props { toggle_bold: ActionEnvelope }
    }
    view(button, _state, cx) =>
    Button(
        child: Text(cx.tr("editor.bold")),
        on_press: button.toggle_bold.clone(),
        focus_policy: FocusPolicy::PreserveCurrentOnPointer,
    ).semantics_identifier("editor.bold")
}
```

The action must still modify the editor's current selection through its normal
state model. Preserving pointer focus is not a reason to remove the button from
keyboard traversal or suppress its accessible name.

## Step 6: test with semantic selectors

This live scenario uses English bundles and starts with an empty draft:

```rust
use fission_test_driver::SelectorQuery;

client.wait_for_visible(SelectorQuery::semantic_identifier("settings.email"), 5_000)?;
client.fill_text_semantic_identifier("settings.email", "alex@example.com")?;
client.tap_semantic_identifier("settings.marketing")?;
client.tap_semantic_identifier("settings.apply")?;
client.wait_for_text("Applied for this session", 5_000)?;

let tree = client.get_tree()?;
let apply = tree.nodes.iter()
    .find(|node| node.identifier.as_deref() == Some("settings.apply"))
    .expect("apply button semantics");
assert_eq!(apply.label.as_deref(), Some("Apply preferences"));
assert!(!apply.disabled);
```

Use those exact values for `settings.apply` and `settings.applied_this_session`
in this test's English bundle. The test proves the control is reachable and
produces the session notice, not that preferences reached durable storage.
Test the applied state transition separately.

If resolution fails, inspect the candidates and visibility information. A
missing target, ambiguous name, clipped control, and disabled action are
different failures; replacing the selector with coordinates would hide that
distinction.

## Step 7: run manual screen-reader QA

Inspect the real target with its platform screen reader. Check that:

- The title and grouped region are discoverable.
- Each control announces its role, label, current value, and state.
- Focus follows the intended order and activation uses the normal reducer.
- Inputs support editing, selection, and submission.
- Dialog focus enters, stays contained where appropriate, and returns on dismissal.
- Errors and pending states have meaning beyond their colour.

A semantic tree assertion is useful evidence, but does not prove every native
screen-reader bridge behaves identically. Keep platform QA alongside it.
