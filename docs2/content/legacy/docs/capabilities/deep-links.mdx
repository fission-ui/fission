# Deep links

Deep links are inbound lifecycle events from an operating system, launcher, notification, or registered external URL. Ordinary Web URLs and browser history use the route contract instead: the shell initializes `Env.current_route` and dispatches `ShellRouteChanged` for pathname, hash, back, and forward changes.

Keep one route field in app state and let both actions update it. `Router` is Fission's default path matcher, but it is optional; a custom or third-party router can consume the same `RouteLocation` and navigation effects.

For Web, `WebRouteStrategy::Auto` accepts both `/projects/42` and `#/projects/42` and preserves the representation used to launch the app. Choose `Path` when the production host rewrites extensionless routes to `index.html`; choose `Hash` when it cannot. `fission run web` includes the safe SPA fallback and still returns 404 for missing assets. If the app is mounted below the origin root, configure the deployment prefix with `WebNavigationConfig::base_path(...)`.

Use `Link::to("Project", "/projects/42")` for ordinary navigation. Custom widgets can attach `Hyperlink` to `SemanticsRegion` or `Pressable`; Web projects that metadata into a genuine DOM `href`, while Static site and SSR render a normal `<a>`. `Hyperlink` also carries browsing-context targets, `rel`, and download metadata, and semantic regions can declare standards-based popover targets.

This example handles an incoming `fission://document/42` URL and opens the matching document. Treat an incoming link as untrusted input: accept only routes your app understands.

Do not parse process arguments or platform URL callbacks inside arbitrary widgets. Keep route ownership in the shell setup and reduce the typed `DeepLinkReceived` action into normal app state.

## 1. Start with the state the screen needs

Add the smallest state fields the screen needs to render honestly. For this flow, useful state is:

```rust
#[derive(Default)]
struct DeepLinkState {
    // Add these fields to your existing app state.
    pending_route: Option<String>,
    route_error: Option<String>,
}

impl GlobalState for DeepLinkState {}
```

Keep the selected route or an error in app state. The screen should render from that state, not parse the launch URL itself.

## 2. Configure the target and host

There is no `fission add-capability` command for deep links. Configure the accepted route in the shell and register the URL scheme or associated domain with each platform. Android uses intent filters; Apple platforms use URL schemes or associated domains; Windows uses protocol activation. Web uses ordinary routes and requires the server or static host to serve the app at the requested path. Fission can record project metadata in [`fission.toml`](/reference/config/fission-toml/), but the route names and domains are yours to choose and verify.

## 3. Handle the incoming link in a reducer

The shell dispatches `DeepLinkReceived` when a configured link arrives. Validate the URL before turning it into app state:

```rust
fn on_deep_link(state: &mut DeepLinkState, action: DeepLinkReceived) {
    if let Some(id) = action.link.url.strip_prefix("fission://document/") {
        state.pending_route = Some(format!("document:{id}"));
        state.route_error = None;
    } else {
        state.route_error = Some(format!("Unknown link: {}", action.link.url));
    }
}
```

## 4. Configure the shell

Register the scheme and the route prefix the app accepts:

```rust
DesktopApp::new(App)
    .with_deep_link_config(
        DeepLinkConfig::new()
            .scheme("fission")
            .domain("example.com")
            .path_prefix("/document"),
    )
    .on_deep_link(reduce_with!(on_deep_link));
```

Do not accept every URL for a scheme when the app only handles a subset. Keep route validation in the reducer even when the shell filters incoming links.

## 5. Render from the routed state

Deep links are inbound, so there is no button to wire for the route itself. The reducer stores route state, and normal widgets render from that state.

```rust


fission_component!
{
    pub CurrentRoute<DeepLinkState> {
    }
    view(component, _state, _cx) => rust {
        let (ctx, view) = fission::build::current::<DeepLinkState>();
                match view.state().pending_route.as_deref() {
                    Some(route) if route.starts_with("document:") => {
                        DocumentScreen::new(route.to_owned()).into()
                    }
                    Some(_) => Text::new("This link is not supported yet").into(),
                    None => HomeScreen.into(),
                }
    }
}
```
The shell delivers a configured URL, the reducer validates it and updates state, and the widget tree renders the selected route.

## 6. Provide and test the host behavior

Deep links use `DeepLinkConfig`, `DeepLinkReceived`, and shell startup handling; there is no provider trait. Use `.with_startup_deep_link(...)` in tests or custom launchers to simulate a cold-start route. Test matching and non-matching links, cold and warm launches, and unknown routes. A valid link should select the expected screen; an invalid link should leave the app in a safe state.

## Platform expectations

Mobile platforms require explicit scheme or associated-domain metadata before the system will launch the app. Desktop support depends on package registration. Web routes work when the server or static host serves the generated page for the requested path.

For route configuration details, see the [Deep links reference](/reference/capabilities/deep-links/).

Before shipping, verify that the platform launches your app for the intended scheme or domain, that the reducer rejects unknown paths, and that cold-start and already-running app flows select the right route.
