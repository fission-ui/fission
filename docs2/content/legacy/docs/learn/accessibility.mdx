# Accessibility in Fission

Accessibility starts in the shared widget tree. You should not need to rebuild the meaning of each screen separately for every platform.

Widgets lower into Core IR along with semantic data such as role, label, value, focus, checked and disabled state, text selection, scrolling, and available actions. Native shells translate that data for the host accessibility API. LiveTest uses it too, so tests can find controls by meaning instead of by their position on screen.

The same model serves three purposes:

- screen readers and other assistive technology need to know what the UI means;
- keyboard and accessibility actions need to activate the same reducers as pointer input;
- tests need stable selectors that do not depend on pixels or generated node order.

## What assistive technology can use today

The winit shell builds an AccessKit tree from Core IR and layout. AccessKit
connects that tree to the operating system's accessibility API; the presence
of an adapter does not prove every navigation path works on a device.

Current native support is:

| Target | Native accessibility bridge | Practical status |
| --- | --- | --- |
| macOS | AccessKit through the AppKit accessibility stack | Supported for roles, labels, values, focus, text editing actions, control actions, scrolling, and range adjustment. |
| Windows | AccessKit through the Windows accessibility stack | Supported for the same Fission semantics exposed by the winit bridge. Validate with Narrator, NVDA, or JAWS for product releases. |
| Linux | AccessKit through the AT-SPI accessibility stack | Supported where the desktop session and assistive technology expose the expected AT-SPI path. Validate with Orca on your target desktop. |
| iOS | AccessKit through the iOS accessibility adapter | Supported by the shared native bridge where the iOS shell uses the winit path. Validate with VoiceOver on simulator and device. |
| Android | AccessKit through the Android accessibility stack | Partial through the generated AndroidX GameActivity host; native TalkBack navigation is incomplete. Validate actual controls with TalkBack, Switch Access, and Voice Access on the Android versions you ship. |

Static site and SSR render HTML instead. Where the renderer has enough information, that includes native inputs, buttons, links, headings, labels, and ARIA or data attributes. Browser assistive technology uses the browser’s accessibility tree. The canvas Web target does not currently expose a DOM accessibility tree for the canvas-rendered app.

Terminal accessibility depends on the terminal emulator and screen reader. Fission semantics can inform terminal rendering and tests, but the terminal backend does not currently expose the full selector command tree available through the winit LiveTest backend.

## What Fission exports today

The native bridge exports the semantic data that widgets put into Core IR.

| Fission data | Accessibility output |
| --- | --- |
| Role | Button, label, text input, password input, multiline input, email input, number input, phone input, URL input, image, checkbox, radio, switch, dialog, slider, list, list item, or generic container. |
| Label | Explicit semantic label, or inferred text from descendants where appropriate. |
| Value | Text input contents, range value, or explicit semantic value. |
| Bounds | Layout bounds converted into platform accessibility coordinates. |
| Focus | Runtime focus mirrored into the accessibility tree; accessibility focus and blur requests update runtime focus. |
| Disabled and read-only state | Exposed as disabled or read-only metadata. |
| Checked state | Exposed for checkbox, radio, and switch roles. |
| Text selection | Editable text selection is exposed and can be set through accessibility actions. |
| Scroll state | Scrollable nodes expose scroll actions and current scroll offsets. |
| Actions | Click/default, focus, blur, replace selected text, set value, set selection, scroll, increment, and decrement map back into the Fission runtime. |

This is the current contract, not a claim that every platform accessibility feature is complete. Custom rotor behavior and platform landmarks beyond the roles listed here still need implementation.

## Design accessible widgets from the start

Make sure someone using a screen reader gets the same meaning and actions as someone using a pointer. Visual appearance alone does not tell assistive technology what a control does.

Use built-in widgets when they fit. `Button`, `TextInput`, `Checkbox`, `Radio`, `Switch`, `Slider`, `Image`, `Text`, `RichText`, `Scroll`, and `Modal` provide useful semantics or fields for adding labels and identifiers.

Give interactive controls stable semantic identifiers when tests, automation, or host integrations need to find them.

```rust
// In view: pay_action is already bound to the checkout reducer.
Button(
    child: Text(cx.tr("checkout.pay")),
    on_press: pay_action,
)
.semantics_identifier("checkout.pay")
```

An identifier is a stable name for code and tests. It is not a label: the label is what the user hears or reads.

Icon-only controls need an explicit label. `ButtonIconContent` pairs an icon
with its accessible name without requiring a hand-written semantics tree:

```rust
use fission::prelude::*;

// In view: delete_action is bound to the item, not its list position.
Button(
    child: ButtonIconContent::new(
        Icon::svg(material::action::delete::regular()),
        cx.tr("todo.delete"),
    ),
    on_press: delete_action,
)
.semantics_identifier("todo.delete")
```

Resolve accessible names from the same active locale as visible copy.
`cx.tr(...)` is a build-phase helper; reducer contexts do not resolve copy.
If a reducer records a status, store its meaning and translate it in the view.

## Keep focus and actions meaningful

Use the same product action for assistive technology, keyboard, and pointer input. Avoid a separate accessibility-only behavior path unless the product has a specific reason for one.

Fission routes semantic actions through the same widget action entries and reducers. A screen reader activating a button should trigger the same `on_press` action as a tap or click.

Keep focus aligned with the visible interface. Use focus scopes for dialogs and panels. Use `FocusPolicy::PreserveCurrentOnPointer` only when a control, such as an editor toolbar, should not take focus away from the editable region when clicked.

## Test accessibility as behavior

Screenshots cannot tell you whether controls are labelled or operable. Include semantic checks in your tests:

- Reducer tests prove the action changes state correctly.
- Headless Fission tests inspect semantics without launching a real window.
- Live tests use `/cmd` selector actions such as `TapSelector`, `FocusSelector`, `FillText`, `WaitForVisible`, and `GetTree` against a real shell.
- Manual QA should include at least one platform screen reader on every target you ship.

Example LiveTest-style checks:

```rust
client.tap_semantic_identifier("checkout.pay")?;
client.fill_text_semantic_identifier("profile.email", "user@example.com")?;

let tree = client.get_tree()?;
assert!(tree.iter().any(|node| {
    node.identifier.as_deref() == Some("checkout.pay")
        && node.role.eq_ignore_ascii_case("button")
        && !node.disabled
}));
```

## Screen readers and tools to validate with

Test with the assistive technology your users rely on for each target. The tools below are part of compatibility QA, not a replacement for automated tests.

| Platform | Common tools to include in QA |
| --- | --- |
| macOS | VoiceOver, Switch Control, Keyboard navigation, Accessibility Inspector. |
| Windows | Narrator, NVDA, JAWS, Windows Magnifier, Inspect. |
| Linux | Orca, AT-SPI inspection tools, desktop keyboard navigation. |
| iOS | VoiceOver, Switch Control, Dynamic Type, Full Keyboard Access. |
| Android | TalkBack, Switch Access, Voice Access, system font scale. Native TalkBack control of Fission apps is not complete yet. |
| Browser-hosted Static site or SSR | VoiceOver with Safari, VoiceOver with Chrome, NVDA with Firefox/Chrome, JAWS with Chrome/Edge, browser accessibility inspectors. |
