# Runtime model

A Fission app follows the same loop on every target: state holds the app’s data, actions describe user intent, reducers update state, and widgets describe the interface from the current inputs. The runtime turns that description into layout, semantics, and output for the platform shell.

We’ll use a small note editor to make each part concrete. It has a draft, a Save button, and a save result.

## Start with `GlobalState`, `Action`, and the reducer

`GlobalState` holds the product data that needs to survive UI reconstruction. In this example, that is the draft, whether a save is running, and any save error.

```rust
use fission::prelude::*;
use serde::{Deserialize, Serialize};

#[derive(Debug, Default, Clone, Serialize, Deserialize)]
pub struct NoteState {
    pub draft: String,
    pub saving: bool,
    pub save_error: Option<String>,
}

impl GlobalState for NoteState {}
```

`NoteState` is the data model. The derive attributes provide common Rust traits; `GlobalState` marks it as the app’s state type. `Option<String>` represents an error that may not exist yet.

Put a value here when it changes what the product means or shows. Keep transient interaction details, such as animation progress and text selection, in the runtime instead.

An `Action` is a typed message about what happened: the draft changed, Save was pressed, or the save completed. A reducer handles that action and applies the state transition. `#[fission_reducer]` generates the action type and reducer wrapper from one function; use `#[fission_action]` when you need to define an action separately.

```rust
#[fission_reducer(UpdateDraft)]
fn on_update_draft(state: &mut NoteState, ctx: &mut ReducerContext<NoteState>) {
    let Some(change) = ctx.input.text_change() else {
        return;
    };
    state.draft = change.new_text.clone();
    state.save_error = None;
}

#[fission_reducer(SaveSucceeded)]
fn on_save_succeeded(state: &mut NoteState) {
    state.saving = false;
}

#[fission_reducer(SaveFailed)]
fn on_save_failed(state: &mut NoteState) {
    state.saving = false;
    state.save_error = Some("Could not save the note".into());
}
```

The first reducer handles `UpdateDraft`. It reads the text edit from `ctx.input`, replaces the draft, and clears an old error. Reducers are the place for state transitions; widgets and platform callbacks dispatch actions instead of mutating app state from separate paths.

## Then define a Compose component

A `Widget` can be a screen, toolbar, dialog, or small control. A named `fission_component!` declares the state the component reads and returns the widget tree for the current inputs:

```rust
fission_component! {
    pub NoteEditor<NoteState> {
        props {}
    }
    view(editor, state, cx) {
        let save = cx.bind(SavePressed, reduce!(on_save_pressed));
        let update = cx.bind(UpdateDraft, reduce!(on_update_draft));
    } =>
    Column(children: [
        Text("Draft note"),
        TextInput(
            value: state.draft.clone(),
            placeholder: Some("Write something...".into()),
            on_input: update,
        ),
        Button(child: Text("Save"), key: "save-note", on_press: save),
    ])
}
```

`NoteEditor` reads `NoteState`. The view passes the current draft to `TextInput` and binds input and button events to reducers. The view describes the interface and its wiring; the reducers change state.

### What it means for `component conversion` to be pure

Component conversion must be pure: it reads its inputs and returns a widget tree. It must not:

- fetch data or start background work;
- mutate global state or write files;
- call platform APIs while deciding what to render.

Fission can convert a component repeatedly after input, resize, animation, or state changes. Keeping conversion pure means those rebuilds and tests do not accidentally repeat outside work. Describe the screen here; request state changes and effects through reducers.

## `ViewHandle` is the read-only input to component conversion

`ViewHandle` is the read-only input to one component conversion. `view.state()` reads `GlobalState`; the handle also exposes runtime data, environment values, and prior layout information such as animation values, theme, locale, viewport size, and geometry. These inputs are explicit and can be supplied in tests, rather than fetched from a global or operating-system API.

## `BuildCtxHandle` is the write-only wiring helper for component conversion

`BuildCtxHandle` records runtime wiring during component conversion. `cx.bind(...)` connects a widget event to an action and reducer. It can also register runtime-managed behavior such as animations, portals, media, web views, and resources. It records what the runtime should do; it does not perform outside work during conversion.

Use `ViewHandle` to read current inputs. Use `BuildCtxHandle` to declare runtime wiring. Use reducers to change state and request effects.

## `ReducerContext` is for the reducer phase, not the conversion phase

`ReducerContext` is available while a reducer runs. Use it to inspect dispatch input and request work outside the reducer. A reducer can decide that a save should start, but the runtime performs the file, network, or host operation after the reducer returns.

```rust
#[fission_reducer(SavePressed)]
fn on_save_pressed(state: &mut NoteState, ctx: &mut ReducerContext<NoteState>) {
    if state.saving {
        return;
    }

    state.saving = true;
    state.save_error = None;

    // Simplified teaching example: ask the runtime to do the save after
    // this reducer returns, then route the result back as an action.
    ctx.effects
        .app(SAVE_NOTE_JOB, state.draft.clone())
        .on_ok(ctx.effects.bind(
            SaveSucceeded,
            reduce_with!(on_save_succeeded),
        ))
        .on_err(ctx.effects.bind(
            SaveFailed,
            reduce_with!(on_save_failed),
        ));
}
```

Here `ctx.effects.app(...)` requests the save job. `on_ok` and `on_err` bind the completion actions. The job runs after the reducer returns, and its result comes back through a new reducer call. `ctx.input` also carries event or effect data for the current dispatch, such as returned bytes, pointer coordinates, or dropped file paths. The context exists only for that reducer call; do not store it.

## `Selector` keeps large apps from turning into a pile of raw state reads

For derived display values, use a `Selector`. It takes a `ViewHandle` and returns the values a widget needs, such as a formatted title, button-enabled flag, grouped list, or small view model.

For the note editor, the screen might want a title, a status line, a save button label, and a `can_save` flag. Those are not separate pieces of stored state. They are values derived from the current inputs.

```rust
struct EditorVM {
    title: String,
    status_line: String,
    save_label: String,
    can_save: bool,
}

impl Selector<NoteState> for EditorVM {
    type Output = EditorVM;

    fn select(view: ViewHandle<NoteState>) -> Self::Output {
        let first_line = view
            .state()
            .draft
            .lines()
            .next()
            .unwrap_or("")
            .trim()
            .to_string();

        let title = if first_line.is_empty() {
            "Untitled note".to_string()
        } else {
            first_line
        };

        let character_count = view.state().draft.chars().count();

        EditorVM {
            title,
            status_line: format!("{character_count} characters"),
            save_label: if view.state().saving {
                "Saving...".to_string()
            } else {
                "Save".to_string()
            },
            can_save: !view.state().saving && !view.state().draft.trim().is_empty(),
        }
    }
}
```

The widget reads the selector output instead of mixing formatting and derived conditions into its layout:

```rust
let vm = view.select_with::<EditorVM>();
```

Selectors keep view-specific formatting and derived values out of large widget trees. Test them independently, and keep them read-only: they can read `view.runtime` and `view.env`, but they do not mutate state or perform effects.

## The whole model in one pass

For the note editor, typing dispatches `UpdateDraft` and its reducer changes `NoteState`. Pressing Save sets the loading state and requests a job through `ReducerContext`; the completion dispatches another action. The component reads current inputs and binds events, while the selector prepares display values. Product behavior stays in this shared flow across targets.
