# RichText

`RichText` handles one text block that needs mixed styles, inline emphasis,
or inline widgets. If the whole block shares one style, use
[`Text`](/reference/widgets/text).

## Example

```rust
use fission::prelude::*;

fission_component! {
    pub SearchExcerpt<()> {
        props {
            before_match: String,
            matched_text: String,
            after_match: String,
        }
    }

    view(excerpt, _state, cx) {
        let accent = cx.view.env().theme.tokens.colors.primary;
    } =>
        RichText(vec![
            RichTextRun::new(excerpt.before_match.clone()),
            RichTextRun::new(excerpt.matched_text.clone())
                .weight(700)
                .color(accent),
            RichTextRun::new(excerpt.after_match.clone()),
        ])
}
```

The three fragments are document content supplied by the search model, not
three translated UI labels forced into English sentence order. The parent
splits on valid text boundaries; all three runs remain one paragraph so
wrapping and selection follow the text rather than a row of separate widgets.

The matched text has weight as well as colour, so emphasis does not depend
on distinguishing the accent hue.

## Content table

| Field | Type | Meaning | Notes / default behavior |
| --- | --- | --- | --- |
| `id` | `Option<WidgetId>` | Stable widget identity. | Defaults to `None`. |
| `runs` | `Vec<RichTextRun>` | The styled runs that make up the text block. | `RichText::new(...)` fills this for you. |
| `inline_widgets` | `Vec<InlineWidgetSpan>` | Inline widgets embedded in the text flow. | Usually produced through `RichText::from_spans(...)`, not built manually. |
| `annotations` | `Vec<RichTextAnnotation>` | Advanced semantic and interaction annotations over byte ranges. | Usually generated from span builders rather than authored by hand. |
| `semantics` | `Option<Semantics>` | Optional wrapper semantics for the whole block. | Defaults to `None`. |

## Practical model

There are two common ways to build rich text. For simple styling changes, `RichText::new(vec![...runs...])` is enough. For more advanced cases such as inline widgets, hoverable spans, or nested semantics, the span-based constructors are the better fit because they generate the annotations and inline-widget bookkeeping for you.

In both cases, the widget stays declarative. Use `.selectable(true)` when the rendered rich text should behave like selectable read-only document text with the standard Copy / Select All context menu.

The paragraph is still derived from content and state, not a mutable text object.

## Specific advice

Reach for `RichText` because the content truly needs mixed styling or inline semantics, not because it feels more powerful. When uniform text is enough, `Text` is easier to read and maintain.

## Production checklist

- Check grapheme-safe content splits, long lines, bidi text, and selection.
- Keep translated sentences whole unless the translation system owns fragment ordering.
- Verify inline widgets/annotations preserve readable and accessible text.
