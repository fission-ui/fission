# 3D and GL

Depth is useful when it preserves a relationship the reader needs: a path through a building, a grid of spatial readings or the shape of a measured surface. It is less useful when it merely gives ordinary totals a more elaborate appearance. Perspective and occlusion then make the comparison harder without adding information.

The 44 gallery variants below are example presentations, not 44 separate built-in series types. They use `fission::three_d::Scene3D` with cube, sphere and mesh primitives. The resulting scene fits into a normal Fission layout, but its geometry does not automatically acquire chart axes, data labels or per-item interaction.

Enable Fission's `three-d` feature and keep the source data separate from its geometry. Load measurements through the application's effect/reducer flow, validate the projection and render the scene once the required data is available.

## Choosing within this family

Start with the relationship in the data. Independent observations suit a point cloud; ordered observations suit a trajectory; connected samples with justified interpolation can form a surface. A graph needs explicit relationships as well as positions. Choosing the wrong representation can imply a path or surface which the source data never established.

Keep important values and relationships available outside the image. A title names a scene, but cannot explain every node, observation or triangle to a reader who cannot see it.

## Authoring from a Fission component

This small presentation boundary accepts a scene already built by a subject-specific component or geometry projection. It does not fetch data or invent substitute measurements.

```rust
use fission::prelude::*;
use fission::three_d::Scene3D;

fission_component! {
    pub SpatialScenePanel<()> {
        props {
            title: TextContent,
            scene: Scene3D,
        }
    }
    view(panel, _state, _cx) => Column(children: [
        Text(panel.title.clone()),
        panel.scene.clone(),
    ])
}
```
Supply a localised title and size the scene intentionally using its optional `width` and `height`. The legacy `Scene3D` used here exposes no `size`, `camera` or `ambient_light` builder methods. It also does not emit `ChartInteractionEvent` values for individual primitives; choose a scene API with explicit picking support if that interaction is required.

## Options, accessibility, and diagnostics

| Area | What to decide | How to check it |
| --- | --- | --- |
| Geometry | Use finite coordinates, valid indices and intentional scene units. | Test the data-to-geometry projection independently. |
| Meaning | Preserve source gaps, graph relationships and the distinction between planned and observed values. | Test cases where a missing sample could create a false connection. |
| Accessibility | Provide labels, source values and important relationships outside the image. | Check that the same question can be answered without seeing the scene. |
| Failure handling | Distinguish an empty dataset from a failed or incomplete load. | Exercise those states before constructing the geometry. |
| Performance | Bound the display projection whilst retaining original measurements. | Measure representative geometry counts and inspect overlap in a real rendering. |
