# Dataset

A reporting table and a chart are different representations of the same facts. Keep the typed records as the authority, then choose a projection that answers the user's question. Replacing a projection when new data arrives does not require moving fetching or persistence into the widget.

## Where the transformations happen

Use the [products by year](./dataset-products-by-year) example for a complete Compose chart with an actual named-column dataset. The current resolver supports dataset encoding for bar and line series. Other examples deliberately project typed rows into their series' data types; a generic dataset does not automatically bind every chart family.

Sorting, filtering and joining belong before rendering. For example, [ranked bars](./dataset-ranked-bars) sort whole records so labels do not become detached from values, whilst the [coverage map](./dataset-map-coverage) joins stable region IDs to supplied geometry. Invalid or missing records need an explicit policy: a numeric fallback to zero is not validation.

## What live means here

A live component receives completed snapshots from application state. Effects obtain external data; reducers accept the current completion and update that state. Keep request generations when a late response could overwrite newer results. The chart itself is not a transport, scheduler or persistence layer.

Choose [brushing](./dynamic-brush-telemetry) for inspecting points, [quarter navigation](./dynamic-timeline-quarters) for selecting a report, and [application commands](./dynamic-toolbox-telemetry) for real export/reset behavior. Visual timeline or toolbox configuration alone does not implement those workflows.

Translate visible titles, series names, units and summaries in the parent. Keep exact values available without relying only on colour, and test the source-to-projection mapping independently from screenshots. Gallery images use separate fixture data; they do not qualify the examples' interactions.
