# Components and interaction

A chart can explain its values, let users inspect them, or let users act on them. Those are separate responsibilities: a threshold line explains a reference, a tooltip reveals data, and a brush completion can dispatch a reducer.

These twenty-three examples distinguish the actual mechanisms from their appearance. In particular, current timeline and toolbox graphics do not implement automatic playback or utility commands simply because labels are drawn.

## Match the mechanism to the claim

Use data-coordinate marks for numeric observations and reference values. Use `ChartGraphic` for plot-relative decoration; its position does not follow a deployment timestamp through a changed window.

Use actual `DataZoom` and `ChartBrush` configuration for their gestures. Brush completions arrive through `ChartBrushSelection::from_action_input(&cx.input)` in a reducer. Plot fractions and data indices are projection details, not durable application-record identities.

The current timeline is an indicator. Its labels and interval field do not implement dataset selection or automatic playback. Likewise, toolbox labels are not functioning reset/save/zoom/brush commands. The relevant pages show standard Compose controls and reducers for operations the application must own.

## Compose and required inputs

Built-in chart configuration uses ordinary `Chart(...)` composition. Reusable prop components in these examples are constructed with fully specified Rust struct literals: their required fields are supplied explicitly rather than assuming a generated `Default` exists. No `rust { ... }` escape block or additional framework API is required.

Keep translated labels and design-system colours in parent-supplied inputs. The actual chart fields include `graphics: Vec<ChartGraphic>`, `mark_points: Vec<MarkPoint>`, `mark_lines: Vec<MarkLine>` and `mark_areas: Vec<MarkArea>`; singular builder-method names are not field types.

## Verify an interaction by using it

A screenshot can show a preview region without proving that a drag works. Use LiveTest to activate controls, drag continuously, release, rebuild and inspect the resulting state. Test empty selections, boundary values, missing data and changed snapshots.

Keep equivalent text, tables and input controls available when hover or pointer gestures are unsuitable. A painted annotation is not automatically a complete accessibility relationship or an application action. Gallery screenshots are reference fixtures, not a substitute for those checks.
