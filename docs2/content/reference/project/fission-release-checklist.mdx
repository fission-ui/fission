# Fission release checklist

This checklist is for maintainers releasing the Fission framework itself. It is
not the app-store publishing flow for apps built with Fission.

Prepare the release in a branch, then merge its PR after local qualification and
CI pass. Tag the resulting clean `main` commit, not an earlier branch revision
or a working tree containing unreviewed edits. Run the following commands from
the Fission checkout:

```sh
git switch main
git pull --ff-only origin main
git status --short
git switch -c release/prepare-<new-version>
```

Start with a clean working tree so release preparation cannot accidentally
include another change. Create the release-prep branch before editing versions.
The tag and published packages must identify the exact qualified commit.

## 1. Confirm release scope

Decide the exact version and whether it is breaking.

- Patch releases fix bugs or docs without requiring app code changes.
- Minor releases can include public API additions and coordinated workflow
  changes.
- Breaking changes must be called out in the blog post, changelog, GitHub
  release notes, and migration section.

Collect the merged work since the last tag:

```sh
git describe --tags --abbrev=0
git log <previous-tag>..HEAD --oneline --decorate
gh pr list --state merged --base main --limit 100
```

Group the scope by user impact rather than by commit order: runtime, widgets,
shells, CLI, packaging, docs, examples, tests, and migration notes.

## 2. Update versions

Bump every stable Fission workspace crate and internal dependency requirement
to the new framework version. Independently versioned alpha crates keep their
exact prerelease version unless that alpha API is being released again. Do not
bump forked third-party packages unless that fork actually changed.

For a release from `<old-version>` to `<new-version>`, update these values:

- every stable first-party `package.version = "<old-version>"` to `"<new-version>"`;
- every stable first-party dependency `version = "<old-version>"` to `"<new-version>"`;
- documentation snippets that tell users to depend on the old Fission version;
- generated-app snippets and `fission init` templates, including the generated
  `AGENTS.md` design-system codegen version;
- `docs2/Cargo.toml` and site chrome that displays the current version;
- `CHANGELOG.md`, release blog post, and any release notes source file.

Keep these dependency versions unchanged unless the corresponding fork release
is part of the same release:

- `fission-vello`, `fission-vello-encoding`, `fission-vello-shaders`;
- `fission-winit`;
- `fission-accesskit-winit`.

Useful search before and after the bump:

```sh
OLD_VERSION="0.8.0" # replace with previous release version
rg -n "${OLD_VERSION}|fission = \\{ version|fission-design-system-codegen" \
  README.md CHANGELOG.md crates docs2 examples
```

After editing, regenerate the lockfile:

```sh
cargo metadata --format-version 1 >/dev/null
```

## 3. Update documentation and examples

A release is not ready when the crates compile but the public docs still point
at the previous version or old behavior.

Check these areas explicitly:

- `README.md` and crate READMEs under `crates/**/README.md`;
- Learn, Guides, Cookbook, and Reference dependency snippets;
- CLI reference pages for new or changed commands;
- `fission.toml` reference for manifest shape changes;
- platform target pages for generated Android, iOS, macOS, Windows, Linux, Web,
  Terminal, Static site, and SSR output;
- examples that demonstrate changed widgets, shell behavior, package flows, or
  testing APIs;
- generated project templates and generated `AGENTS.md` content.

When docs describe a breaking change, include the old behavior, the new behavior,
and the concrete migration step.

## 4. Write the changelog entry

Add the new version to the top of `CHANGELOG.md`.

Use the existing structure:

```md
## [<new-version>] - YYYY-MM-DD

### Added

### Changed

### Fixed

### Migration notes
```

Only include headings that have content. Keep entries user-facing: explain the
capability or bug that changed, not just the module name.

## 5. Write the release blog post

Create a blog post under `docs2/content/blog/` using the existing naming
pattern:

```text
docs2/content/blog/YYYY-MM-DD-fission-<version-with-dashes>-short-title.mdx
```

The post must include:

- frontmatter with `title`, `authors`, `tags`, and `categories`;
- a short opening that states the release theme;
- sections for the major user-facing changes;
- a migration section with the dependency snippet for the new version;
- any target-specific package prerequisites or feature flags;
- links to issues or PRs when they clarify why the change exists.

Use the blog post as the source for GitHub release notes unless the release has a
separate notes file.

## 6. Run pre-release checks

Start with deterministic checks that do not mutate external services.

```sh
cargo fmt --all -- --check
cargo test --workspace
cargo run -p cargo-fission --bin fission -- site check --project-dir docs2 --release
cargo run -p cargo-fission --bin fission -- package --project-dir docs2 --target static-site --format static --release
```

For release workflow changes, run the narrow package/release tests too:

```sh
cargo test -p fission-command-package
cargo test -p fission-command-release
cargo test -p fission-command-ui
cargo test -p fission-test-driver
```

For shell or widget changes, run the affected examples or LiveTests. Prefer
semantic LiveTest commands and screenshots over coordinate-only checks when the
feature is visible UI.

If a required platform cannot be tested locally, use its approved build host.
Record any remaining qualification gap and do not imply that the platform was
validated. A missing required release check remains a blocker, not something a
limitation note silently waives.

## 7. Dry-run crates.io publishing

The preferred path is the **Release Fission** workflow in GitHub Actions. Enter
the version without a `v` prefix after the release-prep commit has reached
`main`. The workflow tags that exact commit, creates a draft GitHub Release,
uses the matching changelog section as its release notes, publishes in dependency
order only after every missing package passes a dry run, and verifies the
installed public CLI by creating and serving a fresh Web application.

Configure the `crates-io` GitHub environment with a
`CARGO_REGISTRY_TOKEN` secret. If crates.io throttles or has not propagated an
upload, the release job exits instead of occupying a runner. It enables the
normally dormant **Resume deferred Fission release** workflow, which checks at
five-minute intervals and dispatches a resume from the immutable tag. A resumed
run verifies already-published framework archives against the release commit
before skipping them. Independently versioned alpha prerequisites are verified
by registry checksum, package identity, clean source provenance, and confirmation
that the package source has not changed since its earlier publishing commit. An
alpha package that changed must receive a new prerelease version. The resumer
disables itself when no draft release remains.

The commands below remain the manual fallback and explain the ordering enforced
by `scripts/publish_release_crates.sh`.

Publish only first-party crates, not examples or the documentation site crate
unless that is an explicit release goal.

Use `--dry-run` first. The release script owns the publish order; inspect it
rather than maintaining another list in this page:

```sh
scripts/publish_release_crates.sh --list
```

Before a release, compare that list with the publishable workspace packages and
their internal dependencies. A newly introduced crate, including a Compose
crate, must be present before a dependent facade can be published. A successful
local path-dependency build does not prove that its registry dependencies exist.

Command pattern:

```sh
cargo publish -p fission-ir --dry-run
cargo publish -p fission-ir
```

Wait for crates.io indexing when a later crate depends on a newly published
version. If a publish fails because the index has not caught up, retry after a
short wait; do not change versions to work around indexing delay.

## 8. Commit, tag, and push

Commit only the reviewed release-prep files after local checks pass. Stage exact
paths, not whole source directories that might contain unrelated edits:

```sh
git status --short
git add <reviewed-release-file> <another-reviewed-release-file>
git diff --cached --check
git diff --cached
git commit -m "chore(release): prepare fission <new-version>"
git push -u origin release/prepare-<new-version>
```

Open and merge the release-prep PR through the repository's normal review flow.
Then update local `main`, confirm its exact commit and clean status, and use the
release workflow described above to create the immutable tag. The workflow owns
tag creation in that path; do not create a competing tag manually.

For an explicitly selected manual release, create the tag only after confirming
that the qualified source revision is the merged `main` commit:

```sh
git switch main
git pull --ff-only origin main
git status --short
git rev-parse HEAD
git tag -a v<new-version> -m "Fission <new-version>"
git push origin v<new-version>
```

Do not move a published tag. If the tagged source is wrong, stop publication and
prepare a new version from a corrected commit. Keep any partially published
packages attached to their original source revision.

## 9. Publish crates

Run the real `cargo publish -p ...` sequence after the release-prep commit is on
`main`. Publish from the same commit that carries the version bump and docs.

After publishing, inspect the public index for the main user-facing crates:

```sh
cargo search fission --limit 5
cargo search cargo-fission --limit 5
```

A search result establishes discoverability, not source or archive identity.
Verify the package archives against the release commit through the release
workflow's checks before calling the release complete.

If one crate publishes and a later crate fails, fix forward with the smallest
safe change. Do not yank a crate unless the published artifact is harmful or
unusable. Document any partial-publish state in the release issue or PR.

## 10. Create the GitHub release

Use the tag and the prepared release notes.

```sh
gh release create v<new-version> \
  --title "Fission <new-version>" \
  --notes-file path/to/prepared-release-notes.md
```

The GitHub release notes should include:

- a short release theme;
- added, changed, and fixed sections;
- migration notes;
- known limitations;
- links to the blog post, changelog, and important issues/PRs.

If binaries or generated artifacts are attached, record their source commit and
how they were built.

## 11. Publish and verify the website

The website publishes through the repository workflow when docs change on `main`.
Verify the workflow and the live site.

```sh
gh run list --workflow publish-website.yml --limit 5
gh run watch <run-id>
```

Check the live pages after deployment:

- the release blog post is reachable;
- dependency snippets show the new version;
- the reference sidebar includes any new reference pages;
- search indexes include the new pages;
- the footer/version chrome does not show an old release.

## 12. Post-release verification

Install the released CLI in a clean environment or from crates.io once the index
is available:

```sh
cargo install cargo-fission --version <new-version> --locked
fission --version
```

Use your normal release-validation workspace outside the source checkout. In an
unused child directory, create an app with the published CLI and verify the
public happy path on a host available on that machine:

```sh
fission init release-smoke --name release-smoke
cd release-smoke
fission add-target web
fission test --target web
fission run --target web --no-open
```

Record any failures as follow-up issues. If the failure blocks normal use, ship a
patch release rather than editing the already-published release in place.
