Fission 0.7.1 is a release-tooling hardening release. It turns the build, package, release-content, and publish path into a single auditable workflow that can be driven from CI, the direct CLI, guided terminal prompts, the Terminal TUI, or the windowed publish app.

The goal is simple: if Fission says a release is ready, that status must come from a deterministic check or a completed provider operation. If something is recommended but not required by the target store, Fission reports it as skippable instead of silently blocking or pretending the release is complete.

## One release workflow

The publish flow now builds a shared release plan with the selected target, package format, provider, track, locales, release version, build number, requirements, capabilities, and steps.

That plan is consumed by:

- `fission readiness release`;
- `fission publish`;
- guided publish prompts;
- the Terminal TUI;
- the windowed publish UI;
- CI JSON mode.

This removes the previous problem where different command surfaces could drift into different release behavior.

## Safer packaging and artifact reuse

Package readiness now checks more of the actual release artifact before provider mutation:

- selected app icon source and generated icon manifest;
- target, format, version, build, source config hashes, and artifact hashes;
- package validation receipts for install/load smoke checks;
- stale existing artifact manifests before expensive rebuilds;
- secondary artifacts such as debug symbols or crash diagnostics and whether the selected provider covers them.

For Linux and Terminal `.run` packages, Fission now verifies the embedded archive, performs a temporary install, validates the install receipt, and uninstalls during package creation. Static packages now write a deterministic load-smoke receipt before the artifact manifest is finalized.

## Provider-aware publishing

The provider layer now records clearer upload plans, provider request/response summaries, provider status observations, stdout/stderr line events, uploaded assets, uploaded byte totals, deployment ids, canonical URLs, preview URLs, manual follow-up, and skipped requirements.

Notable provider improvements include:

- Google Play uses correct edit validate/commit semantics and supports internal app sharing for APK/AAB artifacts.
- App Store Connect can upload screenshots, previews, review attachments, assign TestFlight groups, and submit App Review actions through explicit commands.
- Microsoft Store distinguishes draft updates, private flights, public submission, and certification state, with screenshots/logos uploaded through listing asset APIs.
- GitHub Releases uses an explicit duplicate-asset policy instead of silently replacing assets.
- S3 can inspect the exact object keys planned from an artifact manifest and report `ok`, `partial`, or `missing`.
- Docker registry status checks every configured tag or falls back to tags from docker image metadata.

Some provider behavior remains intentionally explicit: Microsoft Store trailer upload is still a handoff manifest, provider-console rollback remains manual where the provider does not expose a safe API, and Fission does not reimplement provider portals.

## Release-content and metadata are first-class

Store-bound release flows now present release notes, screenshots, localized metadata, privacy/review information, tester setup, and provider assets as release-plan requirements.

The requirement model distinguishes:

- provider-required items;
- Fission-recommended items;
- optional items;
- not-applicable items.

Recommended items can be skipped explicitly and appear in the receipt. Provider-required items still block mutation.

## Secure local and CI credential handling

The release workflow keeps secret material out of `fission.toml`. Secret-bearing paths and inline secret material are rejected for signing and provider credentials.

Local interactive publishing uses private state under `~/.fission/<app-name>/` where needed. CI uses environment variables, base64 environment variables decoded into temporary files, provider CLI auth state, or provider-owned authentication.

The old hidden vault concept remains removed.

## Better automation surfaces

0.7.1 also adds and hardens release automation surfaces:

- `release-config set`, `add-release`, `skip-requirement`, and `bump-build` support dry-run, confirmation, and JSON receipts.
- `release-config version-state` compares local version/build state with provider state where possible and reports actions such as `bump-build` or `upload-new-build`.
- `release-config write-file` writes release sidecar files by release id and kind so scripts do not need physical path knowledge.
- `release-workflow run` supports declarative Fission command recipes with readiness gates, normalized argv, declared inputs/outputs, status, exit codes, and non-overwriting receipts.

## Test-control improvements

Release-content screenshot capture can now use selector-aware test-control actions, including tap, focus, scroll-into-view, fill, clear, toggle, and select. Selectors can target semantic identifiers, widget IDs, roles, labels, accessibility/test identifiers, and scoped duplicate matches.

This makes release screenshots and automated UI checks less dependent on fragile coordinates.

## Migration notes

Update Fission dependencies to 0.7.1:

```toml
fission = { version = "0.7.1", default-features = false, features = ["desktop"] }
```

For release automation, run the readiness plan before publishing:

```sh
fission readiness release \
  --target android \
  --format aab \
  --provider play-store \
  --track internal \
  --locale en-US \
  --json
```

Then publish either from a freshly built artifact or an existing artifact manifest:

```sh
fission publish \
  --provider play-store \
  --artifact target/fission/release/android/aab/artifact-manifest.json \
  --track internal \
  --locale en-US \
  --yes \
  --json
```
